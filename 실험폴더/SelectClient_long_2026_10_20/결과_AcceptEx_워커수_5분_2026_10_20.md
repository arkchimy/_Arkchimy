# AcceptEx 워커 수(w1/w2/w4) 5분 연속 측정 (루프백, 2026-10-20)

## 측정 목적
짧은 측정(12초×3회)의 회차 편차가 커서, 조건마다 5분씩 길게 돌려 워커 수에 따른 처리량 차이와 시간에 따른 변화를 본다.

## 측정 조건
- **서버**: AcceptExServer, slotCnt 1000, 워커 1 / 2 / 4. backlog 65535.
- **클라이언트**: `FloodClient_Select_t8_o100` — 스레드 8 × 세션 64, select 타임아웃 100ms, 호출별 임시 태그 포함.
- **절차**: 서버 시작 → 2초 → 클라 시작 → 3초 워밍업 → 프로파일 리셋 → **300초** → 저장 → 종료 → 10초 대기. 조건당 1회.
- **CPU 클럭**: 측정 중 5초마다 `\Processor Information(_Total)\% Processor Performance` 기록 (기준 클럭 1.3GHz 대비 %, 300% ≈ 3.9GHz).
- **환경**: Core Ultra 5 125U 노트북, **배터리 상태**(전원 어댑터 미연결), 전원 계획 균형 조정.

## 관찰
- **5분 평균으로는 워커 수에 따른 차이가 없다.** w1 9.7k, w2 9.2k, w4 9.3k.
- **처리량이 CPU 클럭을 따라 움직인다.** 세 조건 모두 1분 단위 TPS가 오르내릴 때 CPU성능%도 같이 오르내린다(예: w1 311%→227%일 때 11.2k→8.2k, w4 3분차 197%에서 6.7k로 하락). 배터리 상태 노트북의 전력·발열 한도가 측정값을 지배하고 있다.
- **병목 위치는 워커 수에 따라 바뀐다.**
  - w1: GQCS 3us(워커가 쉬지 않음), 클라 select 13.9ms(클라는 응답을 기다림) → **서버 병목**.
  - w4: GQCS 250us(워커가 일감을 기다림), 클라 select 0.1ms → **클라 병목**.
  - 그런데 두 병목의 상한이 이 환경에서 모두 ~10k 근처라, 워커를 늘려도 클라 상한에 막혀 처리량이 오르지 않는다.
- 워커가 늘수록 서버 1건 처리 시간과 클라 호출 시간이 같이 늘어난다(서버 socket 30→88us, 클라 connect 283→455us). 같은 PC의 CPU·커널을 나눠 쓰는 루프백 측정의 한계다.

## 결론
이 환경(배터리 노트북, 루프백)에서는 **워커 수의 효과를 측정할 수 없다.** 전원 어댑터 연결·성능 모드 고정, 또는 클라를 별도 PC로 분리한 뒤 재측정해야 한다.
