# AcceptServer 처리량 측정 — 클라이언트 스레드 수별 (루프백, 2026-10-18)

## 측정 목적
블로킹 `accept()` 서버(AcceptServer)에 대해, **클라이언트 스레드 수**를 늘려가며
- 클라이언트의 **ConnectTPS** (초당 connect 시도 수)
- 서버의 **AcceptTPS** (초당 accept() 반환 수)

가 어떻게 변하는지 본다.

## 측정 조건
- **서버**: AcceptServer(`mode=accept`). 블로킹 `accept()` **전담 스레드 1개 고정** 구조라, worker 수 분류는 의미 없음(측정에서 제외). backlog=65535.
- **클라이언트**: NonBlocking FloodClient(`FloodClient_NonBlocking`, 당시 이름 `FloodClient_Blocking`). 논블로킹 `connect()`로 SYN만 보내고 핸드셰이크 완료를 기다리지 않은 채 `SO_LINGER(0)` + `closesocket()`으로 즉시 닫는 루프. 스레드 수 = 1, 2, 4, 8, 16, 32.
- **경로**: 루프백(127.0.0.1:32000). 서버·클라이언트를 같은 PC에서 실행.
- **측정 방식**: 각 조건 13초 실행, 워밍업 2초 제외 후 **10초 구간(초당 샘플 10개)의 평균**.
- ConnectTPS = 클라이언트가 센 connect 시도 수(수립 성공 여부는 클라가 판단하지 않음). AcceptTPS = 서버 `accept()` 반환 수.

## 결과

```
Threads  ConnectTPS  AcceptTPS  SrvCPU%  SysCPU%
-------  ----------  ---------  -------  -------
      1      10,128      9,788      1.7     14.7
      2      16,589     16,005      3.7     24.0
      4      20,161     19,779      4.6     38.4
      8      23,134     11,008      4.0     54.8
     16      28,565      2,657      1.1     49.9
     32      30,001      1,067      0.7     49.0
```
(ConnectTPS=클라 시도, AcceptTPS=서버 accept 반환, SrvCPU%=서버 프로세스 CPU, SysCPU%=시스템 CPU)

## 관찰
- **스레드 1~4**: ConnectTPS ≈ AcceptTPS. 클라 시도와 서버 accept가 보조를 맞춘다. AcceptTPS는 스레드 4에서 약 19,800으로 **정점**.
- **스레드 8 이상**: ConnectTPS는 계속 오르는데(최대 30,001) AcceptTPS는 **역으로 붕괴**(11,008 → 2,657 → 1,067). 클라가 더 몰아칠수록 서버 accept 처리량이 오히려 급락.
- 붕괴 구간에서 **서버 프로세스 CPU는 ~1%**(accept 스레드가 일을 못 받고 굶음)인데 **시스템 CPU는 45~60%**로 높다. 즉 CPU는 accept 스레드가 아니라 **커널**이 쓰고 있다. 클라가 핸드셰이크 완료 전에 즉시 닫으면, 서버 커널은 연결마다 half-open(SYN_RCVD) 상태를 만들고 SYN-ACK를 보낸 뒤 곧바로 도착한 RST로 그 상태를 부순다 — 수립도 되지 못한 연결을 **만들었다 부수는 헛일**이 초당 수만 번 발생한다. 이 연결들은 accept 큐(백로그)에 도달하기 전에 죽으므로 accept 스레드는 받을 게 없어 굶는다. (헛일과 커널 락 경쟁의 정확한 비중은 따로 측정하지 않았다.)
- 이 붕괴 수치(t16 ~2,500, t32 ~1,050)는 과도 현상이 아니라 10초 내내 안정적으로 유지됐다.

## 클라이언트 close 방식 비교 — 즉시 close vs 블로킹 connect (추가 측정)

위 결과에서 스레드 8 이상일 때 AcceptTPS가 붕괴한 원인을 확인하기 위해, 클라이언트의 연결 종료 방식을 바꿔 다시 측정했다.

- **즉시 close**: 논블로킹 `connect()`로 SYN만 보내고 핸드셰이크 완료를 기다리지 않은 채 `SO_LINGER(0)` + `closesocket()`. (위 측정과 동일)
- **블로킹 connect**: 소켓을 논블로킹으로 바꾸지 않아 `connect()`가 **핸드셰이크 완료까지 블로킹**한 뒤 close. 연결이 실제로 수립되어 서버 백로그 큐에 적재된 뒤에야 다음 시도로 넘어간다.

(단위: 초당 평균. Connect = 클라 시도 수, Accept = 서버 accept() 반환 수)

```
Threads  Imm_Connect  Imm_Accept  Blk_Connect  Blk_Accept
-------  -----------  ----------  -----------  ----------
      1       10,128       9,788        5,560       5,254
      2       16,589      16,005       14,848      13,750
      4       20,161      19,779       19,266      17,965
      8       23,134      11,008       19,794      13,718
     16       28,565       2,657       16,660      12,020
     32       30,001       1,067       16,558      11,974
```
(Imm_ = 즉시close, Blk_ = 블로킹 connect)

### 해석
- **즉시 close**: 스레드가 늘수록 AcceptTPS가 붕괴한다(스레드 4의 19,779 → 스레드 32의 1,067). ConnectTPS는 계속 오르는데 Accept만 추락.
- **블로킹 connect**: AcceptTPS가 **붕괴하지 않는다**(스레드 16에서 12,020, 32에서 11,974로 유지). ConnectTPS와 AcceptTPS가 끝까지 나란히 붙어 있다.
- → 즉시 close는 연결이 핸드셰이크 완료 전(SYN_RCVD) 단계에서 RST로 죽어 **서버 백로그 큐에 도달조차 못 하게** 만든다. (큐에 이미 들어간 연결은 RST로 빠지지 않는다 — 죽는 지점은 큐 도달 전이다.) 이것이 accept 붕괴의 원인임이 데이터로 뒷받침된다. 블로킹 connect는 수립을 끝낸 뒤 닫으므로 연결이 큐에 정상 적재되어 accept가 받아낸다.
- 부수 관찰: 블로킹 버전은 저스레드(스레드 1)에서 ConnectTPS가 더 낮다(5,560 vs 10,128). 스레드마다 핸드셰이크 완료를 기다리기 때문이며, 동시성이 올라가면(스레드 4~) 즉시 close와 비슷한 수준까지 회복한다.

## 결론
이 측정이 보여주는 것은 "서버의 처리 성능 한계"가 아니라 **공격적인 트래픽 패턴이 서버 자원을 낭비시키는 현상**이다.
- 클라이언트가 SYN만 던지고 핸드셰이크 완료 전에 즉시 닫는(`SO_LINGER 0` → RST) 패턴은, 서버 커널이 half-open(SYN_RCVD) 상태를 **만들었다 부수는 헛일**을 반복하게 만든다. 클라가 몰아칠수록(스레드↑) 이 헛일이 늘어 시스템 CPU를 잠식하는데, 정작 수립된 연결은 accept 큐에 도달하지 못해 서버의 실질 처리량(AcceptTPS)은 오히려 붕괴한다.
- 블로킹 connect(정상적으로 핸드셰이크를 끝내고 닫는 클라)에서는 이 붕괴가 나타나지 않는다. 연결이 정상 수립되어 큐에 적재되고 accept가 받아낸다. → 붕괴의 원인은 서버가 아니라 **클라이언트의 비정상(남용) 종료 패턴**임이 대비로 드러난다.
- 따라서 이 현상의 완화는 서버 아키텍처 튜닝이 아니라 SYN flood류에 대한 방어(연결 속도 제한, SYN 쿠키 등)의 영역이다. 서버 drain 측의 구조적 상한(단일 리슨 소켓 accept 큐 락)은 이와 **별개의 축**으로, 리슨 소켓 샤딩으로 완화할 수 있다.

## 주의
- 루프백 측정이라 서버·클라이언트가 **같은 CPU 자원을 경쟁**한다. 시스템 CPU%는 두 프로세스 + 커널 네트워크 처리의 합산 관점으로 봐야 하며, 절대 성능이 아니라 **조건 간 상대 비교**용이다.
- 유선랜(100Mbps)에서 보였던 SYN_RCVD 교착·재전송 폭주는 RTT가 µs인 루프백에서는 재현되지 않는다. 이 측정은 "SYN flood 현상 재현"이 아니라 **accept 처리량과 클라 동시성의 관계**를 보는 용도다.
