===========================================================
핸드오프 - AcceptServer accept 붕괴 현상 분석 (2026-10-19)
===========================================================

[오늘 한 일]

1. 팩트체크: 백로그(accept) 큐에 "이미 들어간" 연결은 RST로 제거되지 않는다.
   - IBM APAR IY54858: 핸드셰이크 완료 후 리스너 큐에서 대기 중인 소켓에 RST가 와도
     큐에서 안 빠지고, accept() 호출 시 해제되며 accept는 ECONNABORTED 반환.
   - 유저 주장(큐에서 빼는 방법은 accept가 먼저 꺼내는 것)이 맞음으로 확인.

2. 붕괴 기전 교정 (이전 가설 수정):
   - 틀린 가설: "RST가 큐의 연결을 끊어서 붕괴"
   - 교정된 기전: 연결이 accept 큐 "도달 전"(SYN_RCVD/half-open 단계)에서 RST로 죽음.
     즉시-close가 핸드셰이크 완료 전에 RST를 보내 → 커널이 half-open을
     만들었다 부수는 "헛일"만 반복 → 연결이 큐에 도달 못 함 → accept 스레드 기아.
   - 데이터 근거: 서버 프로세스 CPU ~1%(굶음) vs 시스템 CPU 45~60%(커널 헛일).

3. NIC 인터럽트 / 병렬성 팩트체크:
   - 물리 NIC: RSS 없으면 인터럽트+DPC가 한 CPU에 몰림. RSS 있으면 4-tuple 해시로
     여러 코어 병렬(단 같은 연결은 같은 코어). 하이퍼스레딩 논리코어는 RSS 제외.
   - 루프백(127.0.0.1): 물리 NIC/하드웨어 인터럽트 자체가 없음. 소프트웨어 스택 처리.
     => 이번 측정의 SysCPU 상승은 NIC 인터럽트가 아니라 루프백 스택+RST 처리의 합산.

4. 커널 락 구조:
   - 커널도 자원 단위 락(인터럽트/DPC 문맥은 스핀락). 완전 병렬 불가.
   - 최대 직렬화 지점 = "단일 리슨 소켓의 accept 큐 락"(깔때기).
   - 힙 할당은 per-CPU 캐시, 연결 해시는 버킷 단위 락으로 분산(부분 병렬).
   - 완화: 리슨 소켓 샤딩(Linux SO_REUSEPORT). 벤치 100K->335K accept/s 사례.
   - 유저 CPU 상승 해석: 주로 "헛일(half-open 생성/파기)"이지 락 스핀이 주범 아님.

5. 주제/명칭 확정:
   - 이 현상은 "진짜 SYN flood 공격"이 아님(소스 위조/큐 고갈 아님).
   - 정식 용어 분해:
     (1) 클라 행동 = abortive close(하드 클로즈): SO_LINGER(0) -> RST (Winsock 공식 용어)
     (2) 죽는 자리 = half-open / embryonic connection (SYN_RCVD)
     (3) 서버 결과 = accept 큐 기아 / 처리량 붕괴
   - 추천 주제: "abortive close(RST)로 인한 half-open 연결 churn과 서버 accept 붕괴"

6. 문서 규정 방향 합의:
   - 결론은 "서버 성능 한계"가 아니라 "비정상 종료 패턴이 서버 자원을 낭비시키는 현상".
   - 단, 이것을 '목적(풀어야 할 문제)'으로 세우지 않음 -> 해결책(SYN쿠키/방화벽)은
     OS/엣지 레벨이라 앱(게임서버) 범위 밖. 이 문서의 범위는 "발견 + 원인 규명"까지.
   - 서버 설계자 관점 교훈: "피어 생존 증명 전엔 연결당 상태를 할당하지 않는다"
     (TCP=SYN쿠키, 직접 설계 전송계층=connect-token/stateless handshake. RUDP 연결점).
