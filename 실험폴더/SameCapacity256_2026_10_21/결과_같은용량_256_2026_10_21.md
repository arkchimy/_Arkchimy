# accept vs AcceptEx — 수용 용량 256으로 맞춘 비교, 5분 (루프백, 어댑터, 2026-10-21)

## 목적
수용 용량을 같게 맞춰도 AcceptEx가 거절을 덜 하는지 확인한다.
AcceptEx의 이점이 "걸어둔 소켓만큼 용량이 커서"뿐인지, 수락 방식 자체에도 있는지 가린다.

## 조건
- 용량: accept = backlog 256(`SOMAXCONN_HINT`). AcceptEx = backlog 200 + slotCnt 56 = 256.
  AcceptEx 용량 = backlog + slotCnt는 같은 날 용량 확인 실험(`Capacity_w0_2026_10_21`)에서 확인.
- 서버: 기존 바이너리(10/20 측정과 같은 파일). accept 전담 스레드 1개 / AcceptEx 워커 1개.
- 클라: `FloodClient_Select_t8_o100`(동시 512개 > 용량 256), 코드 수정 없음. 4-1(backlog 200 5분)과 같은 클라 조건.
- 절차: 서버 시작 → 2초 → 클라 시작 → 3초 워밍업 → 300초 → 클라 종료 → 서버 종료 → 10초. accept → AcceptEx 순, 각 1회.
- 시작 전 포트 32000 잔여 연결 0, 전 구간 어댑터 연결(BatteryStatus 2).

## 관찰
- **용량을 같게 맞추면 AcceptEx가 거절을 더 많이 했다.** 실패율 0.336% vs 0.038%(약 9배). accept는 처음 1~2분 뒤 거의 0으로 줄었고, AcceptEx는 5분 내내 초당 35~40건이 유지됐다(실패 난 초 263/295).
- 처리량은 비슷하다(평균 10.2k vs 10.9k, 차이 6% — 같은 조건 회차 간 차이 수준).
- 4-1(backlog 200, AcceptEx slotCnt 1000)에서 AcceptEx가 거절 0이었던 것은 **수락 방식이 아니라 걸어둔 소켓 1000개만큼 용량이 커서**였다는 쪽과 맞는다.
- AcceptEx w1 s56의 모양(처리량 저하 + 지속적 소량 실패)은 10/20 AcceptEx w1 s8(9.6k, 0.17%)과 비슷하다. 워커 1개가 완료 꺼내기 + closesocket + socket + AcceptEx 재등록을 모두 해서, 걸어둔 소켓이 다시 채워지는 속도가 accept 스레드가 백로그를 비우는 속도보다 느린 것으로 보인다(추정, 프로파일 미저장).
- 한계: 각 1회, 워커 1개만. AcceptEx 워커를 늘리면 재등록 속도가 달라질 수 있다.

클라 select 대기(us): w2 s56 1,931 / w4 s56 1,176 / w2 s500 134 / w4 s500 984

- **Post(AcceptEx 등록)는 slotCnt를 늘리면 줄었다.** w2 16.9→4.4us(1/4), w4 32.4→14.2us(1/2). 걸어둔 소켓이 모자라 백로그에서 꺼내 붙이는 경로를 탈 때 등록 비용이 커진다는 부분은 맞다.
- **그러나 Complete 전체는 오히려 늘었다.** w2 104→124us, w4 196→236us. socket()이 w2 31→53us, w4 90→145us로 늘어서 Post 감소분보다 크다. 10/20 w4 s8 vs s1000과 같은 모양.
- **워커 수에 따른 Complete 증가는 slotCnt를 늘려도 그대로다.** s500에서도 w2→w4에 Complete 124→236us, socket() 53→145us. → w2→w4의 증가는 백로그 경합이 아니라 socket() 쪽에서 온다.
- 처리량은 s500이 높다(w2 +11%, w4 +7%). w2 s500은 클라 select 대기가 134us로 짧아져 클라가 거의 한계(서버가 클라를 덜 기다리게 함).
- socket()이 비싸진 이유는 미확인. 같은 시간에 처리하는 연결이 많아져 커널 소켓 생성 경로가 바빠진 것인지, 걸어둔 소켓 수 자체가 영향을 주는지 분리 안 됨.
