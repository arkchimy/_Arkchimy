# backlog 큐 동작 확인

## 1. 목적

Windows에서 backlog 큐가 실제로 어떻게 동작하는지 확인한다.

- `listen`에 준 값대로 큐 크기가 정해지는가
- 큐가 가득 찬 뒤 들어오는 연결은 어떻게 처리되는가
- 그때 클라이언트는 어떤 에러를 받는가

## 2. 배경

```cpp
int listen(SOCKET s, int backlog);
```

두 번째 인자 `backlog`가 **backlog 큐의 길이**다.

backlog 큐는 3-way handshake가 끝났지만 아직 `accept()`로 꺼내지 않은 연결이 대기하는 곳이다.
서버가 `accept()`를 호출하면 이 큐에서 하나씩 꺼내 간다.

`backlog`에 넣을 수 있는 값은 세 종류다.

| 값 | 의미 |
|---|---|
| 일반 숫자 (`5`, `1000`) | 이 길이로 요청한다. OS가 줄일 수 있다 |
| `SOMAXCONN` | OS가 적당한 최대값을 정한다 |
| `SOMAXCONN_HINT(N)` | N으로 요청한다. 내부적으로 `-N`(음수)으로 넘어가며, Windows는 이를 힌트로 해석한다 |

## 3. 환경

| 항목 | 값 |
|---|---|
| CPU | Intel Core Ultra 5 125U |
| RAM | 16GB |
| OS | Windows 11 Pro (빌드 26200) |
| 네트워크 | 루프백 (127.0.0.1) |
| 빌드 | Release x64 |

## 4. 방법

**서버** (`networkLibProject`)
- 리슨 소켓을 만들고 `listen`까지만 한다. **`accept()`는 하지 않는다.**
- 따라서 연결은 큐에 쌓이기만 하고 빠지지 않는다.
- `server.cfg`로 `backlog` 값과 `SOMAXCONN_HINT` 사용 여부를 바꾼다.

**클라이언트** (`DummyClient`)
- `client.cfg`에 적힌 횟수만큼 **블로킹 `connect()`를 순서대로** 시도한다.
- 성공한 소켓은 닫지 않고 들고 있는다. 서버 큐에 계속 남겨 두기 위해서다.
- 집계 항목: 성공 수, 실패 수, 첫 실패 번호, 첫 실패 이후 성공 횟수, 에러 코드별 횟수

서버가 accept를 하지 않으므로 **성공 수 = 실제 큐 크기**, **첫 실패 번호 = 큐가 가득 찬 지점**이다.

※ 실패 1건당 걸린 시간은 초기 버전 클라이언트로 측정했다. 현재 클라이언트에는 시간 측정이 없다.

## 5. 결과

| listen의 backlog 값 | 실제 큐 크기 (성공 수) | 큐가 찬 뒤 에러 | 실패 1건당 시간 |
|---|---|---|---|
| `5` | 5 | 10061 | 약 2.0초 |
| `1000` | **200** | 10061 | 약 2.0초 |
| `SOMAXCONN_HINT(5)` | **200** | 10061 | 약 2.0초 |
| `SOMAXCONN_HINT(1000)` | 1000 | 10061 | 약 2.0초 |

`listen(5)`, 20회 시도의 집계 출력:

```
시도 20회
성공 5개
실패 15개
첫 실패: #5
첫 실패 이후 성공: 0회
err=10061 : 15회
```

- 모든 조건에서 큐 크기만큼 성공한 직후부터 실패했고, 실패한 시도는 전부 10061이었다.
- 첫 실패 이후 다시 성공한 경우는 없었다. (예외 1회는 6장 참고)

## 6. 해석

**큐가 가득 차면 연결을 거절한다 (10061)**
- 10061(`WSAECONNREFUSED`)은 `connect()` 단계에서 받는 에러다. 클라이언트가 보낸 SYN에 서버가 RST로 응답했다는 뜻이다.
- SYN을 응답 없이 버리는 방식이었다면 클라이언트는 재전송을 반복하다가 약 21초 뒤 10060(`WSAETIMEDOUT`)을 받았을 것이다. 결과는 10061이므로, Windows는 큐가 찼을 때 버리지 않고 거절한다.

**거절은 즉시 오지 않는다 (약 2초)**
- RST로 거절당했는데도 `connect()`가 실패를 돌려주기까지 약 2초가 걸렸다.
- 클라이언트 TCP 스택이 RST를 받은 뒤에도 몇 차례 재시도하고 포기하는 것으로 추정한다. (패킷 캡처로 확인하지는 않았다)

**일반 숫자는 200에서 잘린다**
- `listen(s, 1000)`을 해도 실제 큐는 200이었다.
- 200보다 큰 큐가 필요하면 `SOMAXCONN_HINT`를 써야 한다.

**`SOMAXCONN_HINT`에는 하한이 있다**
- `SOMAXCONN_HINT(5)`는 5가 아니라 200이 되었다.
- 200보다 작은 큐가 필요하면 `SOMAXCONN_HINT`가 아니라 일반 숫자를 써야 한다.

**비슷한 에러 코드와의 구별**

| 코드 | 이름 | 언제 | 어디서 받나 |
|---|---|---|---|
| 10061 | `WSAECONNREFUSED` | 연결 수립 **전**. SYN에 RST가 돌아옴 | `connect()` |
| 10054 | `WSAECONNRESET` | 연결 수립 **후**. 상대가 RST를 보냄 | `recv` / `send` |
| 10053 | `WSAECONNABORTED` | 연결 수립 **후**. 내 쪽 TCP 스택이 연결을 포기함 | `recv` / `send` |

어느 함수에서 에러를 받았는지(연결 전인지 후인지)가 첫 번째 구별 기준이다.

## 7. 한계

- **조건별 1회 측정이다.** 반복 측정과 중앙값은 내지 않았다.
- **재현되지 않은 결과가 1회 있다.** `listen(5)`에서 성공이 6개 나온 적이 있다. 그때는 출력 일부만 보아서 6번째 성공이 몇 번째 시도였는지 확인하지 못했고, 이후 재실행에서는 5개였다.
- **순차 connect다.** 한 번에 하나씩 연결하므로, 연결이 동시에 몰리는 상황은 확인하지 않았다.
- **2초 지연의 원인은 추정이다.** 패킷 캡처로 확인하지 않았다.
- **10054는 확인하지 않았다.** 큐에 있던 연결(클라이언트 입장에서는 연결 완료 상태)이 서버의 리슨 소켓 종료 후 `recv`에서 10054를 받을 것으로 예상하지만, 실험하지 않았다.
