# IOCP 서버 송신 경로 분석: 최적화가 역효과를 낸 원인에서 찾은 "우연한 모아 보내기"

> 서버 처리량은 **송신 완료를 처리하기 전까지 메시지가 쌓여 우연히 생긴 모아 보내기**에 기대고 있었다. 완료 통지를 줄이는 최적화가 처리량을 61% 떨어뜨린 원인을 추적해 이를 찾았고, 같은 원인으로 부하 중 정상 클라이언트가 끊기는 버그도 있었다. 송신 경로 설계로 둘 다 고쳐 정상 클라이언트 끊김을 없애고, 요청-응답(에코) 트래픽에서 작은 메시지 처리량을 57–58% 올렸다.

> **수치 기준:** 처리량·CPU·지연은 2026-11-05 PC B `/O2` 재측정 값이다(서버·클라이언트를 그 커밋에서 다시 빌드, 원본과 표는 [결과](../../실험폴더/portfolio_o2_2026_11_05/결과.md)). 이전 서버 숫자는 `/Od` 빌드였다. 다시 재지 않은 값은 그 자리에 "재측정 안 함"으로 밝혔다.

**모아 보내기**(send batching): 여러 메시지를 `WSASend` 한 번에 실어 보내는 것. 이 문서에서 가장 중요한 개념이다.

## 1. 측정 환경과 방법

| 항목   | 값                                |
| ------ | --------------------------------- |
| PC     | PC B: Core i5-8600, 6코어 6스레드 |
| 측정일 | 2026-11-05                        |
| 빌드   | 서버·클라이언트 모두 `/O2`        |
| 전원   | 균형 조정(변경하지 않음)          |

- PC A(Core Ultra 5 125U, 노트북)는 문제를 처음 본 곳이다. 5장의 증상과 8-1의 이력에만 나오고, 숫자는 섞지 않는다.
- **절대값보다 같은 조건끼리의 비교**에 의미가 있다. 서버와 클라이언트를 같은 PC에서 돌린 루프백이라 CPU와 커널 TCP 스택을 나눠 쓰기 때문이다.
- 처리량은 부하 클라이언트(LoadClient)로 **세션마다 오가는 양을 고정**해 쟀다. 메시지 N개를 묶어 보내고 전부 에코되면 다음 묶음을 보낸다. 검증은 페이로드 앞 8바이트 순번 비교만 해서 클라이언트 비용을 줄였다(바이트 단위 검증은 정확성 클라이언트가 따로 맡는다).
- **클라이언트가 먼저 포화된 숫자는 쓰지 않았다.** CPU는 `사용 코어 / 스레드 수`로 서버와 클라이언트를 항상 같이 본다.
- **옛 구조는 그 커밋을 그대로 `/O2`로 다시 빌드해 쟀다**(서버 핑도 그 커밋 기본값). 조건마다 15초 3회, 같은 실행 안에서 번갈아 돌리고 회차마다 순서를 바꿔 중앙값을 냈다. 실행 전·중 CPU 상위 프로세스를 기록해, 다른 프로세스가 코어 절반 이상을 쓴 회차는 다시 쟀다.
- **표의 GQCS / GQCSEx는 워커가 완료 통지를 꺼내는 방식이다.** GQCS(`GetQueuedCompletionStatus`)는 1개씩, GQCSEx(`GetQueuedCompletionStatusEx`)는 여러 개씩 꺼낸다. 8장 전까지의 표는 GQCS로 쟀고, 둘의 비교는 8장에서 한다.
- **`WSASend` 1번 시간과 꺼낸 완료 수는 서버 통계로 읽는다.** 프로파일러 기록 비용이 비교를 흐리지 않도록, 재측정은 프로파일러를 끄고 했다(8-1).

| ---- | ------ | -------- | -------------- |
| 2    | 77.9만 | 1.28/2   | 2.42/4         |
| 4    | 80.2만 | 1.63/4   | 2.31/4         |

## 2. 송신 경로 구조
이후의 모든 장은 이 경로 이야기다. 세션마다 송신 링 1개가 있고, 걸려 있는 `WSASend`를 세션당 1건으로 제한하는 **송신 중 표시**(`mSendFlag`)가 있다.

```cpp
struct Session
{
	std::mutex mSendLock;	// 아래 셋을 보호한다
	RingBuffer mSendBuf;	// 보낼 데이터. WSASend에는 이 링의 메모리를 복사 없이 그대로 넘긴다
	bool mSendFlag;	// 송신 중 표시 - WSASend가 걸려 있으면 true (세션당 1건)
	int32_t mSendPosted;	// 지금 걸린 WSASend에 넘긴 바이트 (5장에서 추가)
	// ...
};
```

```
[IOCP 워커 스레드]
수신 완료 → processRecv → OnRecv(컨텐츠) → SendPacket → 송신 링에 push ─┐
                                                                         ↓
송신 완료 → finishSend: 링에서 pop, 송신 중 표시 끔 ──────────────→ postSend
                                                                         ↓
                                        송신 중이 아니면: 표시 켬 → WSASend(링에 쌓인 전부)
```
- 위 그림은 수정 전 경로다. `SendPacket`이 push 직후 바로 `postSend`를 부르는 부분은 6장에서 바뀐다.
- **데이터는 송신 완료를 처리할 때(`finishSend`) 링에서 빠진다.** 4장과 5장의 이야기는 모두 이 점에서 나온다. `WSASend`가 즉시 성공해 데이터가 이미 상대에게 갔더라도, 완료 통지가 처리되기 전까지는 링 자리를 차지하고 송신 중 표시도 켜져 있다.
- 코드: `networkLibProject/NetworkLib.h`(`Session`), `networkLibProject/NetworkLib.cpp`(`processRecv`, `sendRaw`, `postSend`, `finishSend`)

## 3. WSASend 비용은 호출 횟수가 정한다
**같은 데이터를 적은 호출로 보내는 것이 처리량을 정한다.** 송신 한 번의 비용은 메시지 크기와 거의 무관했다.
- `WSASend`는 **100% 즉시 성공**(커널 송신 버퍼로 복사)했지만, 그래도 IOCP 완료 통지는 따로 온다.
- **송신 한 번의 비용은 메시지 크기와 거의 무관했다.** 실린 바이트가 16배 늘어도 `WSASend` 1번은 9.6 → 13.5µs였다.

`09a49f6`, 워커 4, GQCS, skip 끔, 3회 중앙값
| 메시지 × 묶음 | 송신 1번에 실린 바이트 | WSASend 1번 | 처리량  |
| ------------- | ---------------------- | ----------- | ------- |
| 32B × 16      | 242B                   | 9.6µs       | 26MB/s  |
| 4KB × 1       | 3,932B                 | 13.5µs      | 246MB/s |

- 256B × 16과 송신 버퍼 0(`SO_SNDBUF = 0`)의 비교는 PC A `/Od` 값뿐이라 재측정 안 함. 근거로 쓰지 않는다.

즉시 성공한 송신에도 완료 통지가 따로 오므로, 이 통지를 없애면 일이 줄 것처럼 보인다. 다음 장이 그 시도다.

## 4. 완료 통지 skip 방식을 켰더니 처리량이 61% 떨어졌다
**−61%(워커 2), −51%(워커 4)는 완료 통지를 줄인 효과가 아니라, 우연히 생기던 모아 보내기가 사라진 결과였다.**

**완료 통지 skip 방식**(`FILE_SKIP_COMPLETION_PORT_ON_SUCCESS`, 이하 skip): I/O가 즉시 성공하면 완료 통지를 IOCP 큐에 넣지 않고, I/O를 건 스레드가 그 자리에서 완료를 처리하는 방식이다. 대기(`WSA_IO_PENDING`)로 넘어간 I/O는 기존처럼 큐로 통지된다. 이 서버는 송신이 100% 즉시 성공하므로(3장), skip을 켜면 송신 완료 통지가 전부 사라진다.

`09a49f6`, GQCS, 3회 중앙값
| 워커 | 조건     | 처리량              | `WSASend`당 | CPU / 패킷 | 송신 완료까지 |
| ---- | -------- | ------------------- | ----------- | ---------- | ------------- |
| 2    | 32B × 16 | 77.9만/s            | 7.8         | 1.67µs     | 24µs          |
| 2    | + skip   | **30.2만/s (−61%)** | **1**       | **6.72µs** | 6µs           |
| 4    | 32B × 16 | 80.2만/s            | 7.6         | 2.03µs     | 16µs          |
| 4    | + skip   | **39.2만/s (−51%)** | **1**       | **7.70µs** | 10µs          |
| 2    | 4KB × 1  | 6.09만/s            | 1           | 20.84µs    | 18µs          |
| 2    | + skip   | 6.13만/s (+0.6%)    | 1           | 19.90µs    | 12µs          |
| 4    | 4KB × 1  | 5.99만/s            | 1           | 22.73µs    | 19µs          |
| 4    | + skip   | 6.06만/s (+1.2%)    | 1           | 20.99µs    | 13µs          |

- 32B × 16에서 skip을 켜면 서버가 2.03/2, 2.99/4코어까지 올라간다(끄면 1.28/2, 1.63/4). 클라이언트는 포화가 아니다(1.69/4, 1.77/4).

**① 기존 구조에서 우연히 모아 보내지는 이유**

**송신 중인 동안 같은 세션에 보낼 메시지가 더 생기면 모아서 보내진다.** 모이는 창은 "`WSASend`를 건 순간부터 그 완료를 처리할 때까지"다.

라이브러리는 세션마다 `WSASend`를 한 번에 1건만 건다. 걸 때 "송신 중" 표시를 켜고, **그 송신의 완료 통지를 처리할 때** 끈다. 송신 중에 `SendPacket`이 불리면 송신 링에 쌓기만 하고, 완료를 처리할 때 쌓인 것을 전부 `WSASend` 1번으로 보낸다.

```cpp
// SendPacket이 링에 push한 뒤 부른다. 이미 송신 중이면 아무것도 하지 않는다
void NetworkLib::postSend(Session* session)
{
	WSABUF bufs[2];
	int32_t bufCnt = 0;
	{
		std::lock_guard<std::mutex> lock(session->mSendLock);
		if (session->mSendFlag)
		{
			return;	// 송신 중 - 완료 쪽이 이어서 보낸다
		}
		bufCnt = session->mSendBuf.getReadBufs(bufs);	// 링에 쌓인 전부
		if (bufCnt == 0)
		{
			return;
		}
		session->mSendFlag = true;
	}
	WSASend(session->mSock, bufs, bufCnt, nullptr, 0, &session->mSendOv, nullptr);
}

// 송신 완료 통지를 처리할 때 (onSendComplete → finishSend)
{
	std::lock_guard<std::mutex> lock(session->mSendLock);
	session->mSendBuf.pop(transferred);	// 이제야 링에서 빠지고
	session->mSendFlag = false;	// 이제야 송신 중 표시가 꺼진다
}
postSend(session);	// 송신 중에 쌓인 것을 한 번에
```

32B × 16에서는 클라이언트가 메시지 16개를 `send` 한 번에 보내므로, 서버의 수신 완료 1건에 메시지가 약 15개 함께 온다. 워커는 그 자리에서 `OnRecv` → `SendPacket`을 연달아 부른다.
```
OnRecv(메시지 1)    → WSASend(32B) 즉시 성공
                      하지만 완료 통지는 IOCP 큐를 거친다(16–24µs) → 송신 중 표시 유지
OnRecv(메시지 2-15) → 송신 중이라 송신 링에 쌓기만 함
(완료 처리 때)       메시지 1의 송신 완료 처리 → 쌓인 14개를 WSASend 1번으로
→ 메시지 약 15개 = WSASend 2번 (송신 1번에 평균 7.8개, 249B)
```

- 처음에는 PC A `/Od`에서 본 "완료가 큐에서 약 2.5ms 기다리는 동안 쌓인다"로 설명했다. PC B `/O2`에서는 대기가 16–24µs인데도 7–8개가 모인다. 대기의 길이가 아니라 **완료를 처리하기 전이라는 것**이 창을 만든다.

**② 4KB × 1에서는 모아 보낼 메시지가 없는 이유**

서버에서 한 세션에 처리할 메시지가 **항상 1개뿐**이다. 클라이언트는 메시지 1개를 보내고 그 에코를 받아야 다음 메시지를 보내기 때문이다. 송신 중 표시가 켜져 있는 동안 같은 세션에 쌓일 다음 메시지가 없으니, 완료 통지를 늦게 처리하든 바로 처리하든 `WSASend` 1번에는 메시지 1개가 실린다. 실제로 skip 유무와 상관없이 `WSASend`당 메시지가 1개로 같았다.

**③ 그래서 4KB × 1을 대조 조건으로 썼다**

**4KB × 1에서는 skip의 두 효과 중 완료 통지 절감만 따로 보인다.** skip을 켜면 두 가지가 동시에 바뀐다. (a) 큐에 들어가는 완료 통지가 줄고, (b) 송신 완료가 즉시 처리돼 송신 중 표시가 바로 꺼진다(= ①의 모아 보내기가 사라진다).
- 32B × 16: (a)와 (b)가 섞여 −61% / −51% 하나로 나온다.
- 4KB × 1: 원래 모아 보낼 것이 없으니 (b)의 영향이 없고 **(a)만 보인다.** 큐에서 꺼내는 완료가 패킷당 2.05 → 1.00개로 절반이 됐는데 처리량은 +0.6–1.2%, 서버 CPU / 패킷은 −4.5–7.7%였다. 완료 통지를 줄인 이득은 있지만 32B × 16의 CPU / 패킷 약 4배를 설명할 수 없다.
- 따라서 32B × 16의 하락은 (b), 모아 보내기가 사라진 결과다.
```
skip 켬 (32B × 16): 메시지마다 WSASend → 그 자리에서 완료
→ 송신 중 표시가 바로 꺼짐 → 다음 메시지도 바로 WSASend
→ 메시지 약 15개 = WSASend 15번 (송신 1번 32B, 호출 7.8배 → CPU / 패킷 약 4배)
```

**결론**: 처리량은 **송신 완료를 처리하기 전까지 쌓이는 우연한 모아 보내기**에 기대고 있었다. 코드 어디에도 "모아서 보내자"는 의도는 없었다. 그래서 모아 보내기를 **설계로 보장**하기로 했다(6장). skip은 실험 후 코드에서 제거했다(7장에서 다시 켠다).

## 5. 같은 원인의 버그: 부하 중 정상 클라이언트가 끊긴다
**넘침 판정이 이미 상대에게 보낸 데이터까지 세서 정상 클라이언트를 끊었다. 판정 기준을 아직 보내지 않은 데이터로 바꿔 구조상 끊기지 않게 했다.**

**증상**: 정상 클라이언트가 15초 테스트 6–7회 중 1–2회 "송신 링 넘침"으로 끊겼다(PC A, 당시 `/Od`). 정상 클라이언트는 에코가 돌아오지 않은 바이트를 서버 송신 링(16KB)보다 작은 15,360B 이하로 지키는데도 끊겼다.

**가설**: 이미 클라이언트에 도착한 데이터가 링 자리를 차지해서, 클라이언트 기준으로는 한도 안인데 서버 링이 넘친 것이다. 송신 링은 **송신 완료를 처리해야** 비워지므로, 완료 통지가 큐에서 기다리는 동안에는 도착한 데이터도 링에 남는다.

**원인 확인**: **정상 클라이언트를 끊은 링은 전부 이미 상대에게 보낸 데이터였다.** 넘침으로 끊는 순간의 송신 링을 두 몫으로 나눠 기록해 확인했다(PC B, 당시 `/Od`, 이 장의 시험은 재측정 안 함).
- (가) 이미 `WSASend`에 넘긴 바이트: 대부분 상대에게 도착했고 완료 통지만 기다린다.
- (나) 아직 `WSASend`에 넘기지 않은 바이트: 상대에게 절대 도착하지 않았다.

| 끊긴 연결                                    | 링 사용 | (가) 넘긴 몫 | (나) 안 넘긴 몫  | 걸어 둔 송신의 경과 |
| -------------------------------------------- | ------- | ------------ | ---------------- | ------------------- |
| 정상 클라이언트                              | 14,517B | **14,517B**  | **0B**           | 8.5ms               |
| 받지 않는 클라이언트 (대조, 109건 중 앞 5건) | 13–16KB | 15B–3.9KB    | **1.2만–1.5만B** | 77–166ms            |

서버의 넘침 정책이 **"받지 않는 느린 클라이언트"와 "서버 자신의 완료 처리 지연"을 구분하지 못한** 것이다. 그래서 서버가 바쁠수록 정상 클라이언트를 더 끊었다. 진짜 느린 클라이언트는 (나)가 쌓이고 송신이 수십 ms씩 끝나지 않는다.

**재현 조건 찾기**: **가설의 예측(완료 처리가 늦을수록 더 끊긴다)으로 재현 조건을 만들었지만, 버그는 여전히 드물었다.** PC B에서는 기본 설정의 송신 완료까지가 17µs(PC A는 2.2–2.6ms)라 정상 에코 21회 중 1회만 끊겼고, 이를 "고쳐졌다"로 넘기지 않았다. 워커를 1개로 줄이고 부하 클라이언트를 함께 띄워 송신 완료까지를 10–11ms로 늘린 조건에서 끊김을 잡았고, 위 표의 정상 클라이언트 기록은 이때 얻었다(받지 않는 클라이언트 기록은 기본 설정). 다만 나중에 같은 조건에서 수정 전 빌드를 반복해 보니 **16회 중 1회**로 여전히 드물었다. 지연이 길다는 것만으로는 부족하고, 큰 송신이 완료를 기다리는 사이에 클라이언트가 다음 데이터를 보내는 타이밍까지 맞아야 하기 때문으로 보인다.

**수정**: 클라이언트 쪽 한도를 줄이는 임시 조치는 하지 않고 서버를 고쳤다.
- 넘침 기준을 **(나) 안 넘긴 몫**으로 바꿨다. 정상 클라이언트라면 (나)는 클라이언트의 한도를 넘을 수 없고, 받지 않는 클라이언트는 (나)가 계속 쌓이므로 그대로 잡힌다.
- 송신 링을 한도의 2배(32KB)로 늘려, 링에는 (가)+(나)가 항상 들어간다. (가)는 넘길 때의 (나)였으므로 한도를 넘지 않는다.

```cpp
// sendRaw: 송신 링에 넣기 전 넘침 판정 (mSendLock 안)

// 수정 전 - 링 전체가 기준이라 이미 보낸 몫(가)까지 센다
if (session->mSendBuf.getFreeSize() >= packetSize) { /* push */ }
else { /* 넘침 → 끊기 */ }

// 수정 후 - 아직 WSASend에 넘기지 않은 몫(나)만 센다
int32_t pending = session->mSendBuf.getUseSize() - session->mSendPosted;
if (pending + packetSize <= SEND_PENDING_LIMIT) { /* push */ }
else { /* 넘침 → 끊기 */ }
```
수정의 핵심은 판정식 한 줄이다. `mSendPosted`는 `postSend`가 `WSASend`에 넘긴 길이를 적고, `finishSend`가 0으로 돌린다.

**검증** (PC B)
- **판정식: 한도를 지키는 클라이언트는 바뀐 판정식에서 넘침에 걸릴 수 없다.** 횟수가 아니라 구조로 보장된다. 정상 클라이언트는 에코가 안 돌아온 바이트를 15,360B 이하로 지키고, (나)는 클라이언트에 도착하지 않은 바이트이므로 데이터 몫은 항상 15,360B 이하다. 나머지 1KB는 서버가 보내는 핑 몫으로 남겨 두었으므로 (나)는 한도(16KB)를 넘지 않는다.
- **회귀**: 받지 않는 클라이언트는 계속 잡힌다(15초 테스트에서 수정 전 163건, 수정 후 192건).
- **반복 횟수 비교는 근거가 되지 못했다.** 재현 조건에서 수정 전 16회 중 1회, 수정 후 18회 중 0회. 버그가 이만큼 드물면 수정하지 않았더라도 18회 연속 0이 나올 확률이 약 30%라, 횟수로는 수정 효과를 말할 수 없다.
- **결정적 재현 시험: 버그의 조건을 일부러 만들어, 수정 전에는 15초마다 수백 번, 수정 후에는 0번 끊기는 것을 확인했다.** 송신 완료를 처리하기 전에 워커를 일부러 잠재우는 테스트 전용 설정(`testSendCompleteDelayMs`)을 넣었다. 잠든 동안 다른 워커가 같은 세션의 수신을 처리하며 링에 응답을 쌓으므로, 버그의 조건(완료 처리 지연 + 다음 데이터 도착)을 매번 만든다. 수정 전 빌드에도 같은 설정만 덧대 같은 실행 안에서 번갈아 돌렸다(워커 2, 정상 EchoClient만, 15초, 지연별 3회).

| 주입한 지연 | 수정 전: 정상 클라이언트 끊김 | 수정 후            | 처리량 (전 / 후)  |
| ----------- | ----------------------------- | ------------------ | ----------------- |
| 1ms         | 244–382회                     | **0회** (3회 모두) | 94–96 / 96–98MB/s |
| 2ms         | 329–386회                     | **0회** (3회 모두) | 53–67 / 67MB/s    |
| 5ms         | 302–328회                     | **0회** (3회 모두) | 34 / 33–34MB/s    |

받지 않는 클라이언트는 수정 후에도 계속 끊겼다(같은 지연 2ms에서 30건). 지연을 끈 기본 설정에서는 처리량과 끊김이 설정을 넣기 전과 같았다.

**뒤의 변경 (2026-11-02): 판정을 다시 "송신 링이 가득 차면 끊기"로 단순화했다. 기본값이 skip이 되고(7장) 느린 클라이언트를 시간으로 판정하기로 하면서, 바이트 한도는 메모리 보호만 맡으면 되기 때문이다.**
- 송신 링을 32KB 고정 배열로 두고, 링 전체를 기준으로 판정한다. `mSendPosted`(지금 이름 `mSendingBytes`)와 한도 설정은 지웠다.
- 판정식은 수정 전으로 돌아갔지만 링이 16KB에서 32KB가 되어, 한도를 지키는 클라이언트는 여전히 **구조로** 끊기지 않는다. (가)는 넘길 때의 (나)였고 (나)는 클라이언트에 도착하지 않은 바이트라 둘 다 15,360B 이하이므로, 합이 30,720B로 링(32,768B)보다 작다.
- 같은 지연 주입 시험(PC B, 워커 2, GQCS, skip 끔, 지연 1/2/5ms × 3회)에서 정상 클라이언트 끊김은 9회 모두 0이었다.
- 방송처럼 받는 쪽이 받는 양을 정하지 못하는 경우에는 이 보장이 없다. 이전 판정식도 마찬가지였다(정상 클라이언트가 가끔 끊김, README_ERRORS 2-7). 채팅 방 16(워커 2·4, 수신 단위·묶음 단위, skip, 3회씩) 12회에서는 끊김이 없었다.
- 받는 속도가 느린 클라이언트는 시간 기준(걸어 둔 `WSASend`가 오래 끝나지 않음)으로 따로 판정할 예정이다. TCP는 상대가 ACK를 보내며 수신 창을 0으로 알리는 동안에는 연결을 끊지 않기 때문이다.

## 6. 모아 보내기를 설계로 보장하다
**수신 1건으로 생긴 응답을 `WSASend` 1번에 모아 보내도록 바꾸자, 작은 메시지 처리량이 57–58% 오르고 서버 CPU / 패킷이 29–37% 줄었다.** 4장에서 본 우연을 설계로 대신한 것이다. 5장의 수정과 같은 송신 경로라 함께 바꿨다.

다만 **수신한 세션에게 돌려보내는 응답만** 모은다. 에코처럼 요청을 보낸 세션에게 답하는 트래픽에는 맞지만, 채팅처럼 한 세션의 메시지가 다른 세션들에게 가는 트래픽은 아직 모으지 않는다(아래 "적용 범위").

세션당 `WSASend`를 1건만 거는 규칙(송신 중 표시)은 그대로 두고, **첫 송신을 거는 시점**만 바꿨다.
- 수정 전: 송신 중이 아니면 첫 번째 `SendPacket`이 불린 순간 건다. 첫 메시지 하나가 혼자 먼저 나가고, 나머지는 그 송신의 완료가 처리될 때 모여서 나간다.
- 수정 후: 수신 처리 중에 같은 세션으로 보내는 응답은 송신 링에 쌓기만 하고, **수신 처리가 끝날 때 `WSASend`를 한 번** 건다. 수신 처리 밖(컨텐츠 스레드, 핑 스레드)에서 보내는 것은 전처럼 바로 건다.

수신 1건에 메시지 14개가 들어온 경우:
```
수정 전
OnRecv(1)    → SendPacket → 송신 중 아님 → WSASend(1개)   ← 혼자 먼저 나감
OnRecv(2-14) → SendPacket → 송신 중 → 링에 쌓기만
(완료 통지 처리 뒤) 쌓인 13개를 WSASend 1번                → WSASend 2번

수정 후
OnRecv(1-14) → SendPacket → 링에 쌓기만
수신 처리 끝 → WSASend(14개)                                → WSASend 1번
```

```cpp
thread_local Session* tRecvSession = nullptr;	// 이 스레드가 지금 수신 처리 중인 세션

bool NetworkLib::processRecv(Session* session, DWORD transferred)
{
	tRecvSession = session;
	while (완성된 패킷이 있으면)
	{
		OnRecv(session->mId, payload, len);	// 컨텐츠가 안에서 SendPacket → 링에 쌓기만 한다
	}
	tRecvSession = nullptr;
	postSend(session);	// 이번 수신으로 생긴 응답 전부를 WSASend 1번으로
}

bool NetworkLib::sendRaw(Session* session, ...)
{
	// (mSendLock 안에서 송신 링에 push)
	if (session != tRecvSession)
	{
		postSend(session);	// 수신 처리 밖에서 보낸 것은 바로 건다
	}
}
```
- **모이는 양은 트래픽 모양(수신 1건에 메시지가 몇 개 오느냐)이 정한다.** 그래서 아래 +57–58%는 "수신 1건에 메시지 약 15개" 조건의 숫자다. 서버는 메시지가 몇 개 올지 모르고, 이번 수신에 완성된 패킷이 1개면 1개, 15개면 15개를 보낸다.
- **타이머로 기다리지 않는다.** 첫 응답이 기다리는 시간은 같은 수신에 들어온 나머지 패킷을 처리하는 시간뿐이고, 수신 처리가 끝나는 즉시 보낸다. Nagle 알고리즘처럼 "조금 더 모이면 보내자"는 방식이 아니다.

수정 전(`2a91e23`)과 수정 후(`3a2ef87`) 빌드를 **같은 실행 안에서 번갈아** 돌렸다(GQCS, 3회 중앙값).
| 워커 | 메시지 × 묶음 | 처리량 수정 전 → 후           | `WSASend`당 | 서버 CPU / 패킷 |
| ---- | ------------- | ----------------------------- | ----------- | --------------- |
| 2    | 32B × 16      | 81.1만 → **127.6만/s (+57%)** | 7.8 → 15.5  | 1.63 → 1.16µs   |
| 4    | 32B × 16      | 78.9만 → **124.3만/s (+58%)** | 7.6 → 15.5  | 2.04 → 1.28µs   |
| 2    | 4KB × 1       | 6.12만 → 6.10만/s             | 1 → 1       | 21.11 → 20.93µs |
| 4    | 4KB × 1       | 6.04만 → 6.02만/s             | 1 → 1       | 22.20 → 23.59µs |

- 32B × 16: 수신 1건에 메시지 약 15개가 오고, 이제 그것이 `WSASend` 1번으로 나간다. `WSASend`당 메시지가 2배가 됐다.
- 4KB × 1: **이득이 모아 보내기에서 왔음을 보여 주는 대조 조건**이다(4장과 같다). 모아 보낼 메시지가 없어 `WSASend`당 메시지가 그대로이고 처리량 차이도 −0.3%다.
- 서버(1.48/2, 1.59/4)도 클라이언트(2.81/4, 2.72/4)도 포화가 아니므로 **서버 CPU / 패킷(−29%, −37%)**을 함께 본다.

**적용 범위: 수신한 세션에게 가는 응답만 모은다**

`SendPacket`은 송신 링에 넣는 요청일 뿐이고, 실제로 `WSASend`를 거는 곳은 `postSend` 하나다. 몇 번에 나눠 나가는지는 `postSend`를 언제 부르느냐가 정하고, 부르는 곳은 세 군데다.

| `postSend`를 부르는 곳                                | 대상                                             | 모아 보내기                                      |
| ----------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| `processRecv` 끝                                      | 방금 수신을 처리한 세션                          | **설계로 보장** (이 장)                          |
| `sendRaw` - 받는 사람이 수신 처리 중인 세션이 아닐 때 | 다른 세션(브로드캐스트), 컨텐츠·핑 스레드의 송신 | **없음** - 메시지마다 바로 건다                  |
| `onSendComplete`                                      | 송신이 끝난 세션                                 | **우연** - 송신 중 표시가 켜진 동안 쌓인 것(4장) |

- 수신 처리 중인지는 `thread_local` 변수 `tRecvSession`으로 판단한다. `SendPacket(id, ...)`에는 누가 불렀는지가 없고 중간에 컨텐츠 코드(`OnRecv`)가 끼어 있어 인자로 넘길 수도 없으므로, `processRecv`가 자기 스레드에 "지금 이 세션 처리 중"이라고 적어 두고 `sendRaw`가 읽는다.
- 그래서 채팅처럼 `OnRecv(A)` 안에서 B에게 보내면 두 번째 줄로 간다. skip이 켜져 있으면(이 서버의 기본값, 8-3) 송신이 그 자리에서 끝나 송신 중 표시가 바로 꺼지므로, B에게는 **메시지마다 `WSASend` 1번**이 된다. 4장의 하락과 같은 상황이 다른 세션 쪽에서 생긴다(후속 문서 2장에서 측정).
- 일반화하는 방법은 10장 다음 단계에 적었다.

## 7. 완료 통지 skip 방식 다시 켜기
**모아 보내기를 보장한 뒤에는 skip이 손해 없이 서버 일을 줄였고, 서버가 포화될 때 지연을 3분의 1로 줄였다.** GQCSEx와 함께 쓴 결과는 8장에서 다룬다.

4장의 하락은 skip 자체가 아니라 우연한 모아 보내기가 사라진 탓이었으므로, 6장에서 모아 보내기를 설계로 보장한 뒤 skip을 다시 켰다. `WSASend`당 메시지는 16개로 유지됐다(예전 skip은 1개). 이 장의 측정은 모두 에코라서 6장 적용 범위 안이다.

### 7-1. 손해 없이 서버 일이 줄었다

**서버 CPU / 패킷이 모든 조건에서 4.7–12.1% 줄었고, 서버가 포화된 워커 1에서는 32B 처리량이 13.7% 올랐다.**

**측정 전 예상** (2026-10-29, 본 측정 전에 기록)
- skip을 끄면 송신 완료가 IOCP 큐를 거쳐 다른 워커가 처리할 수 있다. 그 워커는 깨어나야 하고(문맥 전환), 다른 코어라면 세션 데이터를 캐시에 다시 불러와야 한다. skip을 켜면 I/O를 건 스레드가 캐시가 따뜻한 상태로 바로 처리하므로 이 비용이 사라진다.
- 그래서 시스템 콜 절감(패킷당 GQCS 0.068번 × 1번 약 0.77µs로 어림하면 3–6%)보다 큰, **10% 이상**의 개선을 예상한다.
- 이 효과는 다른 스레드가 완료를 처리할 일이 많은 **워커 2·4에서 워커 1보다 클 것**이다.
- 완료 통지가 큐에 쌓이면 그만큼 커널 자원(논페이지드 풀)을 오래 쥐고 있게 된다. skip으로 큐 적체를 줄이면 논페이지드 풀 사용량도 줄 것이다.

**측정 방법**: 워커 1·2·4 × skip 유무 × 32B×16·4KB×1을 같은 실행 안에서 번갈아 3회씩 돌린다(`7de336d`). 워커 1은 서버가 포화(약 1.03/1코어)되고 다른 스레드가 깨어날 일이 없는 조건이다.

- **처리량보다 큰 변화는 포화 시 송신 완료 대기가 3.8ms → 9µs로 사라진 것이다.** 서버가 포화되면 송신 완료가 수신 완료 뒤에서 기다렸는데, skip은 이 대기 자체를 없앴다.
- 확인하지 못한 것: 줄어든 일이 어느 함수에서 왔는지, 문맥 전환과 캐시 효과. 이번 재측정에는 프로파일러를 넣지 않았다.

### 7-2. 지연은 CPU 절감보다 훨씬 크게 줄었다

**서버가 포화되면 skip이 왕복 시간을 3분의 1로 줄였다(5.8 → 2.0ms).** CPU 절감(12%)으로는 설명되지 않는 크기다. 그중 약 절반은 송신 중 표시에 걸려 기다리던 핑의 대기였다.

같은 측정에서 서버가 핑으로 잰 부하 세션의 왕복 시간도 함께 봤다(32B × 16, 5회 중앙값).
| 워커          | 왕복 시간 p50 (끔 → 켬) | 송신 완료까지 (끔 → 켬) |
| ------------- | ----------------------- | ----------------------- |
| 1 (서버 포화) | 5.8 → **2.0ms**         | 3.8ms → 9µs             |
| 2             | 4.9 → 4.9ms             | 20 → 11µs               |
| 4             | 5.0 → 5.0ms             | 20 → 12µs               |

워커 1에서 줄어든 왕복 시간은 3.7ms, 송신 완료 대기는 3.8ms로 크기가 비슷하다.

**가설**: 핑이 송신 중 표시에 걸려 기다렸다. 왕복 시간을 재는 핑은 핑 전용 스레드가 보내는, 수신 처리 밖의 송신이다. skip을 끄면 응답의 송신 완료가 큐에서 기다리는 동안 송신 중 표시가 켜져 있고, 그사이 들어온 핑은 링에 쌓인 채 표시가 꺼질 때까지 기다린다.

**측정 전 예상**: 핑을 링에 넣을 때 송신 중 표시가 켜져 있었는지와, 그 핑이 `WSASend`에 실리기까지 기다린 시간을 센다.
- skip 끔 + 워커 1: 핑 대부분이 표시에 걸리고, 수 ms를 기다린다(왕복 시간 차이와 비슷한 크기).
- skip 켬: 표시에 거의 걸리지 않는다.
- 워커 2·4: skip과 상관없이 거의 걸리지 않거나, 걸려도 µs 단위로 기다린다.

- 나머지 약 1.8ms는 설명하지 못했다. 퐁이 돌아올 때 수신 완료가 큐에서 기다린 시간이 skip으로 줄어든 몫으로 추정하지만, 재지 않았다.

## 8. GQCS vs GQCSEx: 모아 보내기 전과 후
**서버에 여유가 있으면 GQCSEx의 처리량 이득은 없었고, 서버가 포화될 때만 +17.6%였다. skip과 함께 쓰면 포화 시 +26.1%로 처리량이 가장 높아, 기본값을 GQCSEx + skip으로 유지했다. 단, 포화 시 왕복 시간은 GQCS + skip이 더 짧다.**

GQCS와 GQCSEx(1장)를 비교하려고, 워커 루프만 다른 **별도 라이브러리(`NetworkLibEx`)**를 만들어 같은 에코 컨텐츠를 올렸다(`EchoServerT<Lib>`). 지금은 한 라이브러리의 설정으로 합쳤다.

### 8-1. 모아 보내기 전: 여유가 있으면 차이가 없었다

`09a49f6`, 32B × 16, 3회 중앙값
| 워커 | GQCS     | GQCSEx(64) | 차이  | `WSASend`당 |
| ---- | -------- | ---------- | ----- | ----------- |
| 2    | 77.9만/s | 79.6만/s   | +2.2% | 7.8 / 7.8   |
| 4    | 80.2만/s | 78.4만/s   | −2.2% | 7.6 / 7.6   |

- 두 워커 수 모두 서버가 포화가 아니고, `WSASend`당 메시지도 같다.
- **PC A `/Od`에서 본 결과는 재현되지 않았다.** 그때는 워커 4에서 +15.4%였고, 패킷당 비용을 프로파일러로 나눠 "이득의 76%가 `WSASend` 호출 감소"로 해석했다(`실험폴더/LoadClient_gqcsex_2026_10_25/`). 서버가 포화라 완료가 쌓인 조건의 값이다. 이 해석은 근거로 쓰지 않는다.
- **측정 함정: 처리량 비교는 프로파일러를 끄고 잰다.** 켠 채 비교하면 기록 비용이 호출 횟수가 많은 GQCS 쪽에만 더 붙는다. 이를 위해 프로파일러 켜기/끄기(`Profile::SetEnabled`)를 추가했다.

### 8-2. 모아 보내기 후: 포화 시에만 이득이 남고 skip과 겹쳤다

**서버가 포화되면 GQCSEx와 skip의 효과가 겹쳐 처리량이 가장 높았다(단독 +17.6%, +13.7% → 함께 +26.1%). 여유가 있으면 네 방식이 같았다.**

GQCSEx와 skip은 둘 다 완료 통지 큐를 다루는 비용을 줄인다. GQCSEx는 큐에서 **꺼내는 호출 횟수**를, skip은 큐에 **들어가는 완료 수**를 줄인다.

**측정 전 예상** (2026-10-29, 측정 전에 기록)
- skip을 끈 상태에서도 GQCSEx가 GQCS보다 빠를 것이다. 서버가 포화되면 큐에 완료가 많이 밀려 있고, GQCSEx는 그것을 한 번에 꺼내 시스템 콜 횟수를 줄일 수 있기 때문이다.
- 지연은 GQCS가 더 길 것이다. skip을 켜도 수신 완료는 똑같이 큐에 쌓이므로, 한 번에 꺼내는 GQCSEx가 더 빨리 비울 것이다.
- 가장 좋은 조합은 **GQCSEx + skip**일 것이다.

**측정 방법**: GQCS / GQCSEx(64) × skip 유무 네 가지를 같은 실행 안에서 번갈아 돌린다. 워커 1(서버 포화)·4(여유), 32B × 16, 3회(`7de336d`).

| 지연은 GQCS가 더 길다                         | 워커 1: 5.8 vs 4.9ms(skip 끔), **2.0 vs 4.9ms(skip 켬)**. 워커 4: 차이 없음                                                                                        | **skip 끔일 때만 맞았다.** skip 켬에서는 GQCS가 더 짧다                         |
| 가장 좋은 조합은 GQCSEx + skip                | 워커 1: 처리량 +26.1%, CPU / 패킷 −21%로 가장 좋음. 왕복 p50은 GQCS + skip이 가장 짧음. 워커 4: 처리량은 같고 CPU / 패킷은 GQCS + skip이 가장 낮음(1.19 vs 1.20µs) | **처리량에서만 맞았다**                                                         |

**해석**
- 두 방법은 줄이는 대상이 달라 **효과가 겹친다**. 다만 두 효과를 곱한 값(1.176 × 1.137 = 1.337)보다 함께 쓴 값(+26.1%)이 작다.
- skip을 켠 GQCSEx는 왕복 시간이 GQCS보다 길었다(4.9 vs 2.0ms). 원인은 재지 않았다. 처리량이 더 높아 같은 PC의 부하가 커진 영향도 섞여 있을 수 있다.
- 지연 개선은 skip + GQCS 조합에서 가장 크다. GQCSEx를 skip 끔에 더한 효과는 5.8 → 4.9ms로 작다.

### 8-3. 결정: 기본값은 GQCSEx + skip

**기본값을 GQCSEx(64) + skip으로 유지했다**(`server.cfg` `gqcsEx = 1`, `skipOnSuccess = 1`).
- 서버가 포화될 때 처리량과 CPU / 패킷이 가장 좋다(+26.1%, 0.80µs). 서버가 버거울 때 버티는 것이 더 중요하다고 봤다.
- 대가로 포화 시 왕복 p50은 GQCS + skip보다 길다(4.9 vs 2.0ms). 서버에 여유가 있으면 넷의 차이가 없다.
- 이 결정은 에코(수신한 세션에게 응답) 트래픽으로 쟀다. 브로드캐스트에서의 재검증은 후속 문서에 있다. 후속 문서의 묶음 단위 모아 보내기는 완료를 여러 개 꺼내는 GQCSEx가 있어야 효과가 난다.

## 9. 측정을 믿기 위해 한 일
숫자는 맞았지만 잘못 읽을 뻔한 것들을 따로 기록했다(`README_ERRORS.md` 4장).
- **서버 Release가 디버깅용 `/Od`로 남아 있었다.** 2026-11-05에 발견해 `/O2`로 복원하고, 이 문서의 비교를 옛 커밋까지 `/O2`로 다시 빌드해 전부 다시 쟀다. 그 결과 −82%가 −61%로, "GQCSEx 이득의 76%"가 재현 안 됨으로 바뀌었다.
- 재측정 도중 옛 커밋 클라이언트에 메시지 크기 설정이 없어 4KB 대조 조건이 32B로 돈 것을 로그로 찾아 다시 쟀다(`README_ERRORS.md` 1-29). 이후 실행마다 실제 크기를 대조했다.
- 처음 잰 처리량이 서버가 아니라 측정 클라이언트의 한계였다(바이트 단위 검증 비용으로 클라이언트 CPU 3.95/4). → 처리량 전용 부하 클라이언트를 따로 만들었다.
- 같은 조건이 회차마다 30% 넘게 달랐다. → 전원 모드 고정, 회차마다 순서 바꾸기, 중앙값으로 편차를 ±1–9%까지 줄였다.
- CPU 표에 분모(스레드 수)를 빠뜨려 "4.34"가 "4개 중 4.34"로 읽혔다. → CPU는 항상 `사용 코어 / 스레드 수`로 적는다.
- 크기가 다른 조건이 집계에서 한 줄로 합쳐져 범위가 62만–546만으로 나왔다. → 범위가 몇 배씩 벌어지면 편차보다 집계 키를 먼저 의심한다.
- 프로파일러 비용이 비교 대상마다 다르게 붙는 혼입 변수가 있었다. → 처리량 비교와 비용 분해를 다른 실행으로 나눴다.
- "송신 완료까지 2–4ms"는 ACK 대기가 아니라 IOCP 큐 대기였다. 처음엔 ACK 대기로 해석했다가, 기본 설정과 skip 비교로 정정했다. 다시 `/O2`로 재니 16–24µs였다.
- 드문 버그의 수정 효과를 반복 횟수로 판단할 뻔했다. 수정 전 3회 중 1회만 보고 "수정 후 9회 중 0회"를 근거로 삼았는데, 수정 전 빌드를 같은 실행 안에서 번갈아 더 돌리자 16회 중 1회로 드물어 근거가 되지 못했다. → 버그의 조건(완료 처리 지연)을 주입하는 시험으로 수정 전 15초마다 수백 번, 수정 후 0번임을 결정적으로 보였다. 수정 전후 비교는 같은 실행 안에서 번갈아 하고, 버그 빈도를 먼저 확인하며, 드문 버그는 조건을 주입해 재현한다.

## 10. 한계와 다음 단계
**한계**
- −61%나 +58% 같은 **크기**는 이 환경의 숫자이고, "호출 횟수가 비용을 정한다"는 **방향**만 일반화한다. 루프백 측정이라 `WSASend` 한 번에 받는 쪽 TCP 처리까지 들어갈 수 있어, 호출 비용(8–14µs)이 실제 NIC와 다를 수 있다.
- 조건마다 3회 측정이고, 전원 모드를 고정하지 않았다(균형 조정). 다른 프로세스 확인은 실행 전·중 각 1회 표본이다.
- 서버와 클라이언트를 다른 PC에 둘 수 없어 서버 단독 한계(워커 8 이상)는 측정하지 못했다.
- 5장의 결정적 재현 시험은 실제 부하에서 버그가 얼마나 자주 나는지는 보여 주지 않는다. 지연을 인위적으로 만든 시험이기 때문이다. PC B에서는 버그가 드물어(수정 전 16회 중 1회) 반복 횟수로는 수정 효과를 보일 수 없었다.
- 포화 전 지연과, 메시지가 드문드문 오는 트래픽에서의 skip 효과는 재지 못했다. 처리량 클라이언트는 closed-loop라 항상 포화 상태를 재고, 7장의 skip 효과도 이 부하(수신 1건에 메시지 약 15개)에서 쟀다. 드문드문 오는 트래픽에서는 송신 완료 통지가 패킷당 더 많아 효과가 다를 수 있다. 전송률을 고정한(open-loop) 부하 모드를 만들었지만, 이 PC에서는 클라이언트가 지연 바닥(약 10ms)을 만들고 CPU도 먼저 찼다.
- 재측정하지 않은 것: 5장의 지연 주입 시험, 3장의 송신 버퍼 0, 7장의 문맥 전환·비용 분해, 8-1의 비용 분해. 각 자리에 밝혔다.
- **모아 보내기는 수신한 세션에게 가는 응답에만 적용된다(6장 적용 범위).** 브로드캐스트처럼 다른 세션으로 가는 송신과 컨텐츠 스레드의 송신은 바로 걸리고, skip 기본값에서는 메시지마다 `WSASend`가 될 수 있다. 7–8장의 skip·GQCSEx 결과와 기본값 결정도 에코로만 쟀다.
- 모아 보내기 적용 후 서버 핑 왕복 p50이 3.8 → 4.9ms(워커 2), 3.9 → 5.0ms(워커 4)로 늘었다. 처리량이 늘어 같은 PC의 부하가 커진 영향으로 추정하지만 확인하지 않았다.

**다음 단계**
- **(진행함) 아래 모아 보내기 일반화와 브로드캐스트에서의 기본값 재검증은 후속 문서 [IOCP 서버 브로드캐스트 송신 경로](../../portfolio/broadcast_send_path_2026_11.md)에 정리했다** - 방 16 전달 12.7–12.9배, 묶음 단위에서 skip 켬과 끔은 처리량이 같고 송신 완료 대기와 지연이 줄어듦, 기본값을 묶음 단위(`mergeSends = 1`) + skip으로 바꿈
- **모아 보내기 일반화**: 기억하는 대상을 "수신 처리 중인 세션 하나"에서 "이 스레드가 이번 작업 단위에 보낸 세션 목록"으로 넓힌다. `sendRaw`는 받는 사람이 누구든 링에 넣고 목록에 올리기만 하고(목록에 있는 동안 해제되지 않게 I/O 카운트를 잡는다), 작업 단위가 끝나면 목록의 세션마다 `postSend`를 한 번씩 건다. 컨텐츠 코드는 지금처럼 `SendPacket`만 부르면 된다.
  - 워커의 경계는 GQCSEx로 꺼낸 묶음 하나로 둔다. 한가할 때는 묶음이 작아 거의 기다리지 않고, 포화되면 커져서 모이는 양이 부하에 따라 조절된다. 타이머로 기다리지 않는다는 원칙은 그대로다.
  - 컨텐츠 스레드는 자기 작업 단위 경계를 직접 정하고, 경계가 없는 스레드(핑 등)는 지금처럼 바로 건다.
  - 검증: 채팅(방 브로드캐스트) 데모에서 지금 구조 / 완료 1건마다 / GQCSEx 묶음마다를 비교하고, 방 크기 1(에코와 같음)을 대조 조건으로 둔다.
- 송신 큐 2단계: 고정 링 대신 버퍼 조각 송신 큐. 브로드캐스트에서 같은 패킷을 참조 카운트로 공유해야 하므로 직렬화 버퍼와 함께 설계하고, 플러시할 때 여러 버퍼를 `WSABUF` 배열로 모아 복사 없이 `WSASend` 1번에 보낸다.
- 클라이언트를 다른 PC에 둘 수 있게 되면(유선 랜) open-loop 부하로 포화 전 지연과 서버 단독 한계 측정.
