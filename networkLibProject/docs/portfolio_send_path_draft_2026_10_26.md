# IOCP 서버 송신 경로 분석: 최적화가 역효과를 낸 원인에서 찾은 "우연한 모아 보내기"

> 완료 통지를 줄이는 최적화가 처리량을 82% 떨어뜨렸다. 원인을 추적해 보니 서버의 처리량은 **완료 통지 지연 덕분에 우연히 생긴 모아 보내기**에 기대고 있었고, 같은 원인으로 부하 중 정상 클라이언트가 끊기는 버그도 있었다. 두 문제를 송신 경로 설계로 함께 고쳤다.

**모아 보내기**(send batching): 여러 메시지를 `WSASend` 한 번에 실어 보내는 것. 이 문서에서 가장 중요한 개념이다.

## 핵심 결과

| 질문 | 결과 |
|---|---|
| GQCSEx는 왜 GQCS보다 빨랐나 (최대 +15%) | 이득의 **76%가 `WSASend` 호출 감소**에서 나왔다. 완료를 몰아 처리하는 동안 송신이 더 많이 모였기 때문 |
| 완료 통지를 줄였더니 왜 처리량이 82% 떨어졌나 | 대조 조건으로 분리한 결과, 완료 통지 절감 효과는 측정 오차 수준이고 **모아 보내기가 사라진 것**이 원인 |
| 부하 중 정상 클라이언트가 왜 끊기나 | 넘침 판정이 이미 상대에게 보낸 데이터까지 셌다. 기준을 아직 보내지 않은 데이터로 바꿔, 한도를 지키는 클라이언트는 **구조상 넘침에 걸리지 않게** 했다. 완료 처리 지연을 주입한 시험에서 정상 클라이언트 끊김 **15초당 244–386회 → 0회** |
| 모아 보내기를 설계로 보장하면 | 작은 메시지 처리량 **+56–67%**, 서버 CPU / 패킷 **−32–41%** |

## 1. 측정 환경과 방법

| | PC A | PC B |
|---|---|---|
| CPU | Core Ultra 5 125U, 14 논리 프로세서, 하이브리드 P/E코어 | Core i5-8600, 6코어 6스레드 |
| 측정일 | 2026-10-25–26 | 2026-10-29 |
| 쓰인 곳 | 1, 3–5장, 6장 증상 | 6장 원인 확인부터, 7장 |

- 두 PC 모두 서버와 클라이언트를 같은 PC에서 돌린 루프백이다. CPU와 커널 TCP 스택을 나눠 쓰므로 **절대값보다 같은 조건끼리의 비교**에 의미가 있고, 두 PC의 숫자는 섞지 않는다.
- 처리량은 부하 클라이언트(LoadClient)로 쟀다. 메시지 N개를 묶어 보내고 전부 에코되면 다음 묶음을 보내 **세션마다 오가는 양을 고정**했다. 검증은 페이로드 앞 8바이트 순번 비교만 해서 클라이언트 비용을 줄였다(바이트 단위 검증은 정확성 클라이언트가 따로 맡는다).
- CPU는 `사용 코어 / 스레드 수`로 서버와 클라이언트를 항상 같이 보고, **클라이언트가 먼저 포화된 숫자는 쓰지 않았다.**
- 비교는 같은 실행 안에서 조건을 번갈아 돌리고, 회차마다 순서를 바꿔 3–5회 중앙값을 냈다. PC A는 전원 연결 + 최고 성능 모드로 고정했다. PC B(데스크톱)는 전원 모드를 따로 바꾸거나 확인하지 않았다. 같은 조건도 실행(날짜)이 다르면 ±5% 안팎 차이가 나서 장마다 기준값이 조금씩 다르다(예: 워커 4 GQCS 72.7만 / 77.2만 / 78.0만).

**기준 처리량** (PC A, GQCS, 32B 메시지 × 16개 묶음, 256세션, 3회 중앙값)
| 워커 | 패킷/s | 서버 CPU | 클라이언트 CPU |
|---|---|---|---|
| 1 | 38.1만 | 1.00/1 | 1.63/4 |
| 2 | 54.0만 | 2.01/2 | 2.72/4 |
| 4 | 72.7만 | 4.02/4 | 3.53/4 |
| 8 | **109.9만** | 7.05/8 | 3.62/4 |

서버가 포화된 상태에서 클라이언트는 여유가 있으므로 이 숫자는 서버의 한계다. 워커 8 이상은 서버와 클라이언트가 같은 CPU를 나눠 쓰는 환경 한계에 걸린다.

## 2. 송신 경로 구조
이후의 모든 장은 이 경로 이야기다. 세션마다 송신 링 1개가 있고, 걸려 있는 `WSASend`를 세션당 1건으로 제한하는 **송신 중 표시**(`mSendFlag`)가 있다.

```cpp
struct Session
{
	std::mutex mSendLock;	// 아래 셋을 보호한다
	RingBuffer mSendBuf;	// 보낼 데이터. WSASend에는 이 링의 메모리를 복사 없이 그대로 넘긴다
	bool mSendFlag;	// 송신 중 표시 - WSASend가 걸려 있으면 true (세션당 1건)
	int32_t mSendPosted;	// 지금 걸린 WSASend에 넘긴 바이트 (6장에서 추가)
	// ...
};
```

```
[IOCP 워커 스레드]
수신 완료 → processRecv → OnRecv(컨텐츠) → SendPacket → 송신 링에 push ─┐
                                                                         ↓
송신 완료 → finishSend: 링에서 pop, 송신 중 표시 끔 ──────────────→ postSend
                                                                         ↓
                                        송신 중이 아니면: 표시 켬 → WSASend(링에 쌓인 전부)
```
- 위 그림은 수정 전 경로다. `SendPacket`이 push 직후 바로 `postSend`를 부르는 부분은 7장에서 바뀐다.
- 데이터가 링에서 빠지는 시점은 **송신 완료를 처리할 때**(`finishSend`)다. `WSASend`가 즉시 성공해 데이터가 이미 상대에게 갔더라도, 완료 통지가 처리되기 전까지는 링 자리를 차지하고 송신 중 표시도 켜져 있다. 5장과 6장의 이야기는 모두 이 점에서 나온다.
- 코드: `networkLibProject/NetworkLib.h`(`Session`), `networkLibProject/NetworkLib.cpp`(`processRecv`, `sendRaw`, `postSend`, `finishSend`)

## 3. GQCSEx는 왜 빨랐나
IOCP 워커는 완료 통지를 `GetQueuedCompletionStatus`(GQCS)로 1개씩 꺼내거나, `GetQueuedCompletionStatusEx`(GQCSEx)로 여러 개씩 꺼낼 수 있다. 두 방식을 비교하려고, 워커 루프만 다른 **별도 라이브러리(`NetworkLibEx`)**를 만들어 같은 에코 컨텐츠를 올렸다(`EchoServerT<Lib>`).

PC A, 32B × 16, 프로파일러 끔, 5회 중앙값
| 워커 | GQCS | GQCSEx(64) | 차이 |
|---|---|---|---|
| 2 | 52.1만/s | 54.4만/s | +4.4% (5회 중 3회 우세) |
| 4 | 77.2만/s | 89.1만/s | **+15.4%** (5회 모두 우세) |

"커널 전환이 줄어서"라고 추측하는 대신, 패킷 1개당 비용을 시스템 콜 단위로 나눠 쟀다.

PC A, 워커 4, 32B × 16, 프로파일러 켬(5–15초 구간), 3회 중앙값
- 패킷 1개당 시간 = (그 함수 안에서 보낸 시간을 모든 워커에 걸쳐 더한 값) ÷ (같은 구간에 받은 패킷 수) = 호출 1번 시간 × 패킷 1개당 호출 횟수

| 항목 | GQCS: 패킷당 | (1번 × 횟수) | GQCSEx: 패킷당 | (1번 × 횟수) | 줄어든 660ns 중 비중 |
|---|---|---|---|---|---|
| 전체 (워커 수 × 구간 ÷ 패킷 수) | 4,917ns | | 4,257ns | | |
| 완료 꺼내기 (`GetQueuedCompletionStatus(Ex)`) | 158ns | 0.77µs × 0.2045 | 53ns | 18.4µs × 0.0029 | 16% |
| **송신 (`WSASend`)** | **4,176ns** | 31.4µs × 0.133 | **3,671ns** | 32.0µs × 0.115 | **76%** |
| 수신 (`WSARecv`) | 198ns | | 190ns | | 1% |
| 라이브러리 로직 (완료 처리 − 그 안의 시스템 콜) | 339ns | | 320ns | | 3% |
| 나머지 (프로파일 바깥) | 47ns | | 22ns | | 4% |

- **완료 꺼내기**: GQCSEx는 호출 1번이 길지만(18.4µs) 완료를 약 64개 꺼내 1개당 0.29µs로, GQCS(1개 0.77µs)보다 싸다. 커널 전환과 포트 락 같은 호출당 고정 비용을 여러 완료가 나눠 내기 때문이다. 그래도 패킷 1개당으로는 105ns 차이라 전체 이득의 16%다.
- **송신**: `WSASend` 한 번의 비용은 같았다(31.4 vs 32.0µs). 달라진 것은 **횟수**였다. 패킷당 0.133 → 0.115번, 송신 1번에 실린 바이트 242 → 280B.
- **검산**: 송신 1번 바이트 ÷ 32B ≈ 1 ÷ 패킷당 `WSASend` 횟수. GQCS는 242 ÷ 32 = 7.6개와 1 ÷ 0.133 = 7.5개, GQCSEx는 280 ÷ 32 = 8.8개와 1 ÷ 0.115 = 8.7개로, 두 측정이 같은 현상을 가리킨다.
- 즉 GQCSEx가 완료를 몰아 처리하는 동안 송신 완료 처리가 늦어져, 그 사이 쌓인 메시지가 한 번에 더 많이 나갔다.
- **측정 함정**: 프로파일러를 켠 채 비교하면 기록 비용이 호출 횟수가 많은 GQCS 쪽에만 더 붙는다. 프로파일러 켜기/끄기(`Profile::SetEnabled`)를 추가해 **처리량 비교는 끄고, 비용 분해에만 켰다.**

## 4. WSASend 비용은 호출 횟수가 정한다
- `WSASend`는 **100% 즉시 성공**(커널 송신 버퍼로 복사)했지만, 그래도 IOCP 완료 통지는 따로 온다.
- **송신 버퍼 0(`SO_SNDBUF = 0`)으로 복사를 없애도 이득이 없었다.** 즉시 성공이 0%(전부 비동기)가 됐지만 반환 시간과 CPU는 같았고 처리량은 2–14% 줄었다.
- **메시지 크기를 바꿔 보니** 송신 한 번의 비용은 크기와 거의 무관했다.

PC A, 워커 4, GQCS, 3회 중앙값
| 메시지 × 묶음 | 송신 1번에 실린 바이트 | WSASend 1번 | 처리량 |
|---|---|---|---|
| 32B × 16 | 242B | 33µs | 25MB/s |
| 256B × 16 | 1,916B | 35µs | 188MB/s |
| 4KB × 1 | 3,690B | 40µs | 317MB/s |

→ 송신 비용은 **호출 횟수**가 정한다. 같은 데이터를 적은 호출로 보내는 것이 처리량을 정한다.

## 5. 완료 통지를 줄였더니 처리량이 82% 떨어졌다
`FILE_SKIP_COMPLETION_PORT_ON_SUCCESS`(이하 skip)를 걸면 즉시 끝난 I/O는 완료 통지를 큐에 넣지 않고, I/O를 건 스레드가 그 자리에서 처리한다. 송신이 100% 즉시 성공하므로 송신 완료 통지가 전부 사라진다.

PC A, 워커 4, GQCS, 3회 중앙값
| 조건 | 처리량 | 송신 1번에 실린 바이트 | 서버 CPU / 패킷 | 송신 완료까지 |
|---|---|---|---|---|
| 32B × 16 | 78.0만/s | 242B | 5.2µs | 2.6ms |
| 32B × 16 + skip | **14.0만/s (−82%)** | **31B** | **29.8µs** | 26µs |
| 4KB × 1 | 7.58만/s | 3,691B | 53.8µs | 2.2ms |
| 4KB × 1 + skip | 7.73만/s (+2%) | 3,829B | 53.6µs | 41µs |

**① 기존 구조에서 우연히 모아 보내지는 이유**

라이브러리는 세션마다 `WSASend`를 한 번에 1건만 건다. 걸 때 "송신 중" 표시를 켜고, **그 송신의 완료 통지를 처리할 때** 끈다. 송신 중에 `SendPacket`이 불리면 송신 링에 쌓기만 하고, 완료를 처리할 때 쌓인 것을 전부 `WSASend` 1번으로 보낸다.

```cpp
// SendPacket이 링에 push한 뒤 부른다. 이미 송신 중이면 아무것도 하지 않는다
void NetworkLib::postSend(Session* session)
{
	WSABUF bufs[2];
	int32_t bufCnt = 0;
	{
		std::lock_guard<std::mutex> lock(session->mSendLock);
		if (session->mSendFlag)
		{
			return;	// 송신 중 - 완료 쪽이 이어서 보낸다
		}
		bufCnt = session->mSendBuf.getReadBufs(bufs);	// 링에 쌓인 전부
		if (bufCnt == 0)
		{
			return;
		}
		session->mSendFlag = true;
	}
	WSASend(session->mSock, bufs, bufCnt, nullptr, 0, &session->mSendOv, nullptr);
}

// 송신 완료 통지를 처리할 때 (onSendComplete → finishSend)
{
	std::lock_guard<std::mutex> lock(session->mSendLock);
	session->mSendBuf.pop(transferred);	// 이제야 링에서 빠지고
	session->mSendFlag = false;	// 이제야 송신 중 표시가 꺼진다
}
postSend(session);	// 송신 중에 쌓인 것을 한 번에
```

32B × 16에서는 클라이언트가 메시지 16개를 `send` 한 번에 보내므로, 서버의 수신 완료 1건에 메시지가 약 14개 함께 온다. 워커는 그 자리에서 `OnRecv` → `SendPacket`을 14번 연달아 부른다.
```
OnRecv(메시지 1)    → WSASend(32B) 즉시 성공
                      하지만 완료 통지는 IOCP 큐에서 약 2.5ms 대기 → 송신 중 표시 유지
OnRecv(메시지 2-14) → 송신 중이라 송신 링에 쌓기만 함
(약 2.5ms 뒤)        메시지 1의 송신 완료 처리 → 쌓인 13개를 WSASend 1번으로
→ 메시지 약 14개 = WSASend 2번 (송신 1번에 평균 7.5개, 242B)
```
즉 **송신 중인 동안 같은 세션에 보낼 메시지가 더 생기면** 모아서 보내진다. 모이는 양은 완료 통지가 큐에서 기다린 시간에 달려 있다.

**② 4KB × 1에서는 모아 보낼 메시지가 없는 이유**

클라이언트는 메시지 1개를 보내고 그 에코를 받아야 다음 메시지를 보낸다. 그래서 서버에서 한 세션에 처리할 메시지는 **항상 1개뿐**이다. 송신 중 표시가 켜져 있는 동안 같은 세션에 쌓일 다음 메시지가 없으니, 완료 통지를 늦게 처리하든 바로 처리하든 송신 1번에는 메시지 1개(약 3.7KB)가 실린다. 실제로 skip 유무와 GQCS/GQCSEx 모두에서 송신 1번 바이트가 거의 같았다(3,691 / 3,829B, GQCSEx 3,714B).

**③ 그래서 4KB × 1을 대조 조건으로 썼다**

skip을 켜면 두 가지가 동시에 바뀐다. (a) 큐에 들어가는 완료 통지가 줄고, (b) 송신 완료가 즉시 처리돼 송신 중 표시가 바로 꺼진다(= ①의 모아 보내기가 사라진다).
- 32B × 16: (a)와 (b)가 섞여 −82% 하나로 나온다.
- 4KB × 1: 원래 모아 보낼 것이 없으니 (b)의 영향이 없고 **(a)만 보인다.** 큐에서 꺼내는 완료가 패킷당 2.2 → 1.07개로 절반이 됐는데 **서버 CPU / 패킷은 그대로**(53.8 → 53.6µs)였다. 완료 통지를 줄인 이득은 측정 오차 수준이다.
- 따라서 32B × 16의 −82%는 거의 전부 (b), 모아 보내기가 사라진 결과다.
```
skip 켬 (32B × 16): 메시지마다 WSASend → 그 자리에서 완료
→ 송신 중 표시가 바로 꺼짐 → 다음 메시지도 바로 WSASend
→ 메시지 약 14개 = WSASend 14번 (송신 1번 31B, 호출 7배 → CPU / 패킷 5.7배)
```

**결론**: 코드 어디에도 "모아서 보내자"는 의도가 없었다. 처리량은 **송신 완료가 큐에서 기다리는 지연 덕분에 우연히 생긴 모아 보내기**에 기대고 있었고, 3장의 GQCSEx 이득도 같은 현상이다. 지연에 기댄 모아 보내기라 서버가 한가할수록 오히려 덜 모인다. 그래서 모아 보내기를 **설계로 보장**하기로 했다(7장). skip은 실험 후 코드에서 제거했다.

## 6. 같은 원인의 버그: 부하 중 정상 클라이언트가 끊긴다
**증상**: 정상 클라이언트가 15초 테스트 6–7회 중 1–2회 "송신 링 넘침"으로 끊겼다(PC A). 정상 클라이언트는 에코가 돌아오지 않은 바이트를 서버 송신 링(16KB)보다 작은 15,360B 이하로 지키는데도 끊겼다.

**가설**: 송신 링은 **송신 완료를 처리해야** 비워진다. 데이터는 이미 클라이언트에 도착했는데 완료 통지가 큐에서 기다리는 동안 링 자리를 차지해서, 클라이언트 기준으로는 한도 안인데 서버 링이 넘친 것이다.

**원인 확인**: 넘침으로 끊는 순간의 송신 링을 두 몫으로 나눠 기록했다(PC B).
- (가) 이미 `WSASend`에 넘긴 바이트: 대부분 상대에게 도착했고 완료 통지만 기다린다.
- (나) 아직 `WSASend`에 넘기지 않은 바이트: 상대에게 절대 도착하지 않았다.

| 끊긴 연결 | 링 사용 | (가) 넘긴 몫 | (나) 안 넘긴 몫 | 걸어 둔 송신의 경과 |
|---|---|---|---|---|
| 정상 클라이언트 | 14,517B | **14,517B** | **0B** | 8.5ms |
| 받지 않는 클라이언트 (대조, 109건 중 앞 5건) | 13–16KB | 15B–3.9KB | **1.2만–1.5만B** | 77–166ms |

정상 클라이언트를 끊은 링은 **전부 이미 상대에게 보낸 데이터**였다. 진짜 느린 클라이언트는 (나)가 쌓이고 송신이 수십 ms씩 끝나지 않는다. 서버의 넘침 정책이 **"받지 않는 느린 클라이언트"와 "서버 자신의 완료 처리 지연"을 구분하지 못한** 것이다. 그래서 서버가 바쁠수록 정상 클라이언트를 더 끊었다.

**재현 조건 찾기**: PC B에서는 기본 설정의 송신 완료까지가 17µs(PC A는 2.2–2.6ms)라 정상 에코 21회 중 1회만 끊겼다. 이를 "고쳐졌다"로 넘기지 않고, 가설이 맞다면 완료 처리가 늦을수록 더 끊겨야 한다는 예측을 이용했다. 워커를 1개로 줄이고 부하 클라이언트를 함께 띄워 송신 완료까지를 10–11ms로 늘린 조건에서 끊김을 잡았고, 위 표의 정상 클라이언트 기록은 이때 얻었다(받지 않는 클라이언트 기록은 기본 설정). 다만 나중에 같은 조건에서 수정 전 빌드를 반복해 보니 **16회 중 1회**로 여전히 드물었다. 지연이 길다는 것만으로는 부족하고, 큰 송신이 완료를 기다리는 사이에 클라이언트가 다음 데이터를 보내는 타이밍까지 맞아야 하기 때문으로 보인다.

**수정**: 클라이언트 쪽 한도를 줄이는 임시 조치는 하지 않고 서버를 고쳤다.
- 넘침 기준을 **(나) 안 넘긴 몫**으로 바꿨다. 정상 클라이언트라면 (나)는 클라이언트의 한도를 넘을 수 없고, 받지 않는 클라이언트는 (나)가 계속 쌓이므로 그대로 잡힌다.
- 송신 링을 한도의 2배(32KB)로 늘렸다. (가)는 넘길 때의 (나)였으므로 한도를 넘지 않고, 링에는 (가)+(나)가 항상 들어간다.

```cpp
// sendRaw: 송신 링에 넣기 전 넘침 판정 (mSendLock 안)

// 수정 전 - 링 전체가 기준이라 이미 보낸 몫(가)까지 센다
if (session->mSendBuf.getFreeSize() >= packetSize) { /* push */ }
else { /* 넘침 → 끊기 */ }

// 수정 후 - 아직 WSASend에 넘기지 않은 몫(나)만 센다
int32_t pending = session->mSendBuf.getUseSize() - session->mSendPosted;
if (pending + packetSize <= SEND_PENDING_LIMIT) { /* push */ }
else { /* 넘침 → 끊기 */ }
```
`mSendPosted`는 `postSend`가 `WSASend`에 넘긴 길이를 적고, `finishSend`가 0으로 돌린다. 수정의 핵심은 판정식 한 줄이다.

**검증** (PC B)
- **판정식**: 정상 클라이언트는 에코가 안 돌아온 바이트를 15,360B 이하로 지키고, (나)는 클라이언트에 도착하지 않은 바이트이므로 데이터 몫은 항상 15,360B 이하다. 나머지 1KB는 서버가 보내는 핑 몫으로 남겨 두었으므로 (나)는 한도(16KB)를 넘지 않는다. 바뀐 판정식에서는 한도를 지키는 클라이언트가 넘침에 걸릴 수 없다. 횟수가 아니라 구조로 보장된다.
- **회귀**: 받지 않는 클라이언트는 계속 잡힌다(15초 테스트에서 수정 전 163건, 수정 후 192건).
- **반복 횟수 비교는 근거가 되지 못했다**: 재현 조건에서 수정 전 16회 중 1회, 수정 후 18회 중 0회. 버그가 이만큼 드물면 수정하지 않았더라도 18회 연속 0이 나올 확률이 약 30%라, 횟수로는 수정 효과를 말할 수 없다.
- **결정적 재현 시험**: 운에 맡기지 않으려고, 송신 완료를 처리하기 전에 워커를 일부러 잠재우는 테스트 전용 설정(`testSendCompleteDelayMs`)을 넣었다. 잠든 동안 다른 워커가 같은 세션의 수신을 처리하며 링에 응답을 쌓으므로, 버그의 조건(완료 처리 지연 + 다음 데이터 도착)을 매번 만든다. 수정 전 빌드에도 같은 설정만 덧대 같은 실행 안에서 번갈아 돌렸다(워커 2, 정상 EchoClient만, 15초, 지연별 3회).

| 주입한 지연 | 수정 전: 정상 클라이언트 끊김 | 수정 후 | 처리량 (전 / 후) |
|---|---|---|---|
| 1ms | 244–382회 | **0회** (3회 모두) | 94–96 / 96–98MB |
| 2ms | 329–386회 | **0회** (3회 모두) | 53–67 / 67MB |
| 5ms | 302–328회 | **0회** (3회 모두) | 34 / 33–34MB |

수정 후 빌드는 같은 지연(2ms)에서도 받지 않는 클라이언트는 계속 끊었다(30건). 지연을 끈 기본 설정에서는 처리량과 끊김이 설정을 넣기 전과 같았다.

## 7. 모아 보내기를 설계로 보장하다
5장에서 처리량이 완료 지연이라는 우연에 기대고 있음을 봤다. 6장의 수정과 같은 송신 경로라 함께 바꿨다.

세션당 `WSASend`를 1건만 거는 규칙(송신 중 표시)은 그대로 두고, **첫 송신을 거는 시점**만 바꿨다.
- 수정 전: 송신 중이 아니면 첫 번째 `SendPacket`이 불린 순간 건다. 첫 메시지 하나가 혼자 먼저 나가고, 나머지는 그 송신의 완료가 처리될 때 모여서 나간다.
- 수정 후: 수신 처리 중에 같은 세션으로 보내는 응답은 송신 링에 쌓기만 하고, **수신 처리가 끝날 때 `WSASend`를 한 번** 건다. 수신 처리 밖(컨텐츠 스레드, 핑 스레드)에서 보내는 것은 전처럼 바로 건다.

수신 1건에 메시지 14개가 들어온 경우:
```
수정 전
OnRecv(1)    → SendPacket → 송신 중 아님 → WSASend(1개)   ← 혼자 먼저 나감
OnRecv(2-14) → SendPacket → 송신 중 → 링에 쌓기만
(완료 통지 처리 뒤) 쌓인 13개를 WSASend 1번                → WSASend 2번

수정 후
OnRecv(1-14) → SendPacket → 링에 쌓기만
수신 처리 끝 → WSASend(14개)                                → WSASend 1번
```

```cpp
thread_local Session* tRecvSession = nullptr;	// 이 스레드가 지금 수신 처리 중인 세션

bool NetworkLib::processRecv(Session* session, DWORD transferred)
{
	tRecvSession = session;
	while (완성된 패킷이 있으면)
	{
		OnRecv(session->mId, payload, len);	// 컨텐츠가 안에서 SendPacket → 링에 쌓기만 한다
	}
	tRecvSession = nullptr;
	postSend(session);	// 이번 수신으로 생긴 응답 전부를 WSASend 1번으로
}

bool NetworkLib::sendRaw(Session* session, ...)
{
	// (mSendLock 안에서 송신 링에 push)
	if (session != tRecvSession)
	{
		postSend(session);	// 수신 처리 밖에서 보낸 것은 바로 건다
	}
}
```
- 서버는 메시지가 몇 개 올지 모른다. 이번 수신에 완성된 패킷이 1개면 1개, 15개면 15개를 보낸다. 모이는 양은 **트래픽 모양**(수신 1건에 메시지가 몇 개 오느냐)이 정하므로, 아래 +56–67%는 "수신 1건에 메시지 약 15개" 조건의 숫자다.
- Nagle 알고리즘처럼 "조금 더 모이면 보내자"며 타이머로 기다리지 않는다. 첫 응답이 기다리는 시간은 같은 수신에 들어온 나머지 패킷을 처리하는 시간뿐이고, 수신 처리가 끝나는 즉시 보낸다.

수정 전 빌드와 수정 후 빌드를 **같은 실행 안에서 번갈아** 돌렸다(PC B, GQCS, 3회 중앙값).
| 워커 | 메시지 × 묶음 | 처리량 수정 전 → 후 | 송신 1번에 실린 바이트 | 서버 CPU / 패킷 |
|---|---|---|---|---|
| 2 | 32B × 16 | 73.3만 → **122.7만/s (+67%)** | 229 → 467B | 1.94 → 1.31µs |
| 4 | 32B × 16 | 74.2만 → **115.9만/s (+56%)** | 209 → 465B | 2.64 → 1.56µs |
| 2 | 4KB × 1 | 5.83만 → 5.64만/s | 3,607 → 3,591B | 22.53 → 22.52µs |
| 4 | 4KB × 1 | 5.76만 → 5.56만/s | 3,601 → 3,564B | 26.37 → 25.35µs |

- 32B × 16: 수신 1건에 메시지 약 15개가 오고, 이제 그것이 `WSASend` 1번으로 나간다. 송신 1번에 실린 바이트가 2배가 됐다.
- 4KB × 1: 5장과 같은 대조 조건이다. 모아 보낼 메시지가 없어 송신 1번 바이트와 서버 CPU / 패킷이 그대로다. 처리량 차이(−3%)는 회차별 범위가 겹친다. → 이득은 모아 보내기에서 왔다.
- PC B에서는 서버(1.6/2, 1.8/4코어)도 클라이언트(2.3/4코어)도 포화가 아니어서, 처리량보다 **서버 CPU / 패킷(−32%, −41%)**이 더 믿을 만한 지표다.

## 8. 측정을 믿기 위해 한 일
숫자는 맞았지만 잘못 읽을 뻔한 것들을 따로 기록했다(`README_ERRORS.md` 4장).
- 처음 잰 처리량이 서버가 아니라 측정 클라이언트의 한계였다(바이트 단위 검증 비용으로 클라이언트 CPU 3.95/4). → 처리량 전용 부하 클라이언트를 따로 만들었다.
- 같은 조건이 회차마다 30% 넘게 달랐다. → 전원 모드 고정, 회차마다 순서 바꾸기, 중앙값으로 편차를 ±1–9%까지 줄였다.
- CPU 표에 분모(스레드 수)를 빠뜨려 "4.34"가 "4개 중 4.34"로 읽혔다. → CPU는 항상 `사용 코어 / 스레드 수`로 적는다.
- 크기가 다른 조건이 집계에서 한 줄로 합쳐져 범위가 62만–546만으로 나왔다. → 범위가 몇 배씩 벌어지면 편차보다 집계 키를 먼저 의심한다.
- 프로파일러 비용이 비교 대상마다 다르게 붙는 혼입 변수가 있었다. → 처리량 비교와 비용 분해를 다른 실행으로 나눴다.
- "송신 완료까지 2–4ms"를 ACK 대기로 해석했다가, 기본 설정과 skip(41µs) 비교로 IOCP 큐 대기로 정정했다.
- PC를 바꾸자 버그가 거의 재현되지 않았을 때 "고쳐졌다"로 보지 않고, 가설의 예측(완료 지연이 길수록 더 끊긴다)으로 재현 조건을 만들었다. 그런데 처음에는 수정 전 3회 중 1회만 보고 "수정 후 9회 중 0회"를 근거로 삼았다. 수정 전 빌드를 같은 실행 안에서 번갈아 더 돌리자 16회 중 1회로 드물어, 이 비교가 근거가 되지 못함을 확인하고 정정했다. 대신 버그의 조건(완료 처리 지연)을 주입하는 시험을 만들어, 수정 전에는 15초마다 수백 번, 수정 후에는 0번임을 결정적으로 보였다. → 수정 전후 비교는 같은 실행 안에서 번갈아, 버그 빈도를 먼저 확인하고, 드문 버그는 조건을 주입해 재현한다.

## 9. 한계와 다음 단계
**한계**
- 루프백 측정이라 `WSASend` 한 번에 받는 쪽 TCP 처리까지 들어가, 호출 비용(30–40µs)이 실제 NIC보다 크다. −82%나 +67% 같은 **크기**는 이 환경의 숫자이고, "호출 횟수가 비용을 정한다"는 **방향**만 일반화한다.
- 4KB 조건은 PC A에서 클라이언트 CPU도 포화(3.98/4)라 처리량보다 서버 CPU / 패킷으로 판단했다.
- 처리량 클라이언트는 closed-loop라 항상 포화 상태를 잰다. 평소 부하의 지연은 전송률을 고정한 부하로 따로 재야 한다.
- 서버와 클라이언트를 다른 PC에 둘 수 없어 서버 단독 한계(워커 8 이상)는 측정하지 못했다.
- 6장의 버그는 PC B에서 드물어(수정 전 16회 중 1회) 반복 횟수로는 수정 효과를 보일 수 없었다. 그래서 완료 처리 지연을 주입해 재현했는데, 이 시험은 지연을 인위적으로 만든 것이라 실제 부하에서 버그가 얼마나 자주 나는지는 보여 주지 않는다.
- 모아 보내기는 수신 처리 안에서 보낸 응답에만 적용된다. 컨텐츠 스레드의 송신이나 브로드캐스트는 아직 모아 보내지 않는다.
- 모아 보내기 적용 후 탐침(데이터 없이 핑만 보내 왕복 시간을 재는 측정용 연결) 지연 p50이 3.6 → 4.1ms로 늘었다. 처리량이 늘어 같은 PC의 부하가 커진 영향으로 추정하지만 확인하지 않았다.

**다음 단계**
- 송신 큐 2단계: 고정 링 대신 버퍼 조각 송신 큐. 브로드캐스트에서 같은 패킷을 참조 카운트로 공유해야 하므로 직렬화 버퍼와 함께 설계하고, 수신 처리 밖 송신의 모아 보내기도 이때 다룬다.
- 모아 보내기 + skip 재비교: 모아 보내기가 설계로 보장되면 skip은 손해 없이 송신 완료 지연만 줄일 가능성이 있다.
- 전송률을 고정한(open-loop) 부하로 포화 전 지연 측정.
