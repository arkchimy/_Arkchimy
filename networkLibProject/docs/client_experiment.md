# 부하 생성 클라이언트 (설계 중, 미구현)

## 목적

`AcceptServer`/`AcceptExServer`의 accept 처리량(TPS)을 비교하려면, 서버 쪽 한계가 보일 만큼
연결을 세게 쏟아부을 수 있는 클라이언트가 필요하다.

지난번 지운 `DummyClient`(블로킹 순차 connect, 성공한 소켓을 안 닫고 들고 있음 — backlog 큐
크기를 확인하려고 일부러 그렇게 만든 것)와는 목적이 다르다. 이번엔 "최대한 빠르게 많이 연결하고
바로 정리"가 목표.

## 왜 논블로킹 + 여러 스레드인가

블로킹 `connect()`는 한 스레드가 한 번에 connect 하나씩만 처리할 수 있어서, 스레드 수가 곧
동시 connect 수의 상한이 된다. 논블로킹이면 `connect()` 호출이 즉시 반환되고 커널이 뒤에서
handshake를 진행하므로, 한 스레드가 짧은 시간에 소켓을 계속 새로 만들어 더 많은 connect를
던질 수 있다. 여기에 여러 스레드를 더하면 동시성이 한 번 더 늘어난다. 목표는 서버 TPS를
클라이언트 쪽이 병목이 되지 않을 만큼 키우는 것.

## 결정된 것

- **connect 성공 후 클라이언트도 바로 소켓을 닫는다.** 서버가 accept 직후 `closeReset`으로
  즉시 RST를 보내는데, 그 RST가 네트워크에서 유실될 가능성이 있다. 클라이언트가 서버의 close
  신호를 기다렸다가 자기 소켓을 정리하면, RST 유실 시 클라이언트 소켓이 계속 남아있게 된다.
  그래서 클라이언트는 서버의 응답을 기다리지 않고 connect 성공이 확인되는 즉시 자기 쪽에서도
  바로 닫는다 — 서버와 동일하게 "맺으면 즉시 정리"로 통일.
- 서버 쪽처럼 1초마다 통계(그 1초간 connect 시도/성공/실패 수)를 콘솔에 출력한다.

## 아직 안 정한 것 (설계 필요)

- **연결 성립 확인 방법.** 논블로킹 `connect()`는 보통 `WSAEWOULDBLOCK`을 돌려주고 바로
  반환되므로, 실제로 연결이 됐는지는 따로 확인해야 한다. 후보:
  - `select()`/`WSAPoll`로 해당 소켓이 writable해지는 시점을 체크
  - 클라이언트도 서버처럼 IOCP로 받기 (구조는 통일되지만 클라이언트 입장에서 과한 설계일 수 있음)
- 연결 실패(타임아웃, RST 등)를 성공과 구분해서 집계할지, 아니면 시도 수만 셀지.
- 서버 주소/포트, 스레드 수, 실행 시간 같은 설정값을 `server.cfg`처럼 cfg 파일로 뺄지, 코드에
  하드코딩할지.
