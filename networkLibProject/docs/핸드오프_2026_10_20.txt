# 핸드오프 2026-10-20 — AcceptEx와 백로그, slotCnt, 워커 수 (포트폴리오 결론 확정)

## 배경
IOCP NetworkLib 결정 지도 ⑧ Accept 방식. accept 전담 스레드 vs AcceptEx 비교를 측정 근거와 함께 포트폴리오로 남기는 중.
측정 환경: LG gram Core Ultra 5 125U, 루프백, 전원 어댑터 연결(배터리면 편차 1.5~3배), Windows 11 Pro 26200
(ws2_32/mswsock 10.0.26100.1, afd.sys 10.0.26100.8036, tcpip.sys 10.0.26100.8521), Winsock 2.2.

## 오늘 흐름 (순서 그대로)
1. 비교 기준 재정의: AcceptEx를 고른 이유는 "백로그 포화로 정상 연결이 거절되는 것을 줄인다". 그런데 기존 측정은 backlog 65535·실패 0 → 거절을 잰 적이 없었음.
2. 거절 측정 방식 확정: backlog 200(hint로 200 미만은 200으로 세팅됨 — 이미 확인), 클라 Select의 exceptSet 실패 횟수로 카운트.
   RST 후 ~2초 SYN 재시도해도 성공 안 함(이미 실험). 비교는 누적값이 아니라 구간 비율(시도/s, 성공/s, 실패율).
3. backlog 200 측정(accept w1, AcceptEx w1/w2/w4, slotCnt 1000): 실패 거의 없음. 이유 = slotCnt 1000 > 클라 동시 진행 512.
4. MSDN 조사 → 걸어둔 AcceptEx가 도착한 연결을 직접 받는다(아래 근거). 유저: "이 실험과정과 MSDN 글은 반드시 포트폴리오에 들어가야 한다."
5. 유저 오해 교정: "AcceptEx는 syscall이 한 번에 끝나서 빠르다" → 실제로는 syscall이 더 많고, 비용을 연결 도착 전으로 옮긴 구조.
6. 유저 지적: "빨리 비운다"가 아니라 "백로그 용량을 늘린 느낌" → 거절 관점에서는 맞음(용량 확보).
7. 걸어둔 게 소진되면 연결은 백로그에 쌓이고, AcceptEx 재등록 시 백로그에서 꺼내 붙음 → slotCnt가 적을수록 "더 비싼 accept"가 됨.
8. 유저 가설: slotCnt 적은데 워커를 늘리면 백로그 큐 경합으로 성능이 안 오른다 → s8 × w1/w2/w4 + w4 s1000 프로파일로 검증.
9. 결과: Post 비용은 slotCnt 부족 시 2.5배 증가(실재), 하지만 socket()이 반대로 움직여 총 비용·처리량 차이는 잡음 수준.
   → 워커 수를 막는 것은 백로그 경합이 아니라 커널 소켓 생성/종료/등록 경로 전반의 비용 증가.
10. DisconnectEx(TF_REUSE_SOCKET) 소켓 재사용 검토 → 유저가 기각(아래).
11. 결론 범위: AcceptEx 워커를 늘린다고 무조건 좋지 않다. 단 accept 다중 스레드는 미측정이라 accept는 결론에 넣지 않음. 포트폴리오는 기존 방향(AcceptEx 범위)으로.

## AcceptEx가 하는 일 (MSDN 근거)
- AcceptEx 레퍼런스: "combines several socket functions into a single API/kernel transition" = accept + 로컬/원격 주소 + 첫 recv.
  "If dwReceiveDataLength is zero ... AcceptEx completes as soon as a connection arrives" → 우리 서버는 0을 넘김(AcceptExServer.cpp:74).
  "lpdwBytesReceived ... set only if the operation completes synchronously" → 걸 때 이미 기다리던 연결이 있으면 즉시 완료.
- MSDN Magazine 2000.10 "Write Scalable Winsock Apps Using Completion Ports"(Anthony Jones, Amol Deshpande — Windows 2000 Networking group):
  "If there are no accept operations pending, the event [FD_ACCEPT] will be signaled by an incoming connection."
  "your server will start to refuse connections to legitimate clients because it has no more accepts pending."
  "let the number of posted AcceptEx operations vary between application-specific low and high watermarks"
  소켓 생성·대기 중인 I/O도 비페이지 풀을 쓴다 → "비페이지 풀 때문에 AcceptEx"는 약한 근거, "흡수 용량을 직접 조절"이 버티는 근거.
- 미문서: 백로그 큐를 거쳐 가는지, backlog 200 칸을 같이 쓰는지(용량 200 vs 200+N). → 검증 실험(첫 거절 순번) 미실시.

```
걸어둔 AcceptEx가 있을 때
  socket() → AcceptEx() 등록 ──(대기)──> [SYN/핸드셰이크 완료] → 커널이 즉시 소켓에 붙임 → 완료 통지 → 워커가 나중에 꺼냄
                                           (서버 스레드를 기다리지 않음)
다 썼을 때 (slotCnt 부족)
  [핸드셰이크 완료] → 백로그 대기 ──(서버 기다림)──> socket() → AcceptEx() 등록 → 백로그에서 꺼내 붙임 → 완료 통지
                                                    (= syscall 3개짜리 accept: GQCS + socket + AcceptEx)
accept()
  [핸드셰이크 완료] → 백로그 대기 ──(서버 기다림)──> accept() 1번 (커널이 소켓 생성까지)
```

## 확정된 결정
```
결정: 소켓 재사용(DisconnectEx TF_REUSE_SOCKET) 안 함
선택     : closeReset(linger0 → RST) + 매번 socket()
기각     : DisconnectEx 재사용
이유(유저): 서버가 RST를 안 쓰면 비정상 클라를 끊을 때 상대가 ACK를 안 보내면 정리가 지연된다
보조(MSDN): 정상 종료라 서버가 먼저 끊으면 TIME_WAIT(기본 240초)로 재사용 지연
비용     : socket()이 동시 생성 수에 따라 증가 (w1 19 → w4 67, s1000 127us) → 감수
```

## 포트폴리오 결론 (초안에 반영할 것 — docs\portfolio_accept_draft_2026_10_20.md)
1. AcceptEx는 "빠른 accept"가 아니다. syscall은 더 많고, 소켓 생성·등록 비용을 연결 도착 전으로 옮겨 도착 시점에 서버를 기다리지 않게 한다.
2. 거절 관점에서 걸어둔 AcceptEx는 흡수 용량이다. slotCnt가 클라 동시 진행 수보다 적으면 연결이 백로그를 거쳐 "더 비싼 accept"가 된다(Post 2.5배).
3. 워커 수를 늘린다고 무조건 좋지 않다. 2개 이후 처리량 정체, socket/close/Post 비용이 워커 수에 따라 증가(이 노트북 루프백 기준의 포화 지점).
4. 소켓 재사용은 RST 정책 때문에 기각.
※ 초안과 충돌: 2절 "수락이 병렬화돼서" → 교체 필요. 3절 "slotCnt 수십 개면 충분"(10/19, w4·backlog 65535) → 오늘 결과(w1에서 큰 영향, w4에선 잡음 수준)와 함께 조건을 밝혀 수정.
※ 한계에 적을 것: 1회 측정·편차 큼, 2000년 문서 vs Windows 11, 200+N 미검증, accept 다중 스레드 미측정, 클라·서버 CPU 공유.
