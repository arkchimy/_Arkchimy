# 처리량 측정 도구와 서버 워커 수 실험 (2026-10-25)

> 측정은 노트북 한 대의 루프백(서버와 클라가 같은 CPU를 나눠 씀)에서 했다. 다른 PC는 쓸 수 없어 서버 단독 한계는 측정하지 못했다.
> 원본 측정값: `실험폴더/LoadClient_workers_2026_10_25/raw_runs.csv`

## 1. 결정할 것
1. 서버 처리량(초당 패킷 수)을 **측정 도구의 한계에 묶이지 않고** 재려면 부하 클라이언트를 어떻게 만들어야 하는가
2. IOCP 워커 수를 늘리면 처리량과 지연이 어떻게 변하는가

## 2. 출발점: 처음 숫자는 측정 클라이언트의 한계였다

EchoClient(정확성 검증용: 무작위 크기로 잘라 보내고 바이트마다 비교)로 잰 첫 결과는 "에코 160MB/s, 부하 중 RTT p50 13ms"였다.
이 숫자를 의심한 근거와 확인 과정:

| 확인 | 방법 | 결과 |
|---|---|---|
| 지연이 서버 세션 큐 때문인가 | 클라의 큐 한도(`maxInflight`)를 15360 → 4099B로 줄임 | 큐를 3.7배 줄여도 RTT는 25%만 감소 → 큐가 주원인이 아님 |
| 클라가 한계인가 | EchoClient에 CPU 코어 출력 추가 | 4스레드에 **3.95코어** = 클라 포화 |
| 서버 몫은 얼마인가 | **탐침** 클라: 데이터 없이 직접 핑만 보내는 연결을 부하와 함께 띄움 | 워커 2: 탐침 p99 8.5ms, 서버도 2.0코어로 포화 / 워커 4: 탐침 p99 3.1ms인데 에코 처리량은 그대로 |

결론: **서버와 측정 클라가 둘 다 포화**였고, 에코 처리량은 워커를 늘려도 변하지 않았다 → 처리량 숫자는 클라 한계였다. 서버를 재려면 더 가벼운 부하 클라가 필요했다.

## 3. 부하 전용 클라이언트(LoadClient) 설계

| 결정 | 이유 |
|---|---|
| 정확성 검증(EchoClient)과 처리량 측정(LoadClient)을 **다른 프로그램으로 분리** | 바이트 단위 검증 비용이 처리량 측정에 섞이지 않게 |
| 32B 고정 메시지(헤더 3 + 페이로드 29, 앞 8바이트 순번), **순번만 확인** | 유실·중복·순서 바뀜은 순번으로 잡힌다. 내용 변조는 EchoClient가 맡는다 |
| `overSend`개를 **`send` 한 번에 일괄 송신**, 묶음이 전부 돌아와야 다음 묶음 | 시스템 콜 수를 메시지 수의 1/overSend로. 동시에 날아가는 양이 `세션 × overSend × 32B`로 정확히 통제된다 |
| `overSend` 최대 480 | 한 묶음(480 × 32B = 15360B)이 서버 송신 링(16384B - 제어 패킷 자리 1KB)에 들어가야 넘침으로 끊기지 않는다 |
| 연결 유지(재연결 없음) | 재연결 비용이 처리량에 섞이지 않게 |
| 서버 핑에 퐁 응답 | 송신 버퍼에 항상 완성된 패킷만 있어서 퐁을 뒤에 붙여도 패킷 경계가 깨지지 않는다 |

- 응답이 와야 다음을 보내는 **closed-loop**라 처리량 전용이다. 서버가 느려지면 덜 보내므로 지연은 별도 탐침으로 잰다.
- 서버에는 워커별 수신 패킷 카운터(64바이트 정렬, 워커당 단일 쓰기)를 추가해 클라 숫자와 교차 확인했다.

첫 실행(워커 2, 256세션, overSend 16): **클라 50만 메시지/s = 서버 수신 50만 패킷/s**, 클라 2.7/4코어(여유), 서버 2.0/2코어(포화) → 이제 서버가 먼저 한계에 닿는다.

## 4. 측정 방법
- 조건: 서버 워커 1 / 2 / 4 / 8 (LoadClient 1개: 4스레드 × 64세션 = 256세션, overSend 16), 워커 8 + LoadClient 2개(512세션). 모든 조건에 탐침(64연결, 10ms마다 핑) 동시 실행
- 조건마다 15초 × **3회**, 회차마다 실행 순서를 한 칸씩 돌려 시간에 따른 변화(발열 등)가 특정 조건에 쏠리지 않게 함
- 값: 연결 직후 2초와 종료 직전 1초를 뺀 1초 값들의 중앙값 → 3회의 중앙값
- 환경: Intel Core Ultra 5 125U(성능 코어 2개/4스레드 + 효율 코어 8 + 저전력 효율 코어 2 = 14스레드), **전원 연결 + 전원 모드 "최고 성능"**(측정 후 균형 조정으로 복원)
- 자동화: `tools/load_sweep.ps1 -Tag best_perf` (server.cfg의 워커 수를 바꿨다가 끝나면 복원, 회차별 CSV + 조건별 중앙값 표)

## 6. 해석

**워커를 늘리면 처리량은 오르지만 코어당 효율은 떨어진다.**
코어당 처리량: 38만(워커 1) → 27만(2) → 18만(4) → 16만(8). 워커 1개는 성능 코어를 혼자 쓰고, 늘어날수록 효율 코어와 스레드 간 경합이 섞이는 것으로 추정한다(코어 고정 실험으로 확인 필요).

**서버 CPU의 약 90%가 커널 시간이다.**
라이브러리 코드(유저 모드)는 10% 남짓이고, 나머지는 `WSARecv`/`WSASend`/GQCS 시스템 콜과 루프백 TCP 처리다. 처리량을 더 올리려면 코드 최적화보다 시스템 콜 한 번에 더 많은 일을 시키는 방향이 효과가 클 것으로 본다.

**이 환경의 측정 상한은 약 110만 패킷/s(32B)다.**
워커 8 + 클라 2개에서 서버(6.26/8)도 클라(4.34)도 포화가 아닌데 처리량이 오히려 줄었다. 실행할 스레드(서버 8 + 클라 8 + 탐침)가 14스레드(빠른 것은 4)를 넘어서, 같은 CPU를 나눠 쓰는 환경 전체가 한계다.

**클라를 늘리자 부하 세션 지연만 100ms 이상으로 튀었다.**
같은 실행에서 탐침 p99는 8ms 그대로였다. 서버가 느려진 것이 아니라, OS가 일부 LoadClient 스레드를 수십 ms 동안 실행하지 못해 그 스레드의 세션 64개가 퐁을 늦게 보낸 것으로 해석한다. 탐침을 함께 띄운 덕분에 서버 지연과 측정 도구의 지연을 분리할 수 있었다.

**지연(수 ms)은 "포화 상태의 지연"이다.**
LoadClient는 closed-loop라 항상 서버를 한계까지 민다. 서버에 여유가 있는 평소 부하의 지연은 이 실험으로 알 수 없다.

**측정 환경 고정의 효과.**
고정 전에는 같은 조건(워커 4)이 회차마다 71만 / 95만으로 30% 이상 달랐다. 전원 모드 고정과 3회 중앙값 이후 워커 1은 ±1%, 워커 8은 ±5%로 줄었다(워커 2만 ±9%).

## 7. 결론
- 처리량 측정은 **정확성 검증 클라와 분리한 가벼운 부하 클라**로 해야 서버 한계가 보인다. 첫 측정 숫자는 측정 클라의 한계였다.
- 서버는 워커 수에 따라 38만 → 110만 패킷/s(32B, 워커 1 → 8)까지 오르고, 그 이상은 이 PC 루프백 환경의 한계다.
- 처리량 숫자와 함께 **서버·클라 CPU(사용 코어 / 스레드 수)**를 반드시 기록해야 병목 위치를 판단할 수 있다.

## 8. 한계와 남은 측정
- 루프백 + 같은 PC: 서버 단독 한계는 측정 불가(다른 PC 사용 불가)
- 하이브리드 CPU: 스레드가 어느 코어에서 돌았는지 고정하지 않았다 → 워커를 성능 코어에 고정(affinity)한 비교가 남아 있다
- 지연은 포화 상태에서만 쟀다 → 목표 전송률(open-loop) 부하로 부하 대비 지연 곡선과 한계점을 재야 한다
- 메시지 크기 32B 하나, overSend 16 하나만 측정했다
- 탐침 단독 RTT(p50 1.3ms)가 서버 핑으로 잰 무부하 RTT(431µs)보다 큰 이유는 아직 확인하지 못했다
