## 1. 이 실험이 증명하려는 것

연결이 쏟아질 때 블로킹 `accept()`와 `AcceptEx`(IOCP 비동기) 중 어느 쪽이
accept 처리량(TPS)이 높은지 비교한다. 서버 쪽 집계 기준은 **"accept/AcceptEx 완료통지를
처리한 개수"**이지 실제 수립된 연결 수가 아니다. (유저가 명시)

### 공격 방어와의 관계 (오늘 정리한 것)
- **SYN flood는 이 실험과 무관하다.** SYN flood는 3-way 핸드셰이크가 끝나지 않아
  앱(L7)까지 연결이 오지 않는다. 방어는 커널(SYN cookie)·L4 장비·앞단 Anti-DDoS의 몫이다.
- 서버 코드가 맡는 건 **핸드셰이크를 완료한** 공격 — 연결 폭주(connection flood),
  Slowloris 등이다. 이때 "빨리 accept해야 인증 기한/IP 제한 같은 앱 단 방어를 적용할 수 있다"가
  성립한다. 즉 **accept 처리량 = 앱 단 방어가 작동할 수 있는 유입 속도의 상한.**
- 단, 지금 실험 자체에는 방어 로직이 없다. "접속 폭주 시 얼마나 빨리 받는가"만 잰다.

## 3. FloodClient 동작 (오늘 재작성 — ConnectEx + IOCP)

이전의 "논블로킹 connect + 바로 close" 설계(`client_experiment.md`)는 **폐기**됐다.
이 문서가 최신이다.

### 흐름
```
init          ConnectEx 포인터 로드 → IOCP 생성 → 워커/스탯 스레드 시작 → slotCnt개 postConnect
postConnect   소켓 생성 → bind(포트 0) → IOCP 등록 → ConnectEx. 실패 시 running 동안 재시도
workerLoop    GQCS로 완료 수신 → 성공 시 SO_UPDATE_CONNECT_CONTEXT 설정 → 성공/거절/기타 집계
              → closeReset(RST) → 같은 슬롯으로 postConnect 재등록
statLoop      1초마다 성공/거절/기타 tps + 동기실패누적 출력
```

### 집계 3분류 (측정 핵심)
- **성공**: ConnectEx 완료 성공 (연결 수립됨)
- **거절**: 완료 실패 중 `WSAECONNREFUSED`(10061) — backlog 넘침 또는 리슨 없음
- **기타**: 그 외 에러. 콘솔에 실제 err 코드 표시 → 포트 고갈 등 **클라 쪽 한계** 판별용
- **동기실패누적**: `postConnect`에서 ConnectEx가 동기적으로 즉시 실패한 횟수(재시도로 숨던 것)

### 핵심 구현 포인트 (면접 소재)
1. **ConnectEx는 WSAIoctl로 함수 포인터를 받아와야 한다.** 확장 함수라 ws2_32.dll에
   고정 심볼이 없고, 소켓이 실제로 연결된 공급자 구현을 런타임에 받아야 하기 때문.
2. **ConnectEx는 bind된 소켓을 요구한다.** 일반 connect와 다름. 포트 0으로 bind → OS가 할당.
3. **실패 완료의 에러는 `GetLastError`가 아니라 `WSAGetOverlappedResult`로 읽어야 한다.**
   GQCS 직후 GetLastError는 소켓 I/O에서 엉뚱한 Win32 코드(예: 52=ERROR_DUP_NAME)를 준다.
4. **ConnectEx 완료 소켓은 `SO_UPDATE_CONNECT_CONTEXT`를 설정해야 한다.** (아래 4절 참고)

## 4. 오늘 해결한 버그 — TIME_WAIT 포트 고갈 (중요)

### 증상
slotCnt=10000로 실행 시 성공 tps가 ~200으로 매우 낮고, 기타 버킷에 10048(WSAEADDRINUSE)
폭증.

### 원인
ConnectEx로 연결한 소켓은 `SO_UPDATE_CONNECT_CONTEXT`를 설정하기 전까지 "반쯤 연결된"
상태라, `closesocket`/`setsockopt(LINGER)` 등이 온전히 동작하지 않는다. 그래서 LINGER 0을
걸어도 **RST가 안 나가고 정상 종료(FIN) → TIME_WAIT**로 빠진다. TIME_WAIT가 포트를 수십 초
잡으면서 동적 포트가 고갈 → 10048 → throughput 붕괴.

### 해결
`workerLoop` 성공 완료 경로에서 closeReset 전에:
```cpp
setsockopt(ov->mSocket, SOL_SOCKET, SO_UPDATE_CONNECT_CONTEXT, nullptr, 0);
```
설정 후 LINGER 0이 제대로 RST로 끊어 TIME_WAIT 없이 포트 즉시 회수. **원인 확정됨.**

## 5. 측정 환경 세팅 (오늘 적용)

### 동적 포트 범위 확대 (관리자 권한 필요, 적용 완료)
```
netsh int ipv4 set dynamicport tcp start=10000 num=55000
```
확인: `netsh int ipv4 show dynamicport tcp` → 시작 10000, 55000개.
**다른 PC에서는 이 설정이 안 돼 있을 수 있으니 측정 전 확인/적용할 것.**
기본값은 49152 시작, 16384개.

### 측정은 루프백(127.0.0.1)으로
- 노트북 유선랜이 100Mbps(USB 동글)라 대역폭 한계가 서버보다 먼저 걸림. 그래서 루프백 사용.
- 루프백은 CPU 경쟁 변수가 있다. 서버+클라가 같은 코어를 나눠 씀 → 측정 시 각 CPU% 같이 기록.
  서버 CPU 100% 미만인데 TPS가 안 오르면 병목은 클라 쪽.
- CPU: Intel Core Ultra 5 125U (논리 14). 서버 워커 + 클라 워커 합계가 14를 넘지 않게.

## 7. 알아낸 사실 / 측정상 한계

1. **단일 IP 루프백에서 동시 연결 상한 = 동적 포트 수.** backlog에 쌓일 수 있는 연결도
   클라가 동시에 쥔 포트 수를 못 넘는다. 그래서 **slotCnt > backlog여야 backlog가 찰 수 있고**,
   그 slotCnt는 포트 수(현재 55000)에 묶인다. backlog 65535는 단일 IP로는 못 채운다.
   → 거절(10061)이 안 뜨면 "단일 IP로는 포트가 먼저 한계라 backlog를 못 채운다"가 결론.
   채우려면 목적지 IP 분산(127.0.0.2, 127.0.0.3 ...) 필요. (미구현)

2. **지금 클라는 closed-loop다.** 완료 오면 즉시 재발사 = 항상 최대 속도. 목표 TPS를 지정해
   쏘지 못한다. 그래서 "backlog가 정확히 몇 TPS에서 찬다"를 직접 못 잰다.
   → 필요하면 rate 제한(토큰 버킷, open-loop) 추가. 워커별 독립 버킷(rate/workerCnt) 권장.
   오늘은 유저 결정으로 보류.

3. **서버 Release 빌드가 `/O2` 아님.** `networkLibProject.vcxproj`에
   `<Optimization>Disabled</Optimization>`가 들어있음(유저가 디버깅용으로 넣음).
   정식 측정값을 낼 때는 /O2로 되돌려 재빌드할 것. 현재 수치는 참고용.
