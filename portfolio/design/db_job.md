# DB 같은 블록 작업을 워커 밖으로 빼기 (설계 논의)

- 시작: 2026-11-09, PC B
- 상태: 2-10 결정·구현(2026-11-11) - 작업 완료를 IOCP로 넘기는 API(2-9)를 빼고 세션 붙잡기 한 쌍만 남겼다. 라이브러리 빌드만 확인, 실행 시험은 새 에코 서버 뒤
- 배경: [워커 수 문제](worker_scaling.md) 4장 결정 - "블록되는 작업이 들어오면 워커 수를 다시 정한다". 게임 서버 컨텐츠는 DB 조회·저장처럼 블록되는 작업이 있다
- 읽는 법: `의견:` 줄에 적거나 본문을 직접 고치면 반영한다

## 1. 기본 구조 (합의한 것)

```text
워커: OnRecv → AcquireSession(id)    // 세션 카운트 +1, 작업을 큐에 넣고 바로 돌아감
DB 스레드: 큐에서 꺼내 동기 DB 호출  // 블록은 여기서만
       → PostJobComplete(id, job)    // PQCS로 IOCP에 넣음
워커: OnJobComplete(id, job)         // 컨텐츠 콜백, 끝나면 세션 카운트 -1
```

- 함수 이름은 2-9 구현 기준이다. 논의 중에는 `RequestJob`/`CompleteJob`으로 불렀다
- **2-10에서 바뀐다:** 작업 완료를 IOCP로 넘기지 않는다. 결과 처리는 컨텐츠가 정한 스레드에서 하고, 라이브러리는 `HoldSession`/`UnholdSession`만 연다

- **세션 카운트를 잡는 이유:** 외부 스레드 `SendPacket`(PQCS로 송신 완료를 넘김)과 같은 방식이다. "끝나지 않은 일 하나 = 카운트 하나"라 수명 규칙이 하나로 유지된다
- **막는 것:** 요청 중 세션이 해제·재사용되는 일. `OnRelease`는 반드시 `OnJobComplete`보다 나중에 온다
- **못 막는 것:** 연결이 끊기는 것 자체. 끊기면 결과를 `SendPacket`해도 실패하고, 해제만 작업이 끝날 때까지 기다린다
- **DB 스레드는 IOCP 워커가 아니다.** 동시 실행 수와 섞이지 않고, 워커는 계속 모아 보내기를 유지한다
- **역할:** 라이브러리는 카운트·전달만, DB 스레드와 쿼리는 컨텐츠가 갖는다

### 2-1. 작업이 끝나지 않을 때 (타임아웃)

DB가 멈추면 그 세션은 끊겼는데도 카운트가 안 내려가 슬롯을 계속 잡는다. `Stop`도 모든 슬롯을 기다리므로 같이 멈춘다.

| 안  | 방법                      | 장점          | 단점                   |
| --- | ------------------------- | ------------- | ---------------------- |
| A   | DB 드라이버 타임아웃만    | 변경 없음     | 드라이버·컨텐츠를 믿음 |
| B   | 라이브러리가 마감 시각 둠 | 반드시 내려감 | 늦게 끝난 작업 처리    |
| C   | 타임아웃 없음             | 단순          | 멈추면 복구 불가       |

- **B의 동작:** 기존 송신 정체 감시 스레드(1초 순회)가 마감이 지난 작업을 "시간 초과"로 완료 처리한다. 그 뒤 DB 스레드가 늦게 끝내면 버린다
  - 완료는 한 번만 일어나야 하므로 작업 상태를 CAS로 바꾼다(대기 → 완료). 먼저 바꾼 쪽만 PQCS한다
  - 작업 객체는 감시 스레드와 DB 스레드가 모두 손을 뗀 뒤에야 풀로 돌아가야 한다 - 세션 카운트와 같은 문제가 작업 객체에도 생긴다
- **추천: A만.** 처음에는 "A를 1차, B를 안전망"으로 제안했으나 아래 의견으로 바꿨다

### 2-2. 한 세션이 요청을 여러 개 걸 때

세션에는 수신·송신·해제용 OVERLAPPED가 하나씩뿐이다. 한 세션이 DB 요청을 동시에 여러 개 걸면 같은 OVERLAPPED로 PQCS가 겹친다.

| 안  | 방법                            | 실행 중 할당 | 넘칠 때           |
| --- | ------------------------------- | ------------ | ----------------- |
| A   | 요청마다 `New`로 작업 객체 할당 | 있음         | 메모리만큼        |
| B   | 서버 전체 작업 풀(시작 때 N개)  | 없음         | `RequestJob` 실패 |
| C   | 세션마다 작업 칸 몇 개 고정     | 없음         | 그 세션만 실패    |

- 작업 객체 = OVERLAPPED(종류 `Job`) + 세션 ID + 상태 + 컨텐츠 데이터
- **OVERLAPPED 수:** 세션은 지금처럼 3개(수신·송신·해제). DB 작업은 작업 객체 하나에 하나씩, 풀에서 꺼낸다. 한 세션이 동시에 쓰는 수 = 3 + 진행 중인 작업 수(세션당 상한까지)
- 풀 크기와 세션당 상한은 설정값(예: 최대 세션 수 × 2, 세션당 4)
- **추천: B.** "실행 중에 세션을 할당하지 않는다"는 지금 원칙과 같고, 풀 크기가 곧 작업 큐 한도가 된다(DB가 느려 요청이 무한정 쌓이는 문제도 같이 막는다). 한 세션이 풀을 독차지하는 것은 C처럼 세션당 상한을 하나 더 두어 막을 수 있다

### 2-3. `OnRelease` 안에서 저장할 때

로그아웃 저장은 보통 `OnRelease`에서 요청한다. 그때는 해제 표시가 서 있어 세션 카운트를 잡을 수 없다(`sessionLock` 실패).

| 안  | 방법                          | 결과    | 단점                  |
| --- | ----------------------------- | ------- | --------------------- |
| A   | 세션 없는 작업(`PostJob`)     | 받음    | 종료 때 따로 기다림   |
| B   | 보내고 잊기, 완료 안 돌려줌   | 안 받음 | 실패를 컨텐츠가 모름  |
| C   | 해제 전 "끊기는 중" 콜백 추가 | 받음    | 세션 수명 규칙이 바뀜 |

- **A:** 카운트를 잡지 않는다. 완료 콜백의 세션 ID는 무효 값이다

### 2-4. 라이브러리가 열어 줄 API

컨텐츠는 `Session`을 모르므로 수명을 다루는 장치를 라이브러리가 줘야 한다.

| 안  | 공개할 것                                  | 짝 맞추기  | 결과 처리 |
| --- | ------------------------------------------ | ---------- | --------- |
| A   | `RequestJob`·`CompleteJob`·`OnJobComplete` | 라이브러리 | 워커      |
| B   | 핸들 `SessionRef`(소멸자에서 반납)         | 소멸자     | 컨텐츠    |
| C   | ID 확인 + 카운트 올리기·내리기             | 컨텐츠     | 컨텐츠    |

- **A:** 카운트, PQCS, 워커에서의 콜백까지 라이브러리가 한다. 가장 안전하지만 변경이 가장 크다(작업 풀, 새 완료 종류)
- **B:** C 위에 RAII를 씌운 것. 반납을 빠뜨릴 수 없지만 결과를 워커로 돌려보내는 장치는 따로 필요하다
- **C:** 변경이 가장 작고 컨텐츠가 스레드 모델을 직접 고른다. 반납을 빠뜨리면 그 세션은 해제되지 않고 `Stop`이 끝나지 않는다
- 처음 추천은 A였다

- RAII(B)는 컨텐츠가 원하면 이 두 함수 위에 직접 감싼다

### 2-5. `Stop`과 남은 작업

워커가 끝난 뒤 DB 스레드가 PQCS하면 아무도 꺼내지 않는다. 반대로 작업이 끝나기를 무한정 기다리면 `Stop`이 멈춘다.

- **추천 순서:**
  1. 새 작업 받기를 멈춘다(`RequestJob`·`PostJob` 실패)
  2. 세션을 끊는다(지금 `Stop`과 같음)
  3. 남은 작업 수(서버 전체 카운터)가 0이 될 때까지 기다린다. 세션 작업은 세션 카운트로, 세션과 무관한 작업(2-3 A)은 이 카운터로만 잡힌다
  4. 그다음 워커를 끝낸다
- 3번에서 DB가 멈추면 `Stop`도 멈춘다. 2-1에서 B(마감 시각)를 넣으면 여기서도 끝이 보장된다. A만 쓴다면 "드라이버 타임아웃이 `Stop`의 상한"이 된다
- DB 스레드는 컨텐츠 소유이므로, 컨텐츠는 `Stop`이 끝난 뒤에 DB 스레드를 멈춘다. 외부 스레드 `SendPacket`의 "워커가 아닌 스레드는 `Stop` 전에 멈춘다"와 순서가 반대이니 문서에 따로 적어야 한다

### 2-6. 같은 계정의 작업 순서 (2-1 의견에서 나옴)

같은 유저가 다시 접속하면 **다른 슬롯의 새 세션**이 된다. 옛 세션을 잡아 두어도 새 세션은 바로 불러오기를 요청할 수 있어, 옛 세션의 저장보다 먼저 실행될 수 있다.

```text
옛 세션: 저장 요청 (DB 스레드 1에서 실행 중)
새 세션: 불러오기 요청 (DB 스레드 2가 바로 실행) → 저장 전 데이터를 읽음
```

- 세션 수명이 아니라 **같은 계정의 작업 순서** 문제다. 2-3의 로그아웃 저장(세션 카운트 없음)도 같다
- **추천: 같은 계정의 작업은 항상 같은 DB 스레드(같은 큐)로 보낸다**(예: 계정 ID % DB 스레드 수). 한 큐는 순서대로 실행되므로 "저장 → 불러오기"가 저절로 지켜진다
- 계정은 컨텐츠만 안다. 계정 키는 작업 객체에 담아 컨텐츠의 DB 스레드가 나눠 보내는 데만 쓰고, 라이브러리 API(2-4)에는 들어가지 않는다
- 대가: 한 계정의 작업이 몰리면 그 큐만 밀린다. 다른 계정은 다른 스레드라 영향이 작다

### 2-7. 나머지에 미치는 영향 (2-1 A, 2-2 B 기준)

- **2-3:** A(세션 없는 `PostJob`) 그대로. 순서는 2-6이 지킨다. "옛 세션이 풀렸다"가 "저장이 끝났다"는 뜻은 아니다
- **2-4:** A 그대로. 계정 키는 컨텐츠 안에서만 쓴다
- **2-5:** 순서 그대로. B가 빠져 "남은 작업이 0이 될 때까지"의 상한은 드라이버 타임아웃 × 큐에 쌓인 작업 수다. 저장을 잃지 않으려면 큐에 든 작업은 모두 실행해야 하므로 종료가 길어질 수 있고, 풀 크기가 최대치를 묶는다
- **새로 정할 것:** 풀이나 세션당 상한에 닿아 `RequestJob`이 실패하면 컨텐츠가 어떻게 할지(클라에 "잠시 후 다시" 응답 등)

### 2-8. 2-4를 C로 정한 뒤 달라지는 것

라이브러리는 세션 카운트 한 쌍만 열고, 작업 객체·큐·DB 스레드는 모두 컨텐츠가 갖는다.

- **2-2 (작업마다 OVERLAPPED):** 라이브러리가 PQCS를 하지 않으므로 라이브러리 쪽 작업 풀은 필요 없다. 작업 객체와 그 한도(풀, 세션당 상한)는 컨텐츠가 정한다
- **2-5 (`Stop`):** 세션 작업은 카운트를 잡고 있으므로 지금 `Stop`이 슬롯이 다 돌아올 때까지 기다리는 것만으로 끝까지 기다린다. 세션 없는 로그아웃 저장(2-3)은 라이브러리가 모르므로, 컨텐츠가 `Stop` 뒤에 자기 DB 큐를 비우고 DB 스레드를 멈춘다
- **남은 질문 - 결과를 워커로 돌려보낼 장치가 필요한가:** 결과를 DB 스레드에서 바로 처리하면 같은 세션의 `OnRecv`와 동시에 돌 수 있다(2-4 결정의 2번 규칙). 컨텐츠가 이것을 피하려면 워커에 일을 넘기는 장치가 필요한데, 지금 라이브러리는 IOCP를 열지 않는다. 데모 컨텐츠의 스레드 모델을 정할 때 함께 정한다

### 2-9. 라이브러리 마무리 - IOCount 기반 작업 API (사용자 결정, 2026-11-09)

2-8의 "결과를 워커로 돌려보낼 장치"를 라이브러리가 갖기로 했다. 수명은 IOCount 하나로 지키고, 작업 완료는 해제 작업처럼 PQCS로 워커에 넘긴다.

- **처음 구현은 사용자 의도와 달라 다시 짰다.** 처음에는 세션마다 작업 칸(OVERLAPPED)을 미리 만들고 비트마스크로 빈 칸을 고르게 했다. IOCount는 "몇이 잡고 있나"만 알고 "어느 OVERLAPPED가 비었나"는 몰라 칸을 고르는 장치가 따로 필요해진 것이다. 사용자 지적으로 OVERLAPPED를 컨텐츠의 작업 객체 안에 두는 방식으로 바꿨고, 칸·비트마스크·`JobTicket`은 없앴다

```text
워커 OnRecv
  └ AcquireSession(id)              ID 확인 + IOCount +1 + 걸린 작업 수 +1
  └ 작업 객체(JobOverlapped 상속)를 DB 스레드로
DB 스레드
  └ DB 호출 (블록)
  └ PostJobComplete(id, job)        걸린 작업 수 -1(음수면 오용) → 작업 객체의 OVERLAPPED로 PQCS
워커
  └ case eIoType::Job               OnJobComplete(id, job) → IOCount -1
```

| 항목      | 내용                                                        |
| --------- | ----------------------------------------------------------- |
| 설정      | `server.cfg` `jobPerSession`(기본 4, 1보다 작으면 1)        |
| 공개 형식 | 새 공개 헤더 `JobOverlapped.h` - `eIoType`, `JobOverlapped` |
| 공개 API  | `AcquireSession`, `PostJobComplete`, 가상 `OnJobComplete`   |
| 세션 상태 | 걸린 작업 수 `mJobCnt` 하나(Interlocked 증가·감소)          |

- **작업 객체:** 컨텐츠가 `JobOverlapped`를 상속해 만들고, `OnJobComplete`에서 `static_cast`로 되돌린다. `OnJobComplete`가 불리기 전에 지우면 안 된다 - 그때까지 IOCP 큐에 주소가 들어 있다
- **세션당 개수:** `AcquireSession`이 걸린 작업 수를 먼저 올리고 한도를 넘으면 되돌린다. 같은 세션에 시도가 겹치면 한도 아래에서도 잠깐 거절될 수 있다(헤더에 적음). 한도를 넘겨 허용하지는 않는다
- **동시 콜백 - ①(사용자 결정):** 라이브러리는 직렬화하지 않는다. "`OnJobComplete`는 같은 세션의 다른 콜백(`OnAccept`·`OnRecv`, 다른 `OnJobComplete`)과 동시에 불릴 수 있다"를 헤더 콜백 규칙에 적었다
- **끊는 중에도 `AcquireSession` 성공:** 끊긴 뒤의 저장을 막지 않는다. 대신 `OnJobComplete`에서 작업을 계속 이어 걸면 해제와 `Stop`이 끝나지 않으므로, 이어 걸기는 컨텐츠가 멈춘다(헤더에 적음)
- **오용 검사(릴리즈에서도 멈춤, `crashOnJobMisuse`):** `PostJobComplete`에서 ID가 범위 밖·세션이 바뀜·처리 전인 OVERLAPPED 재투입·`nullptr`, 그리고 걸린 작업 수를 내렸더니 음수(Post가 Acquire보다 많음)면 로그를 남기고 멈춘다. `OnJobComplete`를 재정의하지 않고 작업을 써도 멈춘다. 조용히 IOCount가 어긋나면 걸린 I/O가 있는 세션이 해제되기 때문이다
  - 처음에는 걸린 작업 수를 워커가 처리할 때 내려서, 같은 세션에 다른 작업이 걸려 있으면 Acquire 없는 Post·처리 뒤 두 번째 Post가 통과했다(cpp-reviewer, 2026-11-09). 사용자 제안으로 `PostJobComplete`에서 내리고 음수를 검사하게 바꿔(2026-11-10) API를 바꾸지 않고 잡는다. 단 드러나는 시점이 잘못한 호출이 아니라 그 세션의 다음 Post일 수 있다
- **진단:** `Stop`이 10초 넘게 끝나지 않으면 작업이 걸린 세션 수를 `stderr`에 한 번 출력. 해제 때 `mJobCnt`가 0이 아니면 디버그 Assert
- **시험용 컨텐츠:** 에코 서버 `echoJobMs`(기본 0 = 끔). 켜면 받은 패킷을 세션별로 쌓아 세션마다 작업 하나씩 가짜 DB 스레드 4개에 넘기고, `OnJobComplete`에서 에코한다. `OnRecv`와 `OnJobComplete`가 겹치므로 세션별 락을 쓴다(① 규칙대로)

**시험 (PC B, 2026-11-09, IOCount 기반 구현, 15초씩, 모두 세션 0·정상 종료)**

| 시험                                  | 결과                                |
| ------------------------------------- | ----------------------------------- |
| 작업 끔: 에코·비정상 헤더·받지 않음   | 정상 끊김 0, 비정상 6.9만, 넘침 192 |
| 작업 켬(1ms): 에코·비정상·받지 않음   | 정상 끊김 0, 받지 않는 클라 넘침 1  |
| 작업 켬, `jobPerSession = 1`          | 정상 끊김 0                         |
| Debug 서버, 작업 켬(비정상·받지 않음) | Assert 없음                         |
| 섞인 클라(채팅) 1회                   | 정상·하트비트 끊김 0                |

- 에코 클라는 바이트 단위로 검증하므로, 작업을 거치며 순서가 섞이거나 빠졌다면 바로 멈췄다
- 시험이 끝날 때 클라를 강제 종료해 작업이 걸린 채로 끊기는 경우를 지났다. 세션 0·정상 종료라 "작업이 끝난 뒤 해제"가 동작했다
- 작업 켬 처리량이 낮은 것(약 200MB 대 3500MB)은 작업마다 `Sleep`(1ms 이상)을 거치기 때문이다
- **시험하지 못한 것:** 세션당 개수 한도에 닿는 경우(시험 컨텐츠가 세션마다 하나만 건다), 오용 검사로 멈추는 경로, `Stop` 10초 진단 출력
- 섞인 클라 최대 지연이 58–77ms로 같은 날 앞선 측정(22–33ms)보다 컸다. 측정 중 Chrome·VS Code가 CPU를 쓰고 있었고 채팅 경로에 더한 것은 완료 분기의 case 하나라 원인으로 보지 않지만, 조용한 PC에서 수정 전 빌드와 번갈아 재야 확정된다

### 2-10. 작업 완료를 IOCP로 넘기지 않는다 - 세션 붙잡기만 라이브러리 (사용자 결정, 2026-11-11)

**문제:** 2-9는 작업 완료를 `PostJobComplete`로 라이브러리의 IOCP에 넣는다. IOCP에서 꺼낸 완료는 워커마다 따로 실행되므로, 같은 세션의 작업 완료가 **요청한 순서대로 처리된다는 보장이 없다**. DB 스레드가 하나여서 완료를 순서대로 넣어도 워커 둘이 연달아 꺼내면 뒤의 것이 먼저 끝날 수 있다.

```text
DB 스레드: 작업1 완료 PQCS → 작업2 완료 PQCS
워커 A:    작업1 꺼냄 ......(처리 중)...... 끝
워커 B:              작업2 꺼냄 → 끝      ← 작업2가 먼저 끝남
```

- 2-9를 만들 때 IOCP를 거치게 한 이유는 두 가지였다. ① 컨텐츠 로직이 항상 워커에서 돌게 하려고 ② 작업 동안 세션이 해제되지 않게 하려고
- ①은 "콜백 스레드 정책은 컨텐츠가 정한다"는 라이브러리 원칙과 맞지 않고, 그 대가가 위의 순서 문제다. 라이브러리에 꼭 필요한 것은 ②뿐이다

| 안  | 완료를 처리하는 곳          | 같은 세션 순서 | 라이브러리 변경 |
| --- | --------------------------- | -------------- | --------------- |
| 2-9 | IOCP → 아무 워커            | 보장 안 됨     | 지금 그대로     |
| B   | 컨텐츠가 정함(DB 스레드 등) | 컨텐츠가 보장  | 붙잡기 한 쌍만  |
| C   | IOCP → 세션별 완료 큐       | 보장           | 2-9 + 큐(큼)    |

결정: **B**(사용자, 2026-11-11). 세션당 작업 수 한도(`jobPerSession`)도 뺀다 - 대기 목록의 크기는 컨텐츠가 정한다

```cpp
// 워커 - OnRecv
if (HoldSession(id))                              // ID 확인 + IOCount +1
{
	dbQueue[idx % DB_THREAD_CNT].Push(job);       // 같은 세션은 항상 같은 DB 스레드 → 넣은 순서대로 처리
}

// DB 스레드 - 조회하고 결과 처리까지
const Result result = QueryDB(job);
SendPacket(job.SessionID, result);                // 아무 스레드에서나 부를 수 있다. 끊기 요청을 받은 세션이면 false
UnholdSession(job.SessionID);                     // IOCount -1, 0이 되면 해제 작업을 워커에 넘김
```

**세션을 지키는 방법 - IOCount 그대로.** 해제는 IOCount가 0이 될 때만 시작한다(`postReleasePQCS`가 0일 때 해제 표시를 세우고 해제 작업을 넣음). 붙잡은 동안은 1 이상이라 해제가 시작되지 않는다.

| 붙잡은 동안 일어나는 일        | 결과                         |
| ------------------------------ | ---------------------------- |
| 클라가 끊음, `Disconnect` 호출 | 끊기 요청만, 해제는 미뤄짐   |
| 소켓 닫기, `OnRelease`         | 마지막 `Unhold` 뒤에만       |
| 인덱스 재사용                  | 마지막 `Unhold` 뒤에만       |
| 해제가 시작된 세션에 `Hold`    | 해제 표시를 보고 실패        |
| 새 연결의 인덱스에 옛 ID로     | `findSession` ID 비교로 실패 |

- 끊기 요청이 서면 걸린 수신·송신은 취소돼 정리되고, 해제 작업만 IOCount가 0이 될 때까지 기다린다

- 그래서 **`OnRelease`는 그 세션의 모든 붙잡기가 풀린 뒤 한 번** 불린다. 로그아웃 저장을 `OnRelease`에서 시작해도 진행 중이던 작업과 겹치지 않는다(같은 계정의 새 세션과의 순서는 2-6)
- **`UnholdSession` 안:** 붙잡은 동안 인덱스는 재사용되지 않으므로 `findSession`을 다시 부르지 않고 인덱스로 찾아 `id == mID`를 확인한 뒤 `sessionUnLock`
- **오용 검사(릴리즈에서도 멈춤):** 세션마다 붙잡은 수(지금의 `mJobCnt`, 이름은 구현 때)를 남겨 `Unhold`가 `Hold`보다 많아 음수가 되거나 ID가 다르면 멈춘다. 조용히 넘어가면 걸린 I/O가 있는 세션이 해제된다
- **동시 실행:** 결과를 DB 스레드에서 처리하면 같은 세션의 `OnRecv`와 동시에 돈다. 함께 쓰는 컨텐츠 데이터는 컨텐츠가 락으로 지킨다(2-9의 `OnJobComplete`도 같았다)

**컨텐츠가 지킬 것 (라이브러리가 막지 못함)**
1. 성공한 `HoldSession`마다 `UnholdSession`을 정확히 한 번. 빠뜨리면 그 세션은 해제되지 않는다
2. `Stop` 전에 세션을 붙잡은 스레드(DB 스레드)를 멈춘다 - `Stop`은 모든 세션의 해제를 기다린다. 2-5의 "DB 스레드는 `Stop` 뒤에 멈춘다"는 세션을 붙잡지 않는 작업(로그아웃 저장)에만 해당한다

**빠지는 것:** `PostJobComplete`, 가상 `OnJobComplete`, 공개 헤더 `JobOverlapped.h`, `eIoType::Job` 분기, `jobPerSession` 설정, 2-9의 OVERLAPPED 재투입·`OnJobComplete` 미재정의 검사. 남는 것: `Stop` 10초 진단(붙잡힌 세션 수), 해제 때 붙잡은 수 0 확인

결정(사용자, 2026-11-11): **라이브러리에서 "DB"·"작업(Job)"을 없앤다.** `HoldSession`은 DB 전용이 아니라 "워커 밖 스레드가 세션 ID를 들고 일하는 동안 해제하지 마라"는 일반 기능이고, DB 큐·스레드·작업 객체·순서·결과 처리는 모두 컨텐츠가 책임진다

**구현(2026-11-11, PC A)**

| 항목      | 바뀐 뒤                                                   |
| --------- | --------------------------------------------------------- |
| 공개 API  | `HoldSession(id)`, `UnholdSession(id)` (`.def`도)         |
| 내부 형식 | `eIoType`(`Job` 삭제)·`MyOverlapped`를 `IoOverlapped.h`로 |
| 세션 상태 | `mJobCnt` → `mHoldCnt`(오용 확인용)                       |
| 설정      | `JobPerSession`·`jobPerSession` 삭제, `echoJobMs`도 삭제  |
| 오용 검사 | `crashOnHoldMisuse` - 범위 밖 ID·ID 다름·Unhold가 더 많음 |

- 확인: `NetworkLib.vcxproj` Release·Debug 빌드 경고 0, 규칙 위반 0. 서버 exe는 `main`이 없어 아직 링크되지 않으므로 실행 시험은 새 에코 서버를 만든 뒤
- 2-9 이전 절과 1장 그림은 기록으로 남긴다

## 3. 시험과 측정 (구현 뒤)

- **가짜 DB:** 정해진 시간만큼 `Sleep`하는 DB 스레드. 실제 DB 없이 블록을 재현한다
- **정확성:** 요청 중 끊기(해제가 완료 뒤에 오는가), 한 세션 여러 요청, 풀 고갈 시 거절, 로그아웃 저장, 작업이 남은 상태의 `Stop`, (B를 넣으면) 멈춘 작업의 마감 처리
- **측정:** 같은 블록 시간에서 "워커에서 직접 호출" 대 "DB 스레드로 넘김"의 처리량·지연. 그리고 [워커 수 문제](worker_scaling.md)에서 미룬 "블록이 있을 때 워커를 동시 실행 수보다 얼마나 많이 둘까"
