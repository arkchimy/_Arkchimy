# 워커가 아닌 스레드의 `SendPacket` (설계 논의)

- 시작: 2026-11-07, PC A
- 상태: 결정, 구현 완료(2026-11-07, E안). 처리량과 세션이 많은 방송은 재지 않았다(5장)
- 배경: 11-06에 "타이머·로직 스레드 없는 구조"로 보고 `SendPacket`을 워커 전용으로 막았다. 컨텐츠 스레드가 생길 때를 대비해 이 제한을 푸는 방법을 찾는다
- 읽는 법: `의견:` 줄에 적거나 본문을 직접 고치면 반영한다
- 시험 코드와 패치: `실험폴더/external_send_2026_11_07/`

---

## 1. 요약

**제한만 풀면 안 된다. 서버가 죽고, 막아도 그 세션의 송신과 해제가 영구히 멈춘다.** 원인은 외부 스레드에 모은 것을 보내 줄 `flushSends`가 없다는 점이다.

**E안으로 결정했다(사용자 제안).** 외부 스레드는 링에 넣은 뒤 `mSendLock` 안에서 `mbSendFlag`를 잡고, `mSendOv`를 0바이트 송신 완료로 PQCS에 넣는다. 워커는 평소의 `onSendComplete`로 처리하므로 새 I/O 종류와 멤버가 필요 없고, `WSASend`는 계속 워커에서만 일어난다. 메시지 유실·순서 오류 없이 동작했고 빈 PQCS도 없었다. 부하가 큰 조건의 처리량과 지연은 아직 재지 않았다.

## 2. 제한만 풀면 생기는 문제

| 번호 | 문제                      | 결과                     | 확인 |
| ---- | ------------------------- | ------------------------ | ---- |
| 1    | 카운터 번호 -1            | 서버 비정상 종료         | 시험 |
| 2    | 보낼 곳 없는 목록         | 메시지가 안 나감         | 시험 |
| 3    | `mbSendTarget`이 1로 고정 | 워커의 송신까지 막힘     | 시험 |
| 4    | 목록 몫 카운트 미반납     | 해제 안 됨, `Stop` 멈춤  | 시험 |
| 5    | 외부 스레드 쪽 목록       | `reserve` 없이 할당      | 코드 |
| 6    | 통계                      | 메시지 수가 적게 집계됨  | 코드 |
| 7    | 재시작과 경쟁             | `mSessions` 교체 중 접근 | 코드 |

- **1번:** `marshalToSendBuf`의 `mWorkerCounters[tWorkerIdx]`가 `tWorkerIdx = -1`로 배열 앞 메모리를 읽는다. 3회 모두 `0xC0000005`로 종료했다
- **2–4번은 한 원인이다:** 외부 스레드의 `addSendTarget`은 플래그를 1로 올리고 자기 목록에 넣지만, 그 목록을 비우는 `flushSends`가 없다
  - 플래그가 1이므로 워커도 "이미 누가 보낼 것"으로 보고 목록에 올리지 않는다. 그 세션은 아무도 보내지 않는다
  - 링이 차면 넘침으로 끊기지만 목록 몫 카운트가 남아 `OnRelease`가 오지 않고, `Stop`도 끝나지 않는다
- **7번:** `Start`가 `mSessions`를 교체하는 동안 외부 스레드가 `SendPacket`을 부르면 해제된 메모리를 읽을 수 있다. 어느 후보에서든 **컨텐츠 스레드는 `Stop` 전에 멈춘다**를 규칙으로 정해야 한다

**이미 안전한 부분:** 외부 스레드가 불러도 세션 ID 확인과 카운트로 ABA와 해제 경쟁은 막힌다. 카운트가 0이 되면 PQCS로 해제를 넘기므로 `OnRelease`가 컨텐츠 락 안에서 재진입하지도 않는다. 그래서 고칠 곳은 **보내는 경로와 통계**다.

| --- | ------------------ | -------------- | ------ | -------- |
| A   | 그 자리에서 보냄   | 외부 스레드    | 약함   | 없음     |
| B   | PQCS로 워커에 맡김 | 워커           | 유지   | 없음     |
| C   | 구간을 직접 지정   | 외부 스레드    | 지정함 | 있음     |

### A. 그 자리에서 `postSend`

11-06 이전과 같은 방식이다. 코드가 가장 작다.

- 메시지마다 `WSASend`에 가까워진다. 시험에서 `WSASend` 1번에 약 2개만 실렸다
- 방 락을 잡고 방송하면 **락 안에서 시스템 콜**이 일어난다. "소켓 송신은 어느 락 안에서도 부르지 않는다"(`lock_logic.md`)가 깨진다
- 즉시 완료 반복(`postSend`의 `while`)에 외부 스레드가 묶여 컨텐츠 처리가 밀릴 수 있다

### B. PQCS로 워커에 맡기기

```cpp
// addSendTarget - 플래그를 처음 올린 스레드만 여기까지 온다
InterlockedIncrement(&session.mIoCount);
if (tWorkerIdx < 0)
{
	// 세션당 하나만 큐에 있으므로(플래그가 보장) OVERLAPPED 하나로 충분하다
	PostQueuedCompletionStatus(mIOCP, 0, 세션, &session.mSendFlushOv);
	return;
}
tSendTargets.push_back(&session);

// handleCompletion - 목록 소유권만 워커로 넘긴다. 플래그와 카운트는 이미 잡혀 있다
case eIoType::SendFlush:
	tSendTargets.push_back(session); // 같은 묶음의 다른 송신과 함께 묶음 끝에서 나간다
	break;
```

- `WSASend`는 계속 워커에서만 일어난다. "락 안에서 시스템 콜 없음"과 `postSend`의 "워커에서만 불린다" 전제가 그대로다
- 큐에 들어 있는 동안 들어온 메시지는 플래그를 보고 링에만 쌓여 함께 나간다. 시험에서 `WSASend` 1번에 48–50개가 실렸다
- 컨텐츠 코드는 바뀌지 않는다
- 단점 1: 외부 스레드가 받는 사람마다 PQCS를 부른다. 방 락 안에서 방송하면 락 안에서 시스템 콜 N번이다. `WSASend`보다 가벼울 것으로 보지만 재지 않았다
- 단점 2: 맡긴 항목이 큐에서 기다리는 동안에는 워커가 같은 세션에 넣은 메시지도 같이 기다린다. 큐가 길면 링이 더 차서 넘침(README_ERRORS 2-7)이 늘 수 있다

### C. 컨텐츠가 구간을 지정

```cpp
{
	SendScope scope(server);  // 끝날 때 이 스레드의 목록을 보낸다
	server.SendPacket(...);
}
```

- 틱 단위로 잘 모을 수 있고 락 밖에서 보내도록 짤 수 있다
- 구간을 빼먹으면 2번 문제가 다시 생기므로 그 경우 처리가 따로 필요하다. API가 늘고 `WSASend` 비용을 컨텐츠 스레드가 낸다
- 시험하지 않았다. B로 부족할 때 B 위에 얹을 수 있다(구간 끝에서 PQCS 한 번으로 목록을 넘기기)

### D. 전용 송신 스레드

- 큐와 스레드가 늘고 주기만큼 지연이 생긴다. 10-31 논의에서 같은 이유로 채택하지 않았다
- 시험하지 않았다

### E. 플래그를 잡고 `Send` 완료로 넣기 (채택)

```cpp
// marshalToSendBuf 끝 - 외부 스레드면 워커에게 맡긴다
if (tWorkerIdx < 0)
{
	requestSendToWorker(session);
	return true;
}

void NetworkLib::requestSendToWorker(Session& session)
{
	{
		std::lock_guard<std::mutex> sendLock(session.mSendLock);
		if (session.mbSendFlag || session.mSendBuf.GetUseSize() == 0)
		{
			return;
		}
		session.mbSendFlag = true;
		session.mWsaSendQPC = getNowQPC();
	}
	InterlockedIncrement(&session.mIoCount); // onSendComplete가 반납
	session.mSendOv.Type = eIoType::Send;    // 앞에서 OVERLAPPED를 0으로 채운다
	PostQueuedCompletionStatus(mIOCP, 0, 세션, &session.mSendOv);
}
```

- 플래그, 카운트, `mSendOv`를 진짜 `WSASend`와 똑같이 잡으므로 워커 코드가 바뀌지 않는다. `mbSendFlag`의 뜻도 "`mSendOv`를 쓰는 중"으로 유지된다
- 앞의 안들과 달리 새 지역 변수나 `SendFlush` 없이 함수 하나로 끝나고, 빈 PQCS도 없다
- 자세한 근거와 대가는 4장 끝 "플래그를 잡고 `Send` 완료로 넣기"

결정: **E안** (사용자, 2026-11-07). B안은 빈 PQCS를 받아들이면 단순하지만 새 I/O 종류와 멤버가 필요하고, A안은 방 락 안에서 시스템 콜이 일어나며, C·D안은 API나 스레드가 늘어 채택하지 않았다

## 4. 시험 결과

서버와 클라가 한 프로세스에 있는 작은 시험이다. 외부 스레드 2개가 각각 1만 개(10B)를 50개씩 1ms 간격으로 보내는 동안, 클라가 에코 200개를 보내 워커 송신과 섞는다. 워커 2, GQCSEx + skip + `mergeSends`, 임시 복사본 `/O2`, PC A.

| 변형          | 회  | 단건 | 에코 | 대량 성공 | 해제 | `Stop` |
| ------------- | --- | ---- | ---- | --------- | ---- | ------ |
| 제한만 제거   | 3   | 종료 | -    | -         | -    | -      |
| + 카운터 막음 | 2   | 0    | 0    | 3,242     | 0    | 멈춤   |
| A             | 5   | 1    | 1    | 20,000    | 1    | 정상   |
| B             | 5   | 1    | 1    | 20,000    | 1    | 정상   |

- 단건: 외부 스레드가 보낸 첫 메시지 도착 수. 에코: 그 직후 워커가 보낸 에코 도착 수
- A와 B는 10회 모두 메시지 20,001개와 에코 201개가 전부 도착했고, 스레드별 순번 오류가 0이었다
- `+ 카운터 막음`의 대량 3,242는 링 32KB가 찰 때까지 넣은 수이고, 나머지 16,758개는 실패했다

대량 구간의 `WSASend` 횟수(메시지 20,200개, 에코 포함):

| 안  | `WSASend`     | 1번당 메시지 |
| --- | ------------- | ------------ |
| A   | 10,029–10,300 | 약 2         |
| B   | 404–421       | 48–50        |

**보낼 데이터가 없는 PQCS** (사용자 지적)

외부 스레드가 PQCS를 부른 뒤 워커가 항목을 꺼내기 전에, 다른 워커의 `postSend`가 그 메시지까지 보낼 수 있다. 이 경우 `postSend`는 빈 링을 보고 돌아오고, 플래그와 카운트도 정상으로 내려가 **동작은 맞다.** 낭비는 PQCS와 큐 꺼내기, 락 확인 한 번씩이고 `WSASend`는 없다.

항목을 꺼낸 시점의 상태를 세어 봤다(3회 범위). "넣을 때 확인"은 메시지를 넣을 때 `mbSendFlag`가 켜져 있으면 PQCS를 부르지 않는 변형이다.

| 조건        | 변형         | PQCS    | 링 빔 | 송신 중 |
| ----------- | ------------ | ------- | ----- | ------- |
| 기본        | B            | 249–258 | 0–1   | 44–55   |
| 기본        | 넣을 때 확인 | 211–229 | 0–1   | 10–15   |
| 송신 버퍼 0 | B            | 284–333 | 0     | 84–133  |
| 송신 버퍼 0 | 넣을 때 확인 | 214–236 | 0     | 13–24   |

- 링이 빈 경우는 드물고, 많은 쪽은 "아직 송신 중"인 경우다. 이때도 완료 쪽이 이어서 보내므로 그 PQCS는 할 일이 없다
- "넣을 때 확인"은 PQCS를 중앙값 기준 약 16%(기본), 약 30%(송신 버퍼 0) 줄였다. 12회 모두 메시지가 전부 도착했고 순서 오류가 없었다
  - 안전한 이유: 같은 락 안에서 플래그가 켜진 것을 봤으므로, 그 송신의 마무리가 나중에 락을 잡고 넣은 메시지까지 읽는다. 송신이 실패하면 어차피 세션을 끊는다
- 이 변형은 값을 확인만 하므로 사용자가 지적한 순서(플래그를 내린 직후 외부 스레드가 넣고, 워커의 `postSend`가 그 메시지까지 보냄)에서는 빈 PQCS가 남는다. 아래 "송신 권리 선점"은 이 경우까지 없앤다
- 세션 1개, 시험 패턴 1개의 값이다. 세션이 많은 방송에서 비율이 어떤지는 모른다. 항목을 꺼낸 시점 기준이라, 묶음 끝에서 실제로 빈 경우는 이보다 많을 수 있다

**송신 권리 선점** (사용자 제안에서 나옴: 플래그를 확인하고 PQCS를 보내기)

외부 스레드가 메시지를 넣는 같은 `mSendLock` 안에서 `mbSendFlag`를 직접 올린다. 올리는 데 성공했을 때만 락 밖에서 PQCS를 부르고, 워커는 항목을 꺼내면 플래그를 내린 뒤 평소처럼 `postSend`를 부른다.

```cpp
// marshalToSendBuf - mSendLock 안
bPushed = true;
if (tWorkerIdx < 0 && !session.mbSendFlag)
{
	session.mbSendFlag = true;
	session.mWsaSendQPC = getNowQPC();
	bClaimed = true;  // 락 밖에서 카운트 +1, PQCS
}

// handleCompletion
case eIoType::SendFlush:
	{
		std::lock_guard<std::mutex> sendLock(session->mSendLock);
		session->mbSendFlag = false;
	}
	postSend(*session);
	decIoCount(*session);
	break;
```

- **빈 PQCS가 구조적으로 없다.** 플래그를 가진 쪽만 링을 읽는다. 외부 스레드가 플래그를 올린 순간 링에는 자기 메시지가 있고, 워커가 항목을 꺼낼 때까지 아무도 그 메시지를 꺼내지 못한다
- `mbSendTarget`을 외부 경로에서 쓰지 않으므로 외부 스레드가 목록 몫을 다루지 않는다
- 플래그가 이미 켜져 있으면 지금 송신의 완료 또는 큐의 항목이 이어서 보내므로 PQCS가 필요 없다
- **CAS는 필요 없다.** `mbSendFlag`는 이미 `mSendLock`이 보호하고, 메시지를 넣을 때 그 락을 잡고 있다
- **PQCS를 락 안에서 부를 이유도 없다.** 플래그만 락 안에서 올리면 순서가 보장된다. 시스템 콜을 락 안에 넣으면 같은 세션의 다른 스레드만 더 기다린다

시험(기본 5회, 송신 버퍼 0 5회): 링이 빈 경우 10회 모두 0, PQCS 204–216, `WSASend` 387–417, 메시지 전부 도착, 순서 오류 0, 해제와 `Stop` 정상.

대가:

- `mbSendFlag`의 뜻이 "송신 중"에서 "송신 중 또는 송신 예정"으로 넓어진다. 플래그를 보는 곳(송신 정체 감시)을 함께 따져야 한다
- 정체 감시는 큐에서 기다리는 시간도 송신 대기로 센다. 기다림이 기준(10초)을 넘을 만큼 서버가 밀렸을 때 정상 클라를 끊을 수 있다
- 항목이 큐에 있는 동안 완료나 워커의 `postSend`도 그 세션을 보내지 못한다. 큐가 길면 링이 더 찰 수 있다(넘침 영향은 재지 않음)
- 항목을 꺼내는 즉시 보내므로, 같은 묶음의 다른 메시지와 묶음 끝까지 모으지는 않는다

**플래그를 잡고 `Send` 완료로 넣기** (사용자 제안)

외부 스레드가 `mbSendFlag`를 잡은 뒤 `mSendOv`를 0바이트 `Send` 완료처럼 PQCS로 넣는다. 워커는 평소의 `onSendComplete`로 처리한다. 플래그, 카운트, `mSendOv`를 진짜 `WSASend`와 똑같이 잡으므로 `SendFlush`와 `mSendFlushOv`가 필요 없다.

- 플래그를 잡을 때 링이 비었는지 함께 보므로 빈 PQCS가 없다. 잡은 뒤에는 아무도 링을 읽지 못한다
- 플래그는 기존 `mSendLock` 안에서 잡는다. CAS로 락 밖에서 잡으면 `postSend`의 확인과 대입 사이에 끼어들어 `mSendOv`가 두 곳에서 쓰이고, `mWsaSendQPC`가 옛 값인 순간이 생겨 정체 감시가 오판한다. CAS 변형은 시험하지 않았다
- 시험(기본 5회, 송신 버퍼 0 5회): 링이 빈 경우 0, PQCS 205–224, `WSASend` 396–422, 메시지 전부 도착, 순서 오류 0, 해제와 `Stop` 정상
- 대가: 큐 대기가 정체 감시 시간에 포함된다. 워커가 꺼내는 즉시 보내 묶음 끝까지 모으지 않는다. 0바이트 완료가 `SendCompleteCnt`에 잡히지 않도록 `completeSend`의 통계를 건너뛰어야 한다

**이 시험으로 알 수 없는 것**

- 처리량과 지연. 50개씩 보내는 시험 패턴이라 `WSASend` 횟수는 방향만 보여 준다
- 세션이 많은 방송, 부하가 포화인 조건, 끊기와 경쟁하는 조건, Debug 빌드
- PQCS 호출 비용, 방 락 안에서 PQCS를 부를 때의 락 보유 시간
