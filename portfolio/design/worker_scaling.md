# 워커를 늘리면 처리량이 줄어드는 문제 (설계 논의)

- 시작: 2026-11-09, PC B
- 상태: 결정(2026-11-09) - 원인 확인(3-1장), 설정 기능만 추가하고 기본값 유지(4장)
- 배경: README_ERRORS 4-10. PC B에서 채팅 처리량이 워커 2에서 가장 높고 워커를 늘리면 떨어진다. README 한계 절에 "원인을 확정하지 못했다"로 남아 있다

## 1. 요약

**가설: 워커가 남으면 완료가 쌓이기 전에 꺼내져, 한 번에 모으는 메시지가 줄고 `WSASend`가 잦아진다.** 모아 보내기의 창은 "워커가 한 묶음을 처리하는 시간"이다. 워커가 바쁘면 그동안 완료가 쌓여 창이 넓어지고, 워커가 쉬면 완료 하나가 오자마자 쉬던 워커가 꺼내 창이 좁아진다. `WSASend` 1번 비용(약 7us)은 실린 메시지 수와 거의 상관없으므로, 덜 모으면 메시지당 비용이 그만큼 오른다.

**먼저 가설을 확인하고 고친다.** 확인 실험 3개(3장)를 추천하고, 고칠 후보는 4장에 있다. 추천은 IOCP 동시 실행 수를 워커 수와 따로 정하는 B안이지만, 실험 결과를 본 뒤 정한다.

## 2. 현상과 근거

PC B(i5-8600), `/O2`, 채팅 방 16, 기본값(GQCSEx 64 + skip + 묶음 단위), 2026-11-05 3회 중앙값([결과](../../실험폴더/portfolio_o2_2026_11_05/결과.md)).

| 워커 | 전달/s | `WSASend`당 메시지 | 꺼낸 완료 | 서버 코어 |
| ---- | ------ | ------------------ | --------- | --------- |
| 1    | 709만  | 111                | 64        | 1.03/1    |
| 2    | 993만  | 59                 | 20        | 1.97/2    |
| 3    | 928만  | 38                 | 4.3       | 2.51/3    |
| 4    | 846만  | 29                 | 2.5       | 2.90/4    |
| 5    | 816만  | 26                 | 1.9       | 3.15/5    |

- **워커 2부터 서버가 포화가 아니게 된다.** 워커 3 이상은 코어를 다 쓰지 않는데, 꺼낸 완료와 `WSASend`당 메시지가 함께 줄고 처리량도 준다.
- **비용 분해(2026-11-09, [architecture 7장](../architecture.md#7-비용-메시지-1건-전달에-쓰는-시간)):** 워커 4는 일하는 시간의 72%가 `WSASend`이고 워커 시간의 27%는 대기다. `OnRecv`는 워커 수와 상관없이 전달 1건에 약 60–69ns다.

**가설을 지지하는 근거**

| 근거                                                  | 어디서            |
| ----------------------------------------------------- | ----------------- |
| 워커가 늘수록 꺼낸 완료·모으기가 함께 줆              | 위 표             |
| 프로파일러로 조금 느리게 하면 더 모으고 더 빠름       | 비용 분해, 워커 2 |
| PC A는 워커 4도 포화라 꺼낸 완료 62, 워커 4가 더 빠름 | 4-10 PC A 재현    |
| 묶음 상한을 강제로 줄이면 처리량이 같이 떨어짐        | 4-10, PC A        |

- 프로파일러: 워커 2에서 끈 5회는 `WSASend`당 56–93개·1031만–1148만/s, 켠 5회는 64–256개·1090만–1768만/s.
- PC A는 CPU가 느려 워커 4까지 포화였고, 같은 코드에서 워커 4(1467만)가 워커 2(1014만)보다 빨랐다. "워커 수"가 아니라 "포화 여부"가 갈림길이라는 뜻이다.

**아직 없는 근거**

- PC B 워커 4에서 "덜 모아서 느리다"를 직접 바꿔 본 실험이 없다. 지금까지는 상관관계와 다른 PC·다른 조건의 결과다.
- **워커가 27% 쉬는데 왜 처리량이 오르지 않는지** 설명이 비어 있다. closed-loop 부하라 처리량 = 동시에 오가는 메시지 ÷ 왕복 시간인데, 서버가 남는다면 왕복 시간을 늘리는 곳이 따로 있다. 후보는 PC 전체 CPU(6코어를 서버·클라·커널 루프백 처리가 나눠 씀)다. `WSASend`가 잦으면 클라가 받는 조각도 많아져 클라와 커널의 일이 늘어난다. PC 전체 CPU 사용률은 아직 기록하지 않았다.

## 3. 확인 실험 (추천: E1 + E3)

| 실험 | 방법 (워커 4 기준)          | 가설이 맞다면             |
| ---- | --------------------------- | ------------------------- |
| E1   | IOCP 동시 실행 수 2 / 4 / 6 | 2일 때 워커 2와 비슷      |
| E2   | 묶음마다 짧은 스핀 주입     | 모으기와 처리량이 오름    |
| E3   | 워커 1–6, PC 전체 CPU 기록  | 워커 3 이상에서 PC가 포화 |

- **E1 - IOCP 동시 실행 수:** `CreateIoCompletionPort`의 마지막 인자는 "동시에 깨어 일할 수 있는 스레드 수"다. 지금은 0(=코어 수 6)이라 워커 4개가 모두 동시에 깨어난다. 이 값을 2로 주면 워커가 4개여도 IOCP가 둘만 깨운다. 워커 2와 비슷해지면 "동시에 꺼내는 워커 수"가 원인이라는 직접 근거가 된다. 시험용으로 `server.cfg` 키 하나와 한 줄만 바꾼다(가장 싸다)
- **E2 - 지연 주입:** 임시 빌드에서 묶음 처리 뒤 GQCSEx를 부르기 전에 QPC를 보며 수십 us를 스핀한다(4장 C안과 달리 고치려는 것이 아니라 원인 확인용, 끝나면 버린다). 프로파일러가 우연히 보여 준 효과를 PC B 워커 4에서 의도적으로 재현하는 것이다. E1이 명확하면 생략해도 된다. 임시 빌드가 필요하다
- **E3 - PC 전체 CPU:** 2장의 빈칸(워커가 쉬는데 처리량이 안 오르는 이유)을 채운다. `load_sweep`에 `_Total` CPU 열을 더한다
- 조건: 채팅 방 16, 기본값, 15초, 3회, 같은 실행 안에서 번갈아. 측정 전 CPU 상위 프로세스 확인, Chrome·Visual Studio 닫기

**E3 - 워커가 쉬는데 처리량이 오르지 않는 이유: PC 전체가 거의 포화다.**

| 워커 | PC 전체 CPU | 서버 커널 비율 | 클라 코어 | 지연 p50 |
| ---- | ----------- | -------------- | --------- | -------- |
| 1    | 41%         | 60%            | 0.80      | 9.2ms    |

| 3    | 89%         | 70%            | 1.67      | 7.0ms    |

- 워커 2에서 이미 PC 전체 CPU가 84%다. 워커를 늘리면 서버가 덜 모아 `WSASend`와 커널 루프백 처리가 늘고(서버 커널 비율 61% → 73%), 서버가 코어를 더 차지한다(1.95 → 3.22). 같은 PC의 클라는 코어를 덜 받아(1.95 → 1.28) 덜 보내고, 왕복이 길어진다(6.3 → 8.8ms)
- 즉 워커 4의 "쉬는 27%"는 서버 입장에서 일감이 없는 시간이고, 그 사이 PC의 나머지 코어는 클라와 커널이 쓰고 있다
- 이 효과의 크기는 서버와 클라가 한 PC를 나눠 쓰는 루프백 측정이라 커진 것이다. 서버 단독이라면 클라 몫을 빼앗는 손해는 없지만, 메시지당 CPU가 늘어나는 것은 같다

## 4. 고칠 후보

| 안  | 방법                          | 지연   | 남는 문제               |
| --- | ----------------------------- | ------ | ----------------------- |
| A   | 워커 2 유지 + 문서로 안내     | 그대로 | PC·부하마다 다시 맞춤   |
| B   | IOCP 동시 실행 수를 따로 설정 | 그대로 | 값을 정하는 기준        |
| C   | 묶음이 작으면 잠깐 기다림     | 늘어남 | 타이머 없는 구조와 충돌 |
| D   | 깨어 있는 워커 수 자동 조절   | 그대로 | 복잡, 흔들림            |

- **A:** 지금 상태를 문서로만 정리한다. 원인이 확인되면 "워커는 포화에 맞춰 정한다"는 근거 있는 안내가 된다
- **B (추천, E1 결과 전제):** 워커 스레드 수와 IOCP 동시 실행 수를 따로 둔다. 동시 실행 수를 워커 수보다 작게 두는 것은 IOCP의 원래 쓰임새다 - 컨텐츠가 잠깐 막혀도(락, 디스크) 다른 워커가 대신 깨어날 여유를 남긴다. 코드는 `NetConfig` 항목 하나와 `CreateIoCompletionPort` 인자 하나다. 남는 것은 "값을 몇으로 하나"인데, 포화에 맞춘다는 점에서는 A와 같은 문제다
- **B와 D의 차이:** B는 `CreateIoCompletionPort`의 마지막 인자(`NumberOfConcurrentThreads`)를 설정값으로 받아 시작할 때 한 번 정한다. D는 실행 중에 부하를 보고 깨어 있는 워커 수를 바꾼다. 이 인자는 IOCP를 만들 때만 정할 수 있어서, D는 워커를 이벤트로 재우고 깨우는 장치를 따로 만들어야 한다
- **C:** "모을 만큼 모일 때까지 기다리기"(Nagle과 비슷). 묶음이 작으면 바로 보내지 않고 GQCSEx를 대기 시간 T로 한 번 더 불러 완료를 더 합친 뒤 보낸다. 문제는 T다
  - GQCSEx·`Sleep`의 대기는 ms 단위이고, 기본 타이머 해상도(약 15.6ms)로 반올림된다. `timeBeginPeriod(1)`을 써도 최소 1ms라, 왕복 6–8ms인 지금 지연이 크게 는다
  - us 단위로 기다리려면 QPC를 보며 스핀해야 해서 그동안 CPU를 태운다
  - 2026-11-06에 정한 "타이머·로직 스레드 없는 구조"와도 부딪친다
- **D:** 효과보다 복잡도가 크다. 비교용으로만 적었다
- 송신 전담 스레드는 후보에서 뺐다(사용자 결정, 2026-11-09 - 2026-10-31에도 채택하지 않았다)

의견:
결정: A + B의 설정 기능(사용자, 2026-11-09). `iocpConcurrency` 설정은 추가하되 기본값은 지금처럼 워커 2, 동시 실행 수 0(코어 수)으로 둔다. 동시 실행 수 2는 이 PC에서 잰 값이라 환경마다 다시 재야 하고, 워커를 동시 실행 수보다 많이 둘 이유(블록되는 컨텐츠)가 아직 없다. 블록되는 작업(DB 등)이 들어오면 블록을 넣는 시험으로 워커 수를 정한다

## 5. 사례로 쓸 때

결과가 가설대로 나오면 "워커를 늘렸더니 느려졌다 → 모으는 창이 워커의 바쁨에 달려 있었다 → IOCP 동시 실행 수로 확인하고 고쳤다"는 흐름이 된다. 앞 사례들("우연에 기대던 모아 보내기를 설계로")의 연장이면서, IOCP의 동시 실행 수라는 면접에서 자주 묻는 주제를 측정으로 다룬다. 가설이 틀리면 그 과정도 4-10과 함께 기록한다.
