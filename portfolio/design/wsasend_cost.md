# WSASend 비용 - 동기 복사 vs 제로카피, WSABUF 개수와 길이 (2026-11-02)

## 요약

**WSASend 비용 = 호출마다 드는 고정 몫(약 9.5us) + 바이트 몫(약 0.19ns/B).**
 우리가 보내는 크기(수 KB 이하)에서는 고정 몫이 대부분이다 - 512B(메시지 16개)에서 약 97%,
 5KB에서 약 85%. 32KB가 되면 바이트 몫이 6.2us로 커져 고정 몫이 약 60%로 내려간다
- 모아 보내기는 바이트 몫은 그대로 두고 **고정 몫을 내는 횟수**를 줄인다

**WSABUF 개수 비용은 모드에 따라 70배 차이가 난다.** 
동기 복사 9ns/개, 제로카피 360-630ns/개
- **제로카피의 조각당 비용은 페이지 수가 아니라 조각(WSABUF) 수에 붙는다.** 페이지를 늘려도, 미리 VirtualLock을 걸어도 그대로다(D1-D3)
- **루프백에서 제로카피는 측정한 모든 점에서 느렸다.** 바이트당 비용은 16% 줄지만 고정 비용과 조각 비용이 더 크다. 조각 하나가 약 21KB를 넘어야 이긴다
- 설계(`send_queue.md`)에 주는 뜻: 지금 구조(동기 복사, 세션별 링, WSABUF 1-2개)가 맞다

## 1. 동기 복사와 제로카피

TCP 소켓마다 커널이 관리하는 **송신 버퍼**(`SO_SNDBUF`)가 있다. 그 크기를 0으로 하면 커널이 복사해 둘 곳이 없어 사용자 버퍼를 직접 쓴다 - Windows의 제로카피

```
동기 복사:  [내 버퍼] --복사(1)--> [커널 송신 버퍼] --(2) 루프백 전달--> [받는 소켓]
            WSASend는 (1)이 끝나면 즉시 성공 - 커널이 자기 복사본으로 보내고 재전송에 대비해 보관

제로카피:   [내 버퍼] ------------------------------(2) 루프백 전달--> [받는 소켓]
            커널이 내 버퍼의 페이지를 잠그고 직접 씀 - WSASend는 대기, 커널이 다 쓰면 완료 통지
```

|                   | 동기 복사 (송신 버퍼 기본값) | 제로카피 (SO_SNDBUF = 0)                  |
|-------------------|------------------------------|-------------------------------------------|
| 내 데이터         | 커널 송신 버퍼로 복사        | 복사 안 함, 내 버퍼를 빌려 씀             |
| WSASend 반환      | 즉시 성공(0)                 | 대기(WSA_IO_PENDING), 완료 통지로 끝남    |
| 내 버퍼 다시 쓰기 | 바로 가능                    | 완료 통지 뒤에만                          |
| 추가로 드는 일    | 복사(바이트당)               | 조각마다 주소 목록(MDL)과 잠금, 완료 처리 |
| 우리 라이브러리   | 이쪽(WSABUF 1-2개)           | -                                         |

- 루프백에서는 (2) 루프백 전달도 송신자의 WSASend 안에서 일어나는 것으로 보인다(고정 비용이 10us로 큰 것이 근거). 제로카피가 없애는 건 (1)뿐이다
- (2)는 받는 소켓의 **수신 버퍼**로 넘기는 일이라 송신 버퍼를 0으로 해도 남는다

## 2. 측정 방법

- 도구: `tools/wsasend_bench/wsasend_bench.cpp`(`build.bat`로 빌드). 라이브러리와 별개
- 루프백 TCP 연결 1개, 받는 쪽 스레드는 `recv`로 비우기만. 송신은 한 번에 1개만 걸어 둔다(라이브러리와 같은 조건), `TCP_NODELAY`
- 측정값: 동기 복사는 WSASend 반환까지(모든 점에서 즉시 성공 100%, 완료 통지 skip), 제로카피는 WSASend 반환 + 완료를 GQCS로 받을 때까지(모든 점에서 대기 100%)
- 시험 묶음
  - A: 4096B를 WSABUF 1-512개로 나눔 - 개수만 변화
  - B: WSABUF 1개로 32B-64KB - 길이만 변화
  - C: 34B 메시지 n개를 WSABUF n개로 vs 이어 붙여 1개로 - 설계 비교(메시지별 버퍼 vs 링)
  - D1-D3: 페이지 배치와 VirtualLock - 제로카피 비용의 원인 좁히기(5장)
- 조각은 서로 64바이트 경계로 떨어뜨림(메시지마다 따로 있는 버퍼처럼). D는 데이터 영역을 페이지 경계에서 시작(`VirtualAlloc`)
- 점마다 10000번(앞 10%는 버림)의 중앙값, 3회, 회차마다 모드 순서를 바꿈. 같은 점의 3회 값 차이는 대부분 1% 안
- 환경: i5-8600(6코어), 루프백, QPC 해상도 100ns
- 원본: `실험폴더/WSASend_bufcnt_2026_11_02/` - `raw_runs.csv`(A-C), `median.csv`(A-C 3회 중앙값), `page_runs.csv`(D)

### A. 4096B를 WSABUF 몇 개로 나누나

|-------------|-----------|----------|--------------|
| 1           | 4096B     | 11.2     | 14.2         |
| 8           | 512B      | 11.1     | 16.7         |

| 64          | 64B       | 11.8     | 57.3         |
| 512         | 8B        | 15.7     | 351.1        |

- 동기 복사: 512개로 나눠도 +4.5us(개당 9ns)
- 제로카피: 개수에 비례해 크게 늘고, 8개에서 16개로 갈 때 계단(+20us)이 있다(5장에서 원인 일부 확인)

### B. WSABUF 1개, 길이만 바꿈

| 길이 | 동기(us) | 제로카피(us) | 32B 메시지로 치면 1개당(동기) |
|------|----------|--------------|-------------------------------|
| 32B  | 9.5      | 13.0         | 9.5us                         |
| 512B | 9.8      | 13.2         | 0.61us                        |
| 2KB  | 10.0     | 13.3         | 0.16us                        |
| 8KB  | 11.9     | 14.4         | 0.05us                        |
| 32KB | 15.7     | 18.2         | 0.015us                       |
| 64KB | 43.6     | 44.9         | 0.02us                        |

- 32B에서 32KB로 1000배 늘려도 1.65배(9.5 → 15.7us). 늘어나는 몫은 바이트당 약 0.19ns
- 제로카피도 길이에 따라 는다 - (2) 루프백 전달과 TCP 처리는 어느 모드든 하기 때문(1장)
- 64KB에서 두 모드 모두 갑자기 뛴다(6장)

## 5. 원인 좁히기 - 제로카피 비용은 페이지 고정 때문인가 (D1-D3)

**결론: 조각당 비용(약 0.6us)은 페이지 수가 아니라 조각(WSABUF) 수에 붙는다. VirtualLock으로는 없앨 수 없다**

- D1: 조각 수와 바이트는 같게, 조각을 **한 페이지에 몰기**(간격 64B) vs **조각마다 다른 페이지**(간격 4096B) - 일부러 다른 페이지에 둔 메모리를 넘겨 비용이 느는지
- D2: 조각 1개, 바이트는 같게, 페이지 경계에 **안 걸치기** vs **걸치기**(페이지 +1)
- D3: 같은 점을 **VirtualLock 없이 / 걸고** - 프로세스가 미리 거는 잠금이 I/O마다의 잠금을 대신하는지
- 동기 복사는 페이지를 잠그지 않으므로 대조군

| 시험 | 조건                 | 비교                         | 동기(us)    | 제로카피(us) |
|------|----------------------|------------------------------|-------------|--------------|
| D1   | 34B x 16개           | 한 페이지 / 16페이지         | 9.9 / 10.0  | 20.2 / 35.6  |
| D1   | 34B x 64개           | 한 페이지 / 64페이지         | 10.7 / 10.8 | 68.6 / 70.3  |
| D2   | 64B x 1개            | 1페이지 / 2페이지(경계 걸침) | 9.5 / 9.4   | 12.9 / 13.0  |
| D2   | 4KB x 1개            | 1페이지 / 2페이지            | 11.2 / 11.3 | 14.0 / 14.0  |
| D2   | 8KB x 1개            | 2페이지 / 3페이지            | 12.1 / 12.2 | 14.5 / 14.5  |
| D3   | 4KB x 1개            | VirtualLock 없음 / 있음      | 11.2 / 11.2 | 14.0 / 14.0  |
| D3   | 34B x 64개(64페이지) | VirtualLock 없음 / 있음      | 10.8 / 10.8 | 70.3 / 69.1  |

- **D2**: 페이지가 하나 늘어도 0.1us 안 → 페이지마다 드는 비용은 측정 해상도(100ns) 아래
- **D1(64개)**: 한 페이지 68.6us vs 64페이지 70.3us(+2%) → 비용은 조각마다 한 번씩 드는 고정 비용. 커널이 조각마다 주소 목록(MDL)을 만들고 잠금 호출을 하는 "호출당" 비용으로 보인다
- **D3**: VirtualLock은 효과가 없다 → 프로세스의 잠금(작업 집합 고정)과 I/O마다의 잠금은 별개. 매번의 잠금을 없애려면 RIO(Registered I/O)처럼 버퍼를 미리 등록하는 API가 필요하다
- **D1(16개)**: 한 페이지 20us vs 16페이지 36us → A의 "8개에서 16개로 갈 때의 계단"은 **조각이 9개 이상이고 여러 페이지에 걸칠 때만** 생긴다(A의 16개 = 4KB가 2페이지에 걸침 37us, C의 16개 = 544B가 1페이지 19us). 64개에서는 페이지와 상관없이 같아진다
- 동기 복사(대조군)는 모든 시험에서 차이가 없었다
- 주의: 1회차 첫 점(D1 16개 한 페이지)만 39.3us로 튀었다(프로그램 시작 직후 첫 측정). 표의 20.2us는 2, 3회차(19.1, 21.2us)의 평균

## 6. 이론 - 비용 모델

`시간 = a + b × WSABUF 개수 + c × 바이트`. 계수는 A(개수)와 B(길이)에서 구하고 C로 검증했다(동기는 n = 1-256에서 오차 9% 안, 제로카피는 n = 64-512에서 18% 안)

| 모드      | 고정 a | 바이트당 c          | WSABUF당 b                      |
|-----------|--------|---------------------|---------------------------------|
| 동기 복사 | 9.5us  | 0.19ns (약 5.3GB/s) | 9ns                             |
| 제로카피  | 13.0us | 0.16ns              | 357ns (1-8개), 632ns (16-512개) |

각 항의 정체(커널 안은 재지 않았으므로 추정, D로 확인한 부분은 표시)

1. **고정 a(9.5-13us)**: 시스템 콜 진입, 소켓 계층(AFD), TCP 처리, 루프백 전달. 루프백이라 실제 NIC보다 클 것이다
2. **동기의 b(9ns)**: 커널이 배열을 돌며 조각마다 송신 버퍼로 복사하는 루프 한 바퀴
3. **제로카피의 b(360-630ns)**: 조각마다 주소 검사, 주소 목록(MDL) 만들기, 잠금 호출, 완료 때 풀기. **페이지 수가 아니라 조각 수에 비례**(D1, D2로 확인). 완료까지 걸리는 시간도 개수에 비례(512개: 반환 315us, 완료 351us)
4. **c(0.16-0.19ns/B)**: 동기는 (1) 복사 + (2) 루프백 전달, 제로카피는 (2)만. 차이 0.03ns/B가 (1)을 없앤 몫
5. **손익분기**: 제로카피가 이기려면 조각 하나의 바이트 절감이 조각 추가 비용을 넘어야 한다 → (632 - 9) / (0.189 - 0.159) = **약 21KB/조각**. 작은 메시지에서는 항상 손해(2026-10-25 송신 버퍼 0 실험의 처리량 -2-14%와 같은 방향)
6. 실제 네트워크에서는 (2)가 송신자 호출 밖(네트워크 카드가 메모리를 직접 읽음)이라 (1)의 비중이 커지고 손익분기가 내려갈 수 있다(재지 않음)

## 7. 설명하지 못한 것

- **64KB를 한 번에**: 두 모드 모두 43-45us로 뛴다(32KB는 15.7 / 18.2us). 32-64KB 사이는 재지 않아 경계를 모른다
- **동기, 34B x 512개(17KB)**: 37us(예측 18us). 같은 바이트를 1개로는 14.4us, 4KB를 512개로는 15.7us → 개수가 많고 전체도 클 때만 뛴다
- **제로카피 계단**: 조각 9개 이상 + 여러 페이지일 때 생긴다는 것까지 확인(5장). 커널 안의 어떤 경로 차이인지는 모른다
- 셋 다 커널이 크기·개수에 따라 다른 경로로 처리하는 것으로 보인다. 커널 내부 분석(함수별 시간)은 하지 않기로 했다(2026-11-02) - 결론(동기 복사 + WSABUF 1-2개 유지)에는 영향이 없다
