## 1. 요약

**라이브러리 소스를 고치지 않고 `.def` 파일로 DLL을 만드는 방식을 추천한다.** 임시 폴더에서 시험한 결과, 서버 exe를 다시 빌드하지 않고 DLL만 바꿔도 함수 내부·`Session`·링 크기 변경이 동작했다.

대신 `NetworkLib`의 멤버를 바꾸면 서버도 다시 빌드해야 한다. 잘못 섞으면 시작 직후 죽었고, 이를 막는 장치가 따로 없으므로 파일 이름 규칙으로 막는다(2-3).

분리와 별개로 **서버 Release 빌드의 최적화가 꺼져 있는 것**을 확인했다(2-5). 분리 전에 정해야 한다.

### 2-1. 라이브러리 형식

결정: **DLL** (사용자, 2026-11-05)

논의에서 확인한 내용을 기록으로 남긴다.

| 기준              | 정적 라이브러리     | DLL              |
| ----------------- | ------------------- | ---------------- |
| 라이브러리만 교체 | 불가, 다시 링크     | 가능, 조건은 2-3 |
| 같은 PC 코드 공유 | 안 됨               | 됨               |
| 호출 인라인       | 전체 최적화 때 가능 | 경계에서 불가    |
| 배포 파일         | exe 하나            | exe + dll        |

- 같은 PC에서 같은 DLL 파일을 쓰면 코드와 읽기 전용 데이터가 공유된다. 멤버 변수, 전역 변수, 힙, 스택은 프로세스마다 따로다
- 공유로 아끼는 메모리는 서버 하나당 DLL 크기인 246KB 이하다(시험 빌드, `/Od`). 세션 1000개의 링 버퍼 약 48MB와 비교하면 작다
- 성능 차이는 재 보지 않았다. 구현 뒤 3장의 측정으로 확인한다

### 2-2. 프로젝트 위치

- **A. `_lib/NetworkLib/` (추천)**
  - 공용 라이브러리는 `_lib/`에 둔다는 지금 규칙과 같다
  - 옮길 것: `NetworkLib.*`, `RingBuffer.h`, `ListenSocket.*`, `SocketUtil.*`
  - `Assert.h`, `Memory.h`는 서버 코드도 쓰므로 함께 옮기고 서버가 include한다
  - 남길 것: `main.cpp`, `NetConfigLoader.*`, `EchoServer.h`, `ChatServer.h`
  - 같이 고칠 것: 규칙 훅 `tools/check_cpp_style.ps1`의 검사 범위, `CODING_STANDARD.md`의 적용 범위, cpp-reviewer 설명, `CLAUDE.md`의 구조 표
- B. `networkLibProject/` 안에 프로젝트만 추가
  - 훅과 문서는 안 고쳐도 되지만 라이브러리와 서버 파일이 한 폴더에 섞여 경계가 안 보인다
- 서버 프로젝트 이름 `networkLibProject`는 두 안 모두 그대로 둔다. 측정 스크립트가 이 경로를 쓴다
- DLL은 서버 exe 옆에 있어야 실행된다. 같은 솔루션이면 기본 출력 폴더가 같을 것으로 보며, 구현 때 확인한다

### 2-3. 내보내는 방법

| 안              | 소스 수정 | 멤버 변경 시 | 작업량 |
| --------------- | --------- | ------------ | ------ |
| A. `.def` 파일  | 없음      | 서버도 빌드  | 작음   |
| B. 상속 + pImpl | 큼        | DLL만 교체   | 중간   |
| C. `dllexport`  | 매크로    | 서버도 빌드  | 작음   |

- **A. `.def` 파일로 내보낸다 (추천, 시험함)**
  - 헤더와 소스를 고치지 않는다. `.def` 파일 하나와 프로젝트 설정만 추가한다
  - 공개 함수가 바뀌면 `.def`의 이름도 고쳐야 한다. 함수 이름에 매개변수 타입이 인코딩되기 때문이다
- B. pImpl로 멤버를 숨긴다
  - 멤버까지 자유롭게 바꿀 수 있지만 `NetworkLib.cpp` 전체가 바뀐다. 멤버 변경이 잦아 불편해지면 그때 옮기면 된다
- C. `__declspec(dllexport)` 매크로
  - A와 교체 조건이 같은데 헤더를 고쳐야 하고 `std::vector`·`std::mutex` 멤버 때문에 C4251 경고가 난다

내보낼 함수는 13개다.

- `NetworkLib`: `~NetworkLib`, `Start`, `Stop`, `GetStat`, `GetNetError`, `SendPacket`, `Disconnect`, 소멸자 별칭 `??_E`
- `WsadataRAII`: 생성자, 소멸자
- `Profile`: `Reset`, `Save`, `SetEnabled`

소멸자 별칭은 컴파일러가 약한 심볼로만 만들어 그대로 내보내면 링크가 실패한다. `??_E…=??_G…`로 연결하고, 이때 나는 경고 LNK4102는 `/IGNORE:4102`로 끈다(README_ERRORS 1-27).

**프로파일러:** `ProfilerLib`는 DLL만 링크하고 `Profile` 함수를 내보낸다. `main`은 코드 변경 없이 DLL의 함수를 부르게 되어 전역 상태가 하나로 유지된다. `ProfilerLib`와 클라 프로젝트는 그대로다.

**CRT:** `/MT`를 유지한다. exe와 DLL이 CRT를 따로 갖지만, 할당과 해제가 같은 쪽에서 일어나므로 시험에서 문제가 없었다. 전체를 `/MD`로 바꾸면 `ProfilerLib`를 링크하는 클라 프로젝트까지 바꿔야 한다.

**DLL만 바꿔도 되는 경우** (시험 빌드, exe는 바이트까지 같은 파일)

| 수정 내용               | 서버 빌드 | 근거               |
| ----------------------- | --------- | ------------------ |
| 함수 내부               | 불필요    | 시험 통과          |
| `Session` 멤버, 링 크기 | 불필요    | 시험 통과          |
| `NetworkLib` 멤버       | 필요      | 시작 직후 죽음     |
| 공개 함수, 가상 함수    | 필요      | 구조상, 시험 안 함 |
| `NetConfig`, `NetStat`  | 필요      | 구조상, 시험 안 함 |

- 세 번째 줄처럼 잘못 섞으면 exe가 만든 객체보다 DLL이 큰 객체로 다룬다. 이번에는 바로 죽었지만 메모리가 조용히 깨질 수도 있다
- **규칙: 서버 빌드가 필요한 변경이면 DLL 파일 이름을 올린다**(`NetworkLib2.dll`). `.def`의 `LIBRARY` 줄만 바꾸면 되고, 이전 exe는 새 파일을 찾지 않으므로 섞이지 않는다. 사람이 지키는 규칙이라 놓칠 수 있다

### 2-4. 라이브러리 출력

사용자 제안: 라이브러리에서 출력을 뺀다. `printf` 10곳은 평소 출력이 아니라 오류 9곳과 경고 1곳이다.

- `/MT`에서는 `main`의 `setvbuf`가 DLL의 `stdout`에 적용되지 않는다. 시험에서 DLL이 `Start` 때 찍은 줄이 로그 맨 끝, `종료 완료` 뒤에 기록됐다
- 그냥 지우면 `bind` 실패 같은 원인을 알 수 없고, skip이 자동으로 꺼져도 알 수 없다(`IsSkipOnSuccess`도 지웠다)

선택지:

- **A. 빼고, 이유를 돌려준다 (추천)**
  - `GetNetError()`: 실패한 단계와 코드, `GetConfig()`: 실제 적용된 설정. 출력은 `main`이 한다
  - `CreateListenSocket`에 단계와 코드를 넘겨받는 매개변수를 추가한다
  - 워커의 GQCS 실패는 다른 스레드에서 기록되므로 Interlocked로 남긴다
  - 2-3의 "소스 그대로" 예외다. 처음 한 번만 고친다. `GetConfig`는 헤더의 인라인 함수라 내보낼 함수는 `GetNetError` 1개만 늘어난다
  - 구현(2단계): 시작 실패·GQCS 실패 모두 첫 오류만 남긴다. GQCS 실패는 전에는 출력만 했으나 이제 `mbRunning`도 내려 `main`이 알게 한다. 포트를 먼저 점유하면 `[main] 서버 시작 실패: bind err=10048`이 찍힌다
  - 변경(2026-11-06, 사용자 결정): GQCS·PQCS 실패는 `stderr` 로그 후 `__debugbreak`로 멈춘다(`lock_logic.md` 9-7). 첫 오류 기록은 시작 단계와 AcceptEx 소켓 생성에 남는다
- B. 그냥 지운다
  - 가장 간단하지만 시작 실패 원인을 알 수 없다
- C. 그대로 둔다
  - 소스를 전혀 안 고친다. 오류일 때만 찍히므로 평소에는 문제가 없지만, 오류 메시지가 로그 끝에야 나온다

### 2-5. 최적화 복원 순서

**서버 Release에 `<Optimization>Disabled</Optimization>`가 있다**(`networkLibProject.vcxproj:122`, `ParserLib.vcxproj:132`). 즉 `/Od`다.

- 사용자가 디버깅용으로 넣은 설정이다. `docs/handoff_2026_10_15.md`에 "정식 측정값을 낼 때는 /O2로 되돌릴 것"이라고 적어 뒀지만 되돌리지 않았다
- `LoadClient`, `EchoClient`에는 이 줄이 없다. 지금까지 서버만 최적화 없이 쟀다는 뜻이다
- 포트폴리오의 처리량·CPU 숫자는 모두 이 조건이다. 조건을 같게 두고 비교한 결론은 그대로일 가능성이 있지만, 다시 재기 전에는 알 수 없다. 절대값은 달라질 수 있다
- `/O2`에서는 `Assert`의 `__assume`이 실제 최적화에 쓰이고 코드 타이밍도 바뀐다. 처리량뿐 아니라 끊김 판정과 순서 검사도 다시 돌려야 한다

선택지:

- **A. 분리 전에 복원 (추천)**: `/O2` 복원 → 시험 → 기준 처리량 측정 → 분리 → 같은 측정으로 차이 확인
  - 최적화 변경과 분리의 영향을 나눠 볼 수 있다
- B. 분리 뒤에 복원
  - 분리 비교는 `/Od`끼리 하게 되고, 그 숫자는 복원 뒤 다시 재야 한다
- C. `/Od`를 유지하고 문서에 조건을 밝힌다
  - 작업은 가장 적지만 "최적화를 끈 빌드의 성능"을 내세우는 포트폴리오가 된다
- 어느 안이든 디버깅에 `/Od`가 필요하면 Debug 구성을 쓰거나, 필요한 파일만 잠시 끈다

## 3. 구현 순서 (추천안 기준)

각 단계를 따로 커밋해 문제가 생기면 원인을 그 단계로 좁힌다.

1. `/O2` 복원, 시험, 기준 처리량 측정
2. 라이브러리 `printf` 제거와 오류 돌려주기 - 아직 exe 하나인 상태에서
3. DLL 프로젝트 추가, 파일 이동, `.def`, 서버의 `ProjectReference` 정리
4. Release·Debug 빌드 경고 0, 규칙 훅 위반 0
5. 회귀 3종, Debug 서버 + 비정상 헤더, 섞인 클라, 방 옮기기 시험
6. **DLL만 교체 시험**을 프로젝트 구성으로 다시 확인하고 포트폴리오용 기록으로 남긴다
7. 1번과 같은 측정으로 처리량 비교 (측정 전 CPU 상위 프로세스 확인, README_ERRORS 1-24)

## 4. 시험 빌드 결과 (2026-11-05, PC B)

저장소 소스를 임시 폴더에서 `cl`, `link`로 직접 빌드했다. 서버와 같은 `/MT /Od` 조건이고 `/GL`은 뺐다. 저장소 파일은 고치지 않았다. **각 1회라 처리량 비교 근거는 아니다.**

| 시험                     | 결과                       |
| ------------------------ | -------------------------- |
| 에코 15초                | 3,960MB, 끊김 0, 정상 종료 |
| 정상 + 비정상 헤더 15초  | 비정상 4.5만, 정상 끊김 0  |
| A, 에코 15초             | 3,963MB, 끊김 0            |
| A, 정상 + 받지 않는 클라 | 넘침 156, 정상 끊김 0      |
| B, 서버 시작             | 시작 직후 종료             |
| 프로파일러 + 클라 7초    | 태그 기록, 파일 저장됨     |

- A: `Session`에 멤버 추가, 송신 링 64KB, `Start`에 출력 추가. DLL만 다시 빌드했고 exe는 해시가 같다. 로그에 추가한 출력이 있어 새 DLL이 돈 것을 확인했다
- B: `NetworkLib` 맨 앞에 멤버 추가. 설정 출력까지 나온 뒤 서버 시작 메시지 없이 프로세스가 끝났다
- 정상 + 비정상 헤더 실행에서는 시작 직후 `connectFail`이 정상 256, 비정상 64 나왔고 정상 처리량도 1,982MB로 낮았다. 서버가 늦게 받기 시작한 것으로 보이나 확인하지 않았다
- 프로파일러: `GQCS`, `Complete`, `WSASend`, `WSARecv` 태그가 워커 2개 모두에 기록됐다
- 크기: DLL 246KB, exe 364KB. `/MT`라 CRT가 양쪽에 들어가 exe가 크게 줄지 않았다

**시험하지 않은 것:** 채팅 서버 경로, Debug 구성, `/GL`, 섞인 클라, 방 옮기기, 실제 프로젝트 구성. 3장에서 확인한다.
