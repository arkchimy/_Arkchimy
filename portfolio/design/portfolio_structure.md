# 포트폴리오 구조 (설계 논의)

## 2판 (2026-11-10) - 라이브러리 설계를 뼈대로

**네트워크 라이브러리가 주인공이고, 뼈대는 "어떤 부품으로 나눴고, 왜 그렇게 설계했고, 무엇을 고민했는가"다.** 측정 숫자는 앞에 내세우지 않고 각 결정의 근거로만 쓴다. 기한은 일주일, 그래픽 클라이언트와 MMO는 만들지 않는다. 사용 예로 오목 대전 서버를 만든다(MySQL 8.0 사용).

결정(사용자, 2026-11-10):

- **오목 대전 서버는 사용 예다.** 오목은 규칙이 단순해 앞세우면 약해 보이므로 라이브러리를 주된 내용으로 둔다
- **핵심 성과 표는 없앤다.** 숫자는 설계 결정 표의 이유 칸과 고민 사례 안에 둔다
- **고민 사례 3개:** 송신 경로, 세션 수명, 무응답 클라
  - 무응답 클라는 하트비트로 보는 수신 타임아웃과, 송신 요청 시각(`WSASend`를 건 시각, `mWsaSendQPC`)을 지금 시각과 비교하는 송신 정체 판정을 다룬다
- **검증은 테스트 케이스 방식이다.** 설계에서 "깨지면 안 되는 것"을 케이스로 뽑아 하나씩 실험한다. 케이스는 `verification/test_cases.md` 초안을 두고 따로 논의해 정한다
- **"SendPacket이 원래 워커에서만 됐다"는 이력은 쓰지 않는다**
- **용어:** 수신 윈도우(받는 창 대신), 무응답 클라(느린 클라 대신), 워커 밖 스레드의 송신

README 구성(약 110줄):

| 순서 | 구성 요소           | 담는 것                           |
| ---- | ------------------- | --------------------------------- |
| 1    | 한 줄 요약          | 무엇을 만들었고, 무엇을 중시했나  |
| 2    | 구조 그림           | 스레드, 세션, 수신·송신 경로      |

| 4    | 가장 오래 고민한 것 | 처음 설계 → 틀린 점 → 지금 설계   |
| 5    | 검증                | 테스트 케이스와 결과 요약         |
| 6    | 사용 예             | 오목 대전 서버, GIF               |
| 7    | 한계, 빌드와 실행   | 알고 있지만 안 고친 것, 실행 방법 |

### 2-5. 앞으로의 작업 순서

**추천 순서는 구조 문서 → 비용 분해 → 성능 사례 1개 → 넘침 제약 → 암호화다.** 구조 문서를 쓰는 과정이 사용자의 구조 파악도 겸하고, 비용 분해 표가 성능 작업의 출발점이 된다.

| 순서 | 작업                          | 포트폴리오에서의 결과 |
| ---- | ----------------------------- | --------------------- |
| 1    | 구조 문서, 사용자와 함께 읽기 | `architecture.md`     |
| 2    | `/O2` 현재 구조 비용 분해     | 구조 문서의 비용 표   |
| 3    | 저장소·문서 정리              | 첫 인상               |
| 4    | 성능 후보 1개 (아래 기준)     | 새 사례 문서          |
| 5    | 넘침 컨텐츠 제약              | 한계 항목 해소        |
| 6    | 암호화                        | 기능 + 비용 측정      |

성능 작업을 시작하는 기준은 다음과 같다.

- **사례가 되는가:** "가설 → 측정 → 원인 → 수정 → 대조 조건" 흐름으로 쓸 수 있어야 한다.
- **설명할 수 있는가:** 숫자가 왜 그렇게 나왔는지 사용자가 직접 설명할 수 있어야 한다.
- **첫 후보(제안):** 워커가 늘면 처리량이 떨어지는 현상이다. README 한계에 이미 미해결로 적혀 있어, 풀면 한계가 사례로 바뀐다. 다만 이 현상은 PC B에서만 나타나 PC B에서 작업해야 한다.
- **측정 PC(사용자 결정, 2026-11-06):** 멀티스레드 성능 측정은 하이브리드가 아닌 PC B에서만 한다. PC A는 성능 코어와 효율 코어가 섞여 있어 부적합하다. 2번 비용 분해는 PC A에서 임시로 쟀으므로 PC B에서 다시 재고, 4번 성능 후보는 그 결과로 고른다.
