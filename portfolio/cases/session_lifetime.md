# 사례: 잠금 없는 세션 수명 관리 - 해제 표시 비트

**세션 카운트를 "0보다 클 때만 올리는 CAS 반복"에서 "무조건 한 번 올리고, 63번 비트(해제 표시)로 막는" 방식으로 바꿨다.** 이 방식은 순서를 하나만 틀려도 해제가 두 번 일어나거나 빈 슬롯이 살아나는데, 리뷰에서 네 판이 구체적인 경쟁 시나리오로 깨졌다. 결론은 **표시를 세우는 곳은 "0일 때 CAS에 성공한 한 스레드", 지우는 곳은 "수락에서 새 ID를 쓴 뒤"뿐이어야 한다**는 것이다.

- 기준 코드: 2026-11-09, `_lib/NetworkLib/NetworkLib.cpp`, `Session.h`
- 처리량 비교는 아직 재지 않았다([6장](#6-한계)).

## 1. 문제

세션은 시작할 때 만든 슬롯을 계속 다시 쓴다. 컨텐츠는 포인터 대신 ID로 세션을 찾고, 여러 스레드가 동시에 같은 세션을 쓴다. 세 가지를 잠금 없이 지켜야 한다.

| 요구                        | 깨지면                               |
| --------------------------- | ------------------------------------ |
| 해제는 정확히 한 번         | `OnRelease` 두 번, 빈 슬롯 번호 중복 |
| 해제 중·빈 슬롯은 못 잡음   | 닫힌 소켓 사용, 수락 중인 세션 해제  |
| 옛 ID로는 새 세션을 못 잡음 | 다른 사람에게 메시지가 감            |

ID = (세대 << 32) | 슬롯 번호라, 카운트를 잡은 뒤 ID를 비교하면 세 번째는 막힌다. 남은 것은 "언제 잡기를 실패시키고, 언제 해제하는가"다.

## 2. 이전 방식: 0보다 클 때만 올리는 CAS 반복

```cpp
LONG count = session.mIoCount;
while (count > 0)
{
	const LONG prev = InterlockedCompareExchange(&session.mIoCount, count + 1, count);
	if (prev == count)
	{
		return true;
	}
	count = prev; // 그사이 바뀌었으면 다시 - 0이 됐으면 실패
}
return false;
```

맞게 동작했다. 다만 채팅에서는 `SendPacket` → `findSession`이 받는 사람마다 이 반복을 돈다. 2026-11-04에 초당 약 720만 번, 약 0.3코어로 쟀다(PC B, 그때는 `/Od` 빌드). 다른 스레드가 같은 세션을 건드리면 CAS가 실패해 다시 돈다.

## 3. 새 방식: 무조건 +1, 63번 비트로 막기

`mIoCount`를 64비트로 넓히고 63번 비트(`RELEASE_FLAG`)를 해제 표시로 쓴다. 표시는 해제 작업을 넣은 순간부터 다음 수락까지 서 있다.

| 단계 | 함수              | 하는 일                                          |
| ---- | ----------------- | ------------------------------------------------ |
| 잡기 | `sessionLock`     | +1, 결과에 표시가 있으면 실패(되돌리지 않음)     |
| 놓기 | `sessionUnLock`   | -1, 0이면 `postReleasePQCS`                      |
| 해제 | `postReleasePQCS` | CAS(0 → 표시)에 성공한 스레드만 해제 작업을 넣음 |
| 수락 | `acceptSession`   | 새 ID를 쓴 뒤 카운트를 1로 덮어씀                |

```cpp
bool NetworkLib::sessionLock(Session& session)
{
	const int64_t count = _InterlockedIncrement64(&session.mIoCount);
	return (count & RELEASE_FLAG) == 0; // 해제 중·빈 슬롯이면 실패 - 올린 1은 되돌리지 않는다
}

void NetworkLib::postReleasePQCS(Session& session)
{
	if (InterlockedCompareExchange64(&session.mIoCount, RELEASE_FLAG, 0) != 0)
	{
		return; // 0을 만든 직후 누가 +1 했다 - 해제는 그 스레드가 다시 0을 만들 때
	}
	// 해제 작업을 IOCP에 넣는다 (OnRelease는 항상 워커에서)
}

// acceptSession - allocSession이 새 mID를 쓴 뒤
InterlockedExchange64(&session->mIoCount, 1); // 표시와 실패한 sessionLock이 남긴 값을 함께 지우고 수락 몫을 잡는다
```

(실제 코드에서 주석과 변수 선언만 줄였다.)

- **왜 되돌리지 않나:** 표시가 선 동안 되돌린 -1이 0을 만들면 CAS가 다시 성공해 해제가 한 번 더 들어간다. 쌓인 값은 수락의 덮어쓰기가 지운다. 표시가 선 동안에는 성공한 잡기가 없으므로 덮어써도 지워지는 정당한 몫이 없다.
- **처음 쓰는 슬롯:** 초기값도 `RELEASE_FLAG`다. 빈 슬롯을 감시 스레드와 `Stop`이 매번 순회하므로 반드시 필요하다.
- **옛 ID:** 수락이 새 ID를 쓴 뒤 표시를 지우고, 둘 다 같은 스레드에서 Interlocked(전체 메모리 장벽) 앞뒤로 일어난다. 표시가 지워진 것을 본 스레드는 새 ID를 보므로 옛 ID는 ID 비교에서 걸러진다.
- **해제가 빠지지 않는 이유:** 마지막 몫이 0을 만든 직후 다른 스레드가 +1 하면 CAS가 실패한다. 그 스레드가 일을 마치고 다시 0을 만들 때 CAS가 성공한다.

## 4. 리뷰에서 깨진 판

같은 날 cpp-reviewer와 직접 검토로 네 번 다시 고쳤다. 모두 빌드 전에 구체적인 실행 순서로 찾았다.

**1판: 올린 뒤 1이면 되돌리기.** "올렸더니 1(=원래 0)이면 -1 하고, 그 결과가 0이 아니면 성공"으로 했다.

| 순서 | 감시 스레드 W         | 워커 X       | 카운트 |
| ---- | --------------------- | ------------ | ------ |
| 1    | +1 → 1 (원래 0)       |              | 1      |
| 2    |                       | +1 → 2, 성공 | 2      |
| 3    | -1 → 1, 0 아님 → 성공 |              | 1      |

W는 몫 없이 성공을 받고 나중에 -1을 한 번 더 한다. 카운트가 실제보다 하나 적어진다. 이미 해제 작업이 들어간 세션이면 해제가 한 번 더 들어가고, 수신이 걸린 세션이면 그 수신이 끝나기 전에 해제된다.

**2판: 표시를 세우기만 하고 지우는 곳 없음.** 한 번 해제된 슬롯은 카운트가 `INT64_MIN` 근처에서 시작해 다시는 0이 되지 않았다. 두 번째 연결부터 해제되지 않고, `Stop`이 끝나지 않는다.

**3판: 처음 쓰는 슬롯의 초기값 0.** 송신 정체 감시가 1초마다 모든 슬롯을 순회하며 빈 슬롯을 0 → 1 → 0으로 만들었다. CAS가 성공해 빈 슬롯에 해제가 들어가고, 빈 슬롯 번호가 스택에 두 번 쌓인다. 그러면 두 연결이 `Session` 하나를 같이 쓰게 되고, `Stop`의 "빈 슬롯 수 = 전체"가 영원히 거짓이 된다.

**4판: `allocSession`에서 0을 쓰기.** 0을 쓴 뒤 수락 몫을 잡기까지 IOCP 등록 같은 시스템 호출이 있다. 그 사이 다른 스레드가 0 → 1 → 0을 만들면 수락 준비 중인 세션이 해제된다. `OnRelease`가 `OnAccept`보다 먼저 오고, 그 슬롯은 쓰는 중인데도 빈 슬롯 스택으로 돌아간다.

`releaseSession`에서 0으로 되돌리는 안도 검토했다. 그러면 빈 슬롯으로 있는 동안 표시가 없어져 3판과 같은 문제가 생기고, 잠깐 잡은 몫을 지워 카운트가 -1이 될 수 있어 채택하지 않았다.

**같이 고친 것:** `WSARecv`가 즉시 실패한 경로만 끊기 플래그를 세우지 않았다. 카운트가 0이 된 직후 잡은 스레드가 끊기 플래그를 못 보고 송신을 다시 걸 수 있어, 이 경로에도 `requestDisconnect`를 넣었다. 이제 0이 되는 모든 경로가 끊기 플래그를 먼저 세운다.

## 6. 한계

- **처리량을 재지 않았다.** 받는 사람마다 하던 CAS 반복이 `lock xadd` 한 번으로 바뀐 효과는 수정 전 빌드(`a6f6374`)와 번갈아 재야 안다.
- **경쟁 시나리오는 검토로 막았고, 그 순서를 강제로 만드는 시험은 없다.** 위 시험은 그 경로를 지날 조건(빈 슬롯 순회, 재연결, 방 이동)을 만든 것이다.
- **0이 된 직후 다시 잡히는 순간이 남아 있다.** 해제 표시가 서기 전에 맞는 ID로 잡으면 성공한다. 해제가 그 스레드로 넘어갈 뿐 빠지거나 겹치지 않고, 0이 되는 경로는 모두 끊기 플래그를 먼저 세우므로 새 송신은 걸리지 않는다.
