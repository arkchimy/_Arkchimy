# 사례: 방 락 안의 `OnRelease` 재진입 데드락 경로

**코드를 읽다 찾은 데드락 경로를 일부러 실패를 일으켜 재현하고, 실제 원인이 재잠금임을 확인한 뒤, 복구 대신 멈추는 방식으로 없앴다.** 실제 운영에서 일어난 적은 없고, 강제 시험으로 확인한 경로다.

## 1. 문제

해제는 원래 IOCP에 작업으로 넣어 항상 워커에서 처리한다. 그런데 이 전달(`PostQueuedCompletionStatus`)이 실패하는 분기만 그 자리에서 해제하고 있었다.

```text
A 세션의 broadcast
[방 락 잡음]
  구성원 B에게 SendPacket
    findSession: B의 카운트 +1
    ... 그사이 다른 워커가 B의 취소 완료를 처리 ...
    decIoCount: 이 스레드의 몫이 마지막이라 0
      전달 실패 → 그 자리에서 releaseSession(B)
        OnRelease(B) → leave
          같은 방 락을 다시 잡음   <-- 자기 자신을 기다림
```

B는 그 방의 구성원이고 방에서 빠지는 시점이 바로 `OnRelease`다. 그래서 다시 잡는 락은 우연이 아니라 **구조적으로 항상 같은 방 락**이다.

## 2. 재현

전달 실패를 강제한 빌드로 시험했다. PC A(Core Ultra 5 125U), 정상 채팅 256세션 + 받지 않는 클라 64세션, 방 16, 20초.

| 빌드                  | 횟수 | 재진입 | 비정상 종료 | 정상 종료 |
| --------------------- | ---- | ------ | ----------- | --------- |
| 표시만 (대조)         | 6    | 0      | 0           | 6         |
| 전달 실패 강제        | 10   | 3      | 3           | 7         |
| 전달 실패 강제 + 진단 | 10   | 1      | 1           | 9         |

재진입이 난 회차만 종료했다. 예외를 찍어 보니 원인이 직접 나왔다.

```text
[deadlock-test] 방 락 안에서 OnRelease 재진입
[deadlock-test] leave 예외 inLock=1 code=36 what=resource deadlock would occur: resource deadlock would occur
```

## 3. 왜 멈추지 않고 종료했나

MSVC의 `std::mutex`가 재잠금을 감지하기 때문이다. `crt/src/stl/mutex.cpp`의 `mtx_do_lock`은 소유 스레드 ID를 먼저 비교해, 같은 스레드면 SRW 락을 잡지 않고 `_Busy`를 돌려준다. `<mutex>`는 이를 `resource_deadlock_would_occur` 예외로 던진다.

표준에서는 정의되지 않은 동작이라 이 감지에 기대면 안 된다. 잡는 곳이 없어 프로세스 전체가 끝났고, 끊긴 세션 하나가 아니라 모든 연결이 사라졌다.

재귀 뮤텍스로 바꿔도 해결되지 않는다. `leave`가 `broadcast`의 구성원 순회 도중 그 벡터를 바꾸기 때문이다.

## 4. 해결 방향을 정한 과정

처음 만든 수정은 해제를 묶음 끝으로 미루는 방식이었다. 강제 실패 20회에서 재진입이 0이었고, 위험 지점을 실제로 지났는지 카운터로도 확인했다(`SendPacket` 안 전달 실패 5건).

그러나 다음 이유로 채택하지 않았다.

- 핸들이 닫혀서 실패하는 경우는 이 코드에서 일어나지 않는다. `Stop`은 슬롯이 전부 돌아온 뒤 워커를 끝내고 나서야 핸들을 닫는다.
- 다른 실패 조건은 문서에 나열되어 있지 않아, 무엇을 복구하는지 알 수 없다.
- 실패 조건도 모르는 경로에 스레드별 목록과 반복문을 두는 것은 과하다.

**결정: IOCP 호출 자체가 실패하면 로그를 남기고 멈춘다.** 완료 기반 서버는 IOCP 없이 복구할 수 없다. GQCS·GQCSEx·종료 신호 PQCS도 같은 함수로 묶었다.

```cpp
static void crashOnIocpFailure(const char* step, const DWORD err)
{
	fprintf(stderr, "[NetworkLib] %s 실패 err=%lu\n", step, err);
	__debugbreak(); // 덤프 핸들러가 잡을 수 있게
}
```

## 5. 검증

호출 하나에만 잘못된 핸들을 넘겨 실제 실패를 만들었다.

| 호출             | 횟수 | 결과                       |
| ---------------- | ---- | -------------------------- |
| 해제 작업 PQCS   | 1    | `err=6` 로그, `0x80000003` |
| GQCSEx           | 1    | `err=6` 로그, `0x80000003` |
| GQCS             | 1    | `err=6` 로그, `0x80000003` |
| 종료 신호 PQCS   | 1    | `err=6` 로그, `0x80000003` |
| 종료 신호 재전달 | 6    | 실행되지 않음              |

일반 회귀(에코, 비정상 헤더, 받지 않는 클라, 방 옮기기, 섞인 클라)는 정상 클라 끊김 없이 통과했다. 방 옮기기 워커 4의 정상 클라 넘침만 이미 알려진 동작대로 11건 있었다.

## 6. 한계

- 잘못된 핸들 외의 실제 실패 조건과 빈도는 모른다.
- 재진입 계기(넘침 끊기인지 다른 끊김인지)는 로그로 확정하지 못했다.
- 종료 신호 재전달 분기는 시험에서 실행되지 않았다.
- 덤프 생성은 아직 없다.
