# 섞인 클라 + 고부하 합격 시험 (2026-11-05 재측정, PC B)

**결론: 서버 CPU가 워커 2개 중 1.86코어인 고부하에서 끊김 정책은 정상 클라를 끊지 않았고, 문제 클라는 각자 맞는 판정으로 끊었다. 3회 모두 판정이 같았다.**

- 측정 PC: PC B(Core i5-8600, 6코어 6스레드, 루프백), 서버·클라 `/O2`, `3fed5a1`. 2026-11-03 PC A 첫 시험의 판정도 같았다(서버 1.97–1.99/2, 원본 `실험폴더/mixed_clients_2026_11_03/raw_runs.csv`) - 숫자는 섞지 않는다
- 원본: `실험폴더/portfolio_o2_2026_11_05/main_mixed_runs.csv`
- 다시 돌리기: `.\tools\mixed_test.ps1 -Rounds 3 -RunSec 25` (빌드: 서버·EchoClient·LoadClient Release x64)

---

## 1. 왜 이 시험인가

**서버의 한계 숫자를 찾는 큰 스트레스 테스트는 하지 않는다(사용자 결정, 2026-11-03).** 서버와 클라가 같은 PC라 한계 숫자는 PC의 한계일 뿐이다.

대신 끊김 정책의 **오판**을 확인한다. 넘침(송신 링 가득), 송신 정체, 무응답은 모두 "클라가 느리다"를 시간이나 양으로 **추정**하는 판정이라, 서버가 바쁘면 정상 클라를 끊을 수 있다. 실제로 그런 일이 있었다.

| 과거 오판(README_ERRORS)               | 원인                           |
| -------------------------------------- | ------------------------------ |
| 2-9: 하트비트 클라를 무응답으로 끊음   | 수신마다 합쳐 처리가 밀림      |
| 2-7: 방송 중 정상 클라를 넘침으로 끊음 | 미루는 동안 여러 바퀴분이 쌓임 |

그래서 확인할 것은 하나다: **고부하에서 정상 클라가 끊기지 않는가, 문제 클라는 맞는 판정으로 끊기는가.**

## 2. 조건

| 항목              | 값                                                |
| ----------------- | ------------------------------------------------- |
| 서버              | 채팅(방 16), GQCSEx(64) + skip + `mergeSends = 1` |
| 워커              | 2 (부하가 몰리게)                                 |
| 판정 기준(시험용) | 무응답 5초, 입장 5초, 송신 정체 3초               |
| 시간              | 25초 × 3회                                        |

**동시에 붙인 클라 6종**

| 클라           | 설정                    | 세션 | 기대                |
| -------------- | ----------------------- | ---- | ------------------- |
| 정상 채팅      | `client_chat.cfg`       | 256  | 끊김 0              |
| 하트비트만     | `client_chatIdleHb.cfg` | 64   | 끊김 0              |
| 입장 후 침묵   | `client_chatIdle.cfg`   | 64   | 무응답끊김          |
| 입장 안 함     | `client_chatNoJoin.cfg` | 64   | 입장시간초과        |
| 받지 않는 채팅 | `client_chatNoRecv.cfg` | 64   | 넘침 또는 송신 정체 |
| 비정상 헤더    | `client_badPacket.cfg`  | 64   | 비정상패킷          |

- 비정상 헤더만 EchoClient다. 운영 기본값은 무응답 30초, 입장 10초, 송신 정체 10초다. 정상 채팅·입장 안 함·받지 않는 채팅은 하트비트 1초, 받지 않는 채팅은 수신 버퍼 1KB다.
- 문제 클라 64세션은 방 0–3에 들어가 정상 클라와 같은 방을 쓴다(받지 않는 클라에 방송이 쌓이게).
- 받지 않는 채팅 클라는 이 시험을 위해 새로 만든 LoadClient `chatNoRecv` 모드다. 입장(`JoinOk`)까지만 받고 그 뒤로 `recv`를 하지 않는다. 무응답 판정에 먼저 걸리지 않게 하트비트는 보낸다.

## 4. 해석

- **송신 정체가 0인 이유**: 받지 않는 채팅 클라에는 방송이 빨리 쌓여, 서버 커널 송신 버퍼(약 64KB)와 송신 링 32KB를 금방 넘는다. 그래서 넘침이 먼저 끊는다. `timeout_design.md` 5-1의 구간 분석(64KB까지 커널 흡수, 64–96KB 송신 정체, 그 위 넘침)과 맞다. 송신 정체 판정은 같은 문서 5장(EchoClient + `sendBufZero`)에서 따로 확인했다.
- **비정상 헤더가 채팅의 `잘못된패킷`이 아닌 이유**: EchoClient는 최대 길이를 넘는 헤더를 보낸다. 라이브러리가 헤더 길이 검사에서 먼저 끊으므로 컨텐츠(채팅)까지 오지 않는다. 의도한 동작이다.
- **문제 클라의 끊김 건수가 세션 수의 배수인 이유**: 끊긴 클라는 바로 다시 연결해서 같은 이유로 또 끊긴다. 건수보다 "어느 판정으로 끊겼는가"가 중요하다.

## 5. 한계

- 루프백, 한 PC. 다른 PC로 클라를 옮기는 측정은 하지 않는다(사용자 결정 - 무선 환경에서 재전송이 많아 비교가 안 됐다).
- 워커 2 한 조건만 봤다. 서버는 1.86/2로 완전 포화는 아니다. 워커를 늘린 조건, 운영 기준값(30초 등)에서의 장시간 실행은 하지 않았다.
- 받지 않는 클라는 방송이 많은 방에서만 시험했다. 방송이 적은 방에서 조금씩 쌓이는 경우는 송신 정체 쪽이며, 이는 5장 시험이 대신한다.
