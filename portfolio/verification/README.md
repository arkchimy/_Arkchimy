# 검증과 측정 방법

**"시험을 통과했다"보다 "시험이 버그를 실제로 잡는가"와 "숫자를 믿을 수 있는가"를 먼저 따졌다.**

## 1. 정확성 검증

- **에코 시험 클라이언트:** select 스레드 하나가 정상·비정상 헤더·송신 정체 역할의 세션을 돌린다. 정상 세션은 응답을 메시지 단위로 비교해 불일치하면 바로 멈추고, 송신 정체·비정상 헤더 세션의 끊김 수는 서버 통계와 맞춰 본다. 케이스와 이유는 [테스트 케이스](test_cases.md)에 있다.
- **일시정지 검사:** 새 요청을 멈추고 기다려, 보낸 요청의 응답이 모두 오는지 본다. 부하 중에는 응답 하나가 서버에 남아도 드러나지 않기 때문이다.
- **지연 주입:** 드물게 재현되는 버그는 조건을 주입해 재현한다. 정상 클라 넘침 끊김은 16회 중 1회로 드물어, 완료 처리를 일부러 늦추는 시험을 만들어 수정 전 15초당 244–386회, 수정 후 0회를 확인했다(`/Od` 당시 값).
- **실패 강제:** 일어나기 어려운 실패는 강제로 만든다. → [데드락 경로](../cases/deadlock.md)

## 2. 측정을 믿기 위해 한 일

- **측정 도구부터 의심:** 처음 잰 처리량은 서버가 아니라 검증 클라이언트의 한계였다. 그래서 부하 전용 클라이언트를 만들고, 서버와 클라이언트 CPU를 항상 함께 본다.
- **비교 방법 고정:** 같은 실행 안에서 조건을 번갈아 돌리고, 회차마다 순서를 바꿔 중앙값을 낸다. 두 PC의 숫자는 섞지 않는다.
- **혼입 변수 제거:** 프로파일러 비용이 GQCS 쪽에 더 붙는 것을 발견해, 처리량과 비용 분해를 별도 실행에서 잰다.
- **측정 비용 확인:** 메시지마다 측정 코드를 넣으면 처리량이 45–49% 떨어져, 그 숫자는 쓰지 않았다.
- **빌드 설정 오류 발견:** 서버 Release가 디버깅용 `/Od`로 남아 있던 것을 찾아 `/O2`로 복원하고, 옛 커밋까지 다시 빌드해 다시 쟀다. 그 결과 −82%가 −61%로 바뀌고, skip의 처리량 이득 +31–35%와 수 초 기아는 재현되지 않아 결론을 고쳤다. → [재측정 결과](../../실험폴더/portfolio_o2_2026_11_05/결과.md)
- **측정 스크립트도 검증:** 재측정 중 옛 커밋 클라이언트에 메시지 크기 설정이 없어 4KB 대조 조건이 32B로 돈 것을 로그로 찾아 다시 쟀다.
- **해석 실수도 기록:** 송신 완료 2–4ms를 ACK 대기로 잘못 읽은 일 등을 [README_ERRORS.md](../../README_ERRORS.md) 4장에 남겼다.
