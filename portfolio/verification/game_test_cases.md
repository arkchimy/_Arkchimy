# 게임 서버 테스트 케이스

게임 서버(TRPG 던전 + 경매장 + MySQL + 운영 툴)와 로그인 서버(가입·로그인, Redis 세션 키, 암호 통로)를 시험 스크립트 8개(`tools/game/`)로 시험했다. 스크립트마다 서버를 띄우고 시험 클라에 명령을 넣은 뒤, 클라 출력·서버 통계·DB를 읽어 판정을 PASS/FAIL로 낸다. 판정은 모두 68개이고, 마지막 실행(2026-11-15)에서 모두 통과했다.

오래 돌릴 때만 드러나는 문제(누수, 드문 경쟁, 멈춤)는 [장시간 시험](game_soak.md)이 맡는다.

## 1. 무엇을 잡으려는가

| 영역        | 시험          | 잡으려는 문제                        |
| ----------- | ------------- | ------------------------------------ |
| 로그인·인증 | `login`       | 남의 계정 입장, 키 재사용, 계속 시도 |
| 암호 통로   | `login`       | 도청·변조·가짜 서버·평문 우회        |
| 로그인 경쟁 | `login_race`  | 한 세션이 두 계정에 로그인           |
| 경매·골드   | `auction`     | 골드 중복·증발, 알림 순서            |
| 저장·재시작 | `restart`     | 서버가 꺼질 때 데이터 유실           |
| 저장·재시작 | `reconnect`   | DB 연결이 끊길 때 저장 유실          |
| 운영 툴     | `admin`       | 회수 경로별 정합성, 제재             |
| 던전        | `dungeon4`    | 이탈 처리, 파티원 간 순서            |
| 던전        | `potion_full` | 인벤토리가 가득 찬 사람의 전리품     |

- **공통 판정**: 시험이 끝나면 대부분 "DB 골드 = 로그 합계"와 "DB 실패 0"을 함께 본다. 골드는 바뀔 때마다 증감으로 저장하고 로그에 한 줄씩 남기므로, 저장이 하나라도 빠지거나 두 번 들어가면 이 둘이 어긋난다.

## 2. 시험별 케이스

### 2-1. `login` - 로그인 서버, 세션 키, 암호 통로 (판정 21개)

로그인 서버는 비밀번호를 Argon2id + 솔트 + 페퍼로 저장하고, 로그인에 성공하면 30초짜리 세션 키를 Redis에 넣는다. 게임 서버는 그 키로 만든 입장 증명을 확인한 뒤 키를 지우고, 그 뒤의 메시지는 키에서 파생한 방향별 키로 암호화한다.

**가입·로그인**
1. 가입 성공
2. 같은 아이디 다시 가입 → "이미 있음"
3. 짧은 비밀번호 → 거절(8–64바이트)
4. 틀린 비밀번호와 없는 아이디 → 같은 실패 응답 - 응답 종류로 어느 쪽인지 알려 주지 않는다
5. 맞는 비밀번호 → 게임 서버 입장
6. 한 연결에서 5번 틀리면 끊김 - 비밀번호를 계속 맞혀 보는 속도를 늦춘다

**로그인 구간 암호화**

7. 암호문 한 바이트를 바꾸면 서버가 응답 없이 끊음 - 확인 값(Poly1305)이 맞지 않는다
8. 클라가 가진 서버 공개 키가 다르면 "서버 확인 실패"로 비밀번호를 보내지 않음 - 가짜 서버(중간자)를 막는 서명 확인

**세션 키와 입장**

9. 로그인 서버에서 세션 키를 받음
10. 틀린 증명 → 입장 실패
11. 틀린 증명 뒤에도 진짜 키로 입장 - 확인에 실패하면 키를 지우지 않아, 가짜 증명으로 남의 키를 지워 입장을 막지 못한다
12. 같은 키로 다시 입장 → 실패 - 키는 한 번만 쓰인다
13. 30초 지난 키 → 입장 실패
14. Redis에 남은 키 0 - 쓴 키는 지우고, 쓰지 않은 키는 30초 뒤 Redis가 지운다

**게임 구간 암호화**

15. 입장 뒤 암호문으로 인벤토리를 주고받음
16. 게임 연결에서 암호문 한 바이트를 바꾸면 끊김
17. 입장 전에 평문 명령을 보내면 끊김 - 평문으로 암호 통로를 건너뛰지 못하게

**Redis 장애**

18. Redis가 꺼지면 로그인 3번 모두 "서버 오류"
19. 3번에 5초 안 - 연결 1초 제한과 실패 뒤 5초 바로 실패. 멈춘 Redis가 인증 스레드·DB 스레드(저장도 함)를 오래 붙잡지 않는다

**정리**

20. 게임 서버 세션 0
21. 로그인 서버 세션 0

- **시험용 클라 명령**: `auth`(세션 키만 받아 출력), `enter`(받은 키로 입장, `bad`면 증명을 틀리게), `authrepeat`(한 연결에서 여러 번 로그인), `authbad`(로그인 구간 암호문 변조), `pinkey`(서버 공개 키 바꾸기), `tamper`(게임 구간 암호문 변조)
- **이 시험이 찾은 버그**: 응답 직후 바로 보낸 다음 요청을 로그인 서버가 "응답 전 요청"으로 끊던 순서(README_ERRORS 2-15). 6번 판정이 응답 4번에서 1번으로 떨어지면서 드러났다

### 2-2. `login_race` - 로그인 중 이중 로그인 (판정 3개)

같은 세션이 로그인을 처리하는 중(DB 스레드가 계정을 읽는 중)에 다른 아이디로 또 로그인한다. 20회 반복한다.

1. 두 번째 로그인을 보낸 세션은 모두 잘못된 패킷으로 끊김
2. 첫 아이디로 새 접속에서 다시 로그인 성공 - 아이디가 잠기지 않았다
3. 세션 0으로 돌아옴

- **왜**: 예전에는 한 세션이 두 계정에 로그인된 뒤 끊기면 뒤 계정만 로그아웃돼, 첫 아이디가 서버를 다시 켤 때까지 잠겼다. "로그인 중 표시를 계정보다 먼저 읽고, 표시를 내린 뒤 응답"으로 고쳤다
- **한계**: 경쟁 창이 나노초 수준이라 이 시험이 그 순간을 매번 재현하지는 않는다. 고친 순서가 정상 경로를 깨지 않는지와, 잠김이 없는지를 본다

### 2-3. `auction` - 경매장 (판정 10개)

판매자 1명, 입찰자 2명, 아무도 사지 않는 판매자 1명. 경매 기간을 `server.cfg`에서 잠시 5초로 줄인다.

1. 던전 중 등록 → 거절
2. 없는 아이템, 시작가 0 → 거절
3. 내 경매·낮은 값·골드 부족·최고 입찰자 재입찰·너무 빠른 입찰 → 각각 거절
4. 밀린 입찰자에게 환불 알림
5. 낙찰·판매·유찰 알림
6. 최종 골드: 판매자 121, 낙찰자 79, 밀린 사람 100, 유찰 100
7. 구경꾼 둘이 같은 알림을 같은 순서로 받음
8. DB의 아이템 위치: 낙찰품은 낙찰자, 유찰품은 판매자
9. DB 골드 = 로그 합계
10. DB 실패 0

- **왜**: 입찰 골드는 미리 빼고 밀리면 돌려준다. 입찰자 둘의 골드가 서로 다른 플레이어 락에서 움직이므로, 빠지거나 두 번 돌려주면 6·9번이 어긋난다. 알림은 경매장 락 안에서 보내므로 구경꾼 모두 같은 순서여야 한다(7번)

### 2-4. `restart` - 재시작 (판정 7개)

경매를 열고 입찰한 채 서버를 끄고 다시 켠다.

1. 1회차: 입찰로 골드 70
2. 재시작 때 열린 경매 정리 로그
3. 2회차: 입찰자 골드 100으로 환불
4. 2회차: 경매에 올렸던 아이템이 판매자에게 돌아옴
5. 2회차: 장비 착용이 남음
6. DB: 그 경매는 cancelled
7. DB 골드 = 로그 합계

- **왜**: 끌 때 열려 있던 경매는 다음 시작 때 취소·환불한다(이어 가지 않음). 바뀔 때마다 저장하므로 장비 착용도 재시작 뒤 남아야 한다

### 2-5. `reconnect` - DB 연결 끊김 (판정 5개)

서버가 도는 중에 DB 쪽에서 서버의 연결을 `KILL`한 뒤 장비를 착용한다.

1. 서버 쪽 DB 연결을 끊음
2. 장비 착용 성공
3. 끊김(2006·2013)을 감지하고 다시 연결
4. DB에 착용이 저장됨 - 같은 트랜잭션을 다시 실행했다
5. DB 실패 0

- **왜**: COMMIT 전에 끊긴 트랜잭션은 서버가 이미 되돌렸으니 한 번 더 실행하고, COMMIT 중에 끊기면 반영 여부를 몰라 다시 하지 않는다(골드 증감이 두 번 들어가면 안 된다). 이 시험은 앞의 경우를 본다

### 2-6. `admin` - 운영 툴 (판정 12개)

운영 툴(`AdminTool.exe`)로 회수·제재를 명령한다.

1. 운영자 포트는 127.0.0.1에만 열림
2. 키 없이 붙은 연결 4개가 5초 뒤 끊김 - 몇 안 되는 세션 칸을 막지 못하게
3. 회수 ① 경매 중인 아이템 - 경매 취소, 입찰자 환불
4. 회수 ② 접속한 계정의 착용 장비 - 메모리에서 꺼내고 착용도 벗긴다
5. 회수 ③ 로그인하지 않은 계정 - DB에서만 지운다
6. 없는 아이템 → 실패 응답
7. 분 입력 검증(빈 값·"1h" 거절)
8. 제재: DB에만 있는 계정, 없는 계정, 접속 중인 계정(끊김)
9. 차단 중 로그인 거절, 해제 뒤 로그인 성공
10. 아이템 이력에 한글 사유가 깨지지 않음
11. DB: 회수한 아이템 셋이 없음
12. DB 골드 = 로그 합계

- **왜**: 아이템이 있는 곳(경매장, 메모리 계정, DB만)에 따라 회수 경로가 다르고, 경로마다 메모리와 DB가 같이 바뀌어야 한다

### 2-7. `dungeon4` - 4명 던전 (판정 5개)

4명이 던전을 시작하고, 3초 뒤 차례가 아닌 파티원 하나가 나간다.

1. 첫 턴 알림은 10초, 파티원이 빠진 뒤 같은 턴 알림이 남은 시간(10초 미만)으로 다시 옴
2. 던전이 끝남(성공 또는 실패)
3. 남은 세 명의 던전 이벤트가 같은 순서
4. 나간 파티원은 "파티 없음" 알림
5. DB 실패 0

- **왜**: 던전은 파티 락 안에서만 판정하고 이벤트를 같은 순서로 보낸다. 이탈 때 차례를 다시 알리면서 남은 시간을 10초로 되돌리면 안 된다
- **결과가 매번 다름**: 주사위라 성공·실패는 판정하지 않고, 순서와 시간을 본다

### 2-8. `potion_full` - 인벤토리가 가득 찬 사람의 전리품 (판정 5개)

인벤토리가 가득 찬 계정과 여유 있는 계정이 조사로 회복약을 찾을 때까지 던전을 돈다(한 판 성공 확률 55%, 12판).

1. 가득 찬 사람에게 "버림" 알림
2. 여유 있는 사람에게 "받음" 알림
3. 두 파티원이 같은 알림을 같은 순서로
4. 가득 찬 계정은 아이템 32개 그대로
5. DB: 가득 찬 계정은 획득 로그가 없고, 받은 계정은 받은 만큼

- 환경: i5-8600(6코어 6스레드), 서버·클라·MySQL 9.4·Redis 3.0.504 모두 같은 PC 루프백, Release x64
- 2026-11-15 마지막 실행(커밋 `5fc2e47`): 8개 모두 PASS, 판정 68개 통과
- 같은 날 장시간 10분·봇 30개도 PASS - 봇 로그인 93번, 인증 실패 0, 예상밖끊김 0, 메모리 그대로([장시간 시험](game_soak.md))

**시험이 찾은 버그**

| 버그                              | 드러난 곳     | 기록           |
| --------------------------------- | ------------- | -------------- |
| 응답 직후 다음 요청을 끊던 순서   | `login` 6번   | 에러 기록 2-15 |
| 입장 직후 첫 암호문을 평문으로 봄 | 장시간 5분    | 에러 기록 2-14 |
| 시험 계정 해시에 안내 줄이 섞임   | 기존 시험 5개 | 시험 도구 수정 |

- 2-14는 기능 시험 8개는 통과했는데 장시간 시험에서만 드러났다. 봇은 응답을 받자마자 다음 요청을 보내므로, 사람 속도의 시험 클라로는 안 보이는 순서를 만든다

## 4. 시험 방식

- **서버 띄우기**: 시험마다 Redis(127.0.0.1, 비밀번호, 디스크 저장 끔) → 로그인 서버 → 게임 서버 순서로 띄우고, 끝나면 반대로 끈다. Redis 비밀번호는 명령줄에 쓰지 않고 잠깐 만든 설정 파일로 넘긴 뒤 지운다
- **계정은 DB에 직접 만든다**(`New-TestAccount`): 골드·아이템을 정해 넣고, 로그인 정보는 `LoginServer.exe --hash`로 받은 해시를 넣는다. 그래서 시험끼리 서로의 결과에 기대지 않고 몇 번이든 다시 돌릴 수 있다. 처음 보는 아이디를 쓰는 시험(`login`, `login_race`, `dungeon4`)은 클라의 `register`로 가입한다
- **시험 클라에 명령을 흘려 넣는다**: 콘솔 클라의 표준 입력에 명령을 쓰고, 끝난 뒤 출력 줄을 읽는다. 비밀번호를 빼면 시험용 기본값을 쓴다
- **판정은 세 곳에서 읽는다**: 클라 출력(알림·결과 문구), 서버 통계 줄(세션·잘못된패킷·DB실패), DB(`mysql.exe`로 골드·아이템·로그). DB 비밀번호는 환경 변수로만 넘기고 출력하지 않는다

## 5. 이 시험이 보지 못하는 것

- 같은 PC의 루프백이라 네트워크 지연·손실은 없다
- 경쟁은 일부러 만들 수 있는 것만 본다(`login_race`도 경쟁 창을 매번 재현하지는 않는다) - 드문 순서는 장시간 시험과 코드 리뷰가 맡는다
- 능동 중간자는 시험하지 않는다 - 서버 공개 키가 다를 때 클라가 막는 것(2-1의 8번)까지만 본다
- 처리량·지연은 재지 않는다

## 6. 다시 돌리기

`Game\Game.sln`을 Release x64로 빌드한 뒤 저장소 맨 위에서 실행한다. `Game\Server\db.cfg`(MySQL·Redis 접속 정보)와 `Game\Login\login.cfg`(페퍼·서버 비밀 키), `Game\Login\server_public.cfg`(서버 공개 키)가 있어야 한다 - 셋 다 저장소에 없고 같은 이름의 `.example`을 복사해 채운다. Redis 경로가 기본 위치와 다르면 환경 변수 `REDIS_DIR`을 준다.

```powershell
.\tools\game\run_all.ps1      # 8개 전부 - 시험마다 [result] 줄, 마지막에 [all] PASS/FAIL
.\tools\game\login.ps1        # 하나만
```

로그는 `%TEMP%\arkchimy_game_test\<시험 이름>\`(server.txt, login.txt)에 남는다. 시험은 `db.cfg`의 데이터베이스를 직접 고치므로 운영 데이터가 있는 DB로 돌리지 않는다.
