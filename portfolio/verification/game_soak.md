# 게임 서버 장시간 시험

봇 30개가 1시간 동안 실제 플레이처럼 던전·경매·장비·재접속을 반복하게 하고, 그동안 서버가 **조금씩 망가지는지**를 본다. 기능이 맞는지는 짧은 시험(`tools/game/run_all.ps1`)이 이미 확인한다. 이 시험은 짧은 시험으로는 드러나지 않는 문제 - 반복될수록 쌓이는 것, 드물게만 겹치는 순서 - 를 잡으려는 것이다.

## 1. 잡으려는 문제

| 문제                  | 짧은 시험에서 안 보이는 이유 | 판정                 |
| --------------------- | ---------------------------- | -------------------- |
| 메모리 누수           | 한 번에 몇 바이트씩 쌓인다   | 증가 20% 이하        |
| 핸들 누수             | 재접속 수백 번에 하나씩      | 핸들 추이(보고)      |
| 세션 해제 누락        | 드문 순서에서만 짝이 어긋남  | 끝난 뒤 세션 0       |
| 데드락·멈춤           | 드문 락 순서 겹침            | 매 분 행동 수가 는다 |
| 정상 클라를 끊는 오판 | 부하·타이밍이 겹칠 때만      | 예상밖끊김 0         |
| 드문 경쟁의 Assert    | 타이머·재접속·마감이 겹칠 때 | 덤프 없음, 정상 종료 |
| 메모리·DB 불일치 누적 | 저장 하나 빠져도 티가 안 남  | 골드 = 로그 합계     |
| 아이템 위치 꼬임      | 경매·회수·재시작이 겹칠 때   | 꼬인 아이템 0개      |
| DB 대기열 적체        | 1분 시험은 저장이 적다       | DB대기 최대 100 미만 |
| 오래 돈 뒤 종료 순서  | 타이머·DB·운영자가 다 바쁨   | 정상 종료, 세션 0    |

- **메모리 누수**: 세션 슬롯 재사용, 파티 만들기·지우기, 경매 등록·마감, DB 저장 요청(`std::function`), 턴 마감 대기열의 옛 항목처럼 계속 만들고 지우는 것이 많다. 계정은 메모리에서 내리지 않지만 봇이 30개로 고정이라 계정 수는 30에서 더 늘지 않는다 - 그래서 예열 뒤 메모리가 계속 오르면 데이터가 아니라 새는 것이다(서버 통계의 `계정` 수로 함께 확인).
- **핸들 누수**: 봇은 2–6분마다 스스로 끊고(절반은 RST) 다시 접속한다. 소켓을 닫지 않는 경로가 있으면 핸들이 재접속 수만큼 는다.
- **세션 해제 누락**: 처음 보는 아이디의 로그인은 `HoldSession` → DB 스레드 → `UnholdSession`, 던전 중 끊김은 파티·던전에서 빼기, 경매 구경꾼 지우기를 거친다. 짝이 하나라도 어긋나면 그 슬롯은 영영 돌아오지 않는다.
- **데드락·멈춤**: 락이 계정 표·파티 표·파티·플레이어·경매장·대기열로 여럿이고, 워커·턴 타이머·경매 타이머·DB 스레드가 함께 만진다. 서버가 멈춰도 봇은 끊기지 않으므로, 봇이 한 행동 수가 매 분 늘었는지로 본다.
- **정상 클라를 끊는 오판**: 봇은 정상 클라가 할 수 있는 행동만 한다. 서버가 봇을 끊으면(송신 링 넘침, 송신 정체, 잘못된 패킷 판정) 판정이 틀린 것이다 - 봇이 끊지 않았는데 끊긴 수를 `예상밖끊김`으로 센다.
- **드문 경쟁**: 턴 마감 타이머와 행동이 같은 턴에, 마감과 입찰이 같은 경매에, 재접속과 로그인 정리가 같은 아이디에 겹치는 순서는 짧은 시험에서 거의 나오지 않는다. 깨지면 `Assert`가 멈추고 덤프를 남긴다(`python tools\dump_info.py`로 확인).
- **메모리·DB 불일치 누적**: 골드는 바뀔 때마다 증감으로 저장하고 로그에 한 줄씩 남긴다. 저장이 하나라도 빠지거나 두 번 들어가면 계정의 DB 골드와 로그 합계가 어긋난다.
- **아이템 위치 꼬임**: 경매에 올린 아이템은 DB에서 경매 번호를 가진다. 마감·취소 저장이 빠지면 닫힌 경매를 가리키는 아이템이 남는다.

## 2. 조건

- 서버: `Game\x64\Release\GameServer.exe`, `server.cfg` 기본값(워커 2, 턴 10초, 경매 60초), MySQL 9.4(이 PC, 루프백)
- 봇: `GameBot.exe` 30개(계정마다 스레드 하나), 60분. 3명 한 조로 파티를 만들어 던전을 돌고, 차례가 오면 공격·조사·회복약 중에서 고른다(5%는 일부러 쉬어 턴 마감 타이머가 자동 방어). 로비에서는 0.5–3초마다 경매 등록·목록·입찰, 장비 착용, 구경 켜기·끄기, 가끔 파티 나가기 중 하나를 한다. 2–6분마다 스스로 끊고 다시 접속한다
- 수집: 1분마다 서버 통계 한 줄(메모리, 핸들, 세션, 로그인, 계정, 파티, 경매, DB대기, DB실패, 끊김 통계)과 봇 통계
- 실행: `.\tools\game\soak.ps1 -Minutes 60 -Bots 30` (결과 `%TEMP%\arkchimy_game_test\soak\samples.csv`, `server.txt`, `bot.txt`)

## 3. 판정 기준

- 봇: 예상밖끊김 0, 프로토콜오류(모르는 종류·길이) 0
- 서버: DB실패 0, 잘못된패킷·넘침끊김·송신정체끊김 0, 봇이 끝난 뒤 세션 0, 정상 종료, 새 덤프 없음
- 진행: 매 분 봇 행동 수가 늘었다(멈춘 분 0), DB대기 최대 100 미만
- DB: 봇 계정마다 골드 = 로그 합계, 닫힌 경매를 가리키는 아이템 0개
- 메모리: 예열(전체의 20% 지점) 뒤 → 마지막 증가 20% 이하. 핸들은 수치로 보고한다

## 4. 이 시험이 보지 못하는 것

- 서버와 봇, MySQL이 한 PC의 루프백이라 네트워크 지연·손실은 없다
- 봇은 정상 행동만 한다 - 조작된 패킷·폭주는 에코 시험(`portfolio/verification/test_cases.md`)과 리뷰가 맡는다
- 처리량 한계는 재지 않는다(봇 30개는 서버를 포화시키지 않는다). 목적은 오래 돌 때 쌓이는 문제다
- 1시간은 운영 기간보다 짧다 - 1시간이 깨끗하면 3시간으로 늘려 다시 본다
