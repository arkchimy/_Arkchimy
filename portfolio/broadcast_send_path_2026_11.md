# IOCP 서버 브로드캐스트 송신 경로: 모아 보내기를 넓히고 기본값을 다시 따지다

> 에코에서만 보장하던 모아 보내기를 브로드캐스트(채팅 방)로 넓히자 방 16에서 전달 처리량이 **9.6–9.9배**가 됐다. 보내는 시점을 "워커가 꺼낸 완료 묶음 끝"으로 넓히자 완료 통지 skip 방식이 skip을 끈 경우보다 빨라졌다(**+31–35%**). 그런데 기본값(수신마다 보내기 + skip)은 채팅에서 처리량이 1/3로 떨어지고 지연이 1.3초까지 밀리는 기아를 일으켰고, 이를 찾아 기본값을 묶음 단위로 바꿨다. 에코에서는 손해가 없었다.

앞 문서 [IOCP 서버 송신 경로 분석](../networkLibProject/docs/portfolio_send_path_draft_2026_10_26.md)의 후속이다. 앞 문서는 두 가지를 숙제로 남겼다.
- 모아 보내기는 **수신한 세션에게 돌려보내는 응답만** 모았다. 다른 세션으로 가는 송신(브로드캐스트)은 메시지마다 `WSASend`였다(앞 문서 6장 "적용 범위").
- 기본값(GQCSEx + skip)은 **에코로만** 재서 정했다(앞 문서 8-3).

## 핵심 결과

| 질문                     | 결과                                   |
| ------------------------ | -------------------------------------- |
| 방송은 얼마나 모이나     | `WSASend` 1번에 메시지 **1.06개**      |
| 받는 사람마다 모으면     | 방 16 전달 **9.6배** (30만 → 284만/s)  |
| 완료 묶음 끝으로 넓히면  | skip 켬이 skip 끔보다 **+24–35%**      |
| 기본값은 채팅에서도 맞나 | 아니었다 - 처리량 1/3, 최대 지연 1.3초 |

- 방송이 메시지마다 `WSASend`였던 것은 skip 켬(기본값)일 때다. skip 끔은 115–125개씩 모였지만 송신 완료 대기라는 우연에 기댄 것이었다(2장).
- 받는 사람마다 모으자 CPU / 전달이 89% 줄고 방 락 보유가 100 → 3.1µs가 됐다(3장).
- 완료 묶음 끝으로 넓히자 여러 보낸 사람의 메시지가 합쳐져 `WSASend` 1번에 152개가 실렸고, skip 켬이 지연도 더 짧았다(4장).
- 기본값(수신 단위 + skip)의 기아는 다른 PC에서 최대 지연 6초로 정상 클라이언트가 무응답 판정에 끊긴 것으로 드러났다. 기본값을 묶음 단위로 바꿨고 에코는 차이 없었다(5장).

## 1. 측정 환경

- **PC B**(Core i5-8600, 6코어 6스레드)만 썼다. 서버와 클라이언트가 같은 PC인 루프백이다. 기아 증상만 PC A(노트북)에서 처음 봤고, 숫자는 섞지 않는다.
- 비교는 같은 실행 안에서 조건을 번갈아 돌리고, 회차마다 순서를 바꿔 3회 중앙값을 냈다.
- **채팅 데모**(`networkLibProject/ChatServer.h`): 방에 입장한 세션이 보낸 메시지를 방 전원(보낸 사람 포함)에게 뿌린다. 방 256개, 세션 256개, 방 크기 1/4/16. 방 크기 1은 에코와 같아 **대조 조건**이다.
- **부하 클라이언트**(LoadClient 채팅 모드): 세션마다 32B 메시지 16개를 묶어 보내고, 자기 메시지 16개가 방송으로 돌아오면 다음 묶음을 보낸다.
- **순서 검사**: 서버가 방 락 안에서 방 순번을 매기고, 같은 락 안에서 방 전원의 송신 링에 넣는다. 클라이언트는 방 순번이 +1씩 오는지 본다. 어긋나면 멈추므로 모든 측정이 순서·누락 검사를 통과한 결과다.
- 지표
  - **전달/s**: 방송 1번 × 방 인원. 서버가 받는 사람 송신 링에 넣은 메시지 수
  - **`WSASend` 1번당 메시지**: 넣은 메시지 수 ÷ 송신 완료 수. 모아 보내기가 되는지 보는 지표
  - **CPU / 전달**: 서버 CPU 시간 ÷ 전달 수
  - 지연: 11-01 측정은 서버가 보낸 핑의 왕복, 11-03 측정은 클라이언트가 잰 자기 메시지 왕복이다. **서로 다른 지표라 장을 넘어 비교하지 않는다**

## 2. 기준값: 브로드캐스트는 메시지마다 `WSASend`였다

**skip을 켜면(기본값) 방송은 `WSASend` 1번에 메시지 1.06개였다. skip을 끄면 115–125개로 모였지만, 그것은 송신 완료가 큐에서 기다리는 동안 생긴 우연이었다.**

| 워커 | 방  | skip | 전달/s | `WSASend`당 | CPU / 전달 |
| ---- | --- | ---- | ------ | ----------- | ---------- |
| 2    | 1   | 켬   | 116만  | 15.1        | 1.46µs     |
| 2    | 1   | 끔   | 117만  | 14.5        | 1.48µs     |
| 2    | 16  | 켬   | 29만   | **1.06**    | 6.81µs     |
| 2    | 16  | 끔   | 521만  | 115         | 0.39µs     |
| 4    | 16  | 켬   | 43만   | **1.06**    | 7.38µs     |
| 4    | 16  | 끔   | 741만  | 125         | 0.41µs     |

- 원인은 앞 문서 6장의 적용 범위 그대로다. `OnRecv(A)` 안에서 B에게 보내면 "수신 처리 중인 세션이 아님"으로 판단해 바로 `postSend`를 건다. skip이면 송신이 그 자리에서 끝나 송신 중 표시가 바로 꺼지므로, 다음 메시지도 또 `WSASend`를 건다.
- skip을 끄면 송신 완료가 IOCP 큐에서 4.8–6.6ms 기다리는 동안 송신 중 표시가 켜져 있어 다른 구성원의 메시지가 쌓인다. 앞 문서 4장의 "우연한 모아 보내기"가 다른 세션 쪽에서 다시 나타난 것이다.
- 부작용: skip 켬에서 방 락 보유가 105–130µs였다. 방 락 안에서 구성원 16명에게 `WSASend`를 16번 걸었기 때문이다.
- 방 1(대조)은 둘이 같다. 문제는 브로드캐스트에만 있다.

## 3. 받는 사람마다 모아 보내기

**"수신 처리 중인 세션 하나"만 기억하던 것을 "이번 수신 처리에서 보낼 게 생긴 세션 목록"으로 넓혔다. 방 16 전달이 9.6–9.9배가 됐고, `WSASend`가 방 락 밖으로 나갔다.**

`SendPacket`은 받는 사람이 누구든 링에 넣고 목록에 올리기만 한다. 수신 처리가 끝나면 목록의 세션마다 `WSASend`를 한 번씩 건다. 컨텐츠 코드는 그대로 `SendPacket`만 부른다.

```cpp
static thread_local bool tbDeferSend = false;	// 이 스레드가 지금 수신 처리 중 - 송신은 링에 쌓기만 한다
static thread_local std::vector<Session*> tSendTargets;	// 보낼 게 생긴 세션 - 각자 I/O 카운트를 하나씩 잡고 있다

void NetworkLib::addSendTarget(Session& session)
{
	if (session.mbSendTarget.exchange(true))
	{
		return;	// 이미 어느 워커의 목록에 있다 - 그 워커가 보낼 때 이번 것도 같이 나간다
	}
	++session.mIoCount;	// 목록에 있는 동안 해제되지 않게
	tSendTargets.push_back(&session);
}

void NetworkLib::flushSends()
{
	for (Session* session : tSendTargets)
	{
		session->mbSendTarget = false;	// 링을 읽기 전에 내린다 - 그 뒤에 넣은 스레드는 자기 목록에 다시 올린다
		postSend(*session);	// 링에 쌓인 전부를 WSASend 1번으로
		decIoCount(*session);
	}
	tSendTargets.clear();
}
```
- 플래그는 **`postSend` 전에** 내린다. 뒤에 내리면, `postSend`가 링을 읽은 뒤 다른 워커가 넣은 메시지가 "이미 목록에 있음"으로 처리되어 아무도 보내지 않게 된다.
- 목록은 워커 시작 때 최대 세션 수만큼 `reserve`한다. 세션은 목록에 최대 한 번이라 재할당이 없다.
- 에코는 목록이 {보낸 사람} 하나라 앞 문서 6장 구조와 같다(특수한 경우).

수정 전·후 빌드를 같은 실행 안에서 번갈아 돌렸다(skip 켬, 3회).

| ---- | --- | ------------- | --------- | ----------- |
| 2    | 16  | 30만 → 284만  | **9.6배** | 1.06 → 15.7 |
| 4    | 16  | 43만 → 426만  | **9.9배** | 1.06 → 16.1 |
| 2    | 4   | 37만 → 236만  | 6.5배     | 1.29 → 15.5 |

| ---- | --- | ------------- | ------------- | ------------ |

- **남은 차이**: 방 16에서 skip 끔이 여전히 1.8–2배 빨랐다(`WSASend`당 116–126 vs 16). 보내는 시점이 "수신 1건 끝"이라 보낸 사람 1명의 묶음(16개)만 합쳐지고, 여러 보낸 사람의 메시지는 합쳐지지 않았기 때문이다.

## 4. 보내는 시점을 완료 묶음 끝으로

**보내는 시점을 "워커가 GQCSEx로 꺼낸 완료(최대 64개)를 다 처리한 뒤"로 넓히자 여러 보낸 사람의 메시지가 받는 사람마다 합쳐졌다. skip을 켠 채로 skip 끔보다 빨라졌고 지연도 짧아졌다.**

설정 `mergeSends`(송신 합치기 범위)로 고를 수 있게 했다. 0이면 수신 완료 하나마다(3장, 이하 "수신 단위"), 1이면 꺼낸 완료 묶음마다(이하 "묶음 단위") 보낸다.

```cpp
// runWorkerLoopGqcsEx - 완료를 최대 mGqcsBatch개씩 꺼낸다
bOk = GetQueuedCompletionStatusEx(mIOCP, entries.data(), mGqcsBatch, &count, INFINITE, FALSE);
if (mbMergeSends)
{
	tbDeferSend = true;	// 이 묶음에서 생긴 송신은 묶음 끝에서 받는 사람마다 한 번에
}
for (ULONG i = 0; i < count; ++i)
{
	handleCompletion(...);	// 수신 완료면 completeRecv → OnRecv → SendPacket(링에 쌓기만)
}
if (mbMergeSends)
{
	tbDeferSend = false;
	flushSends();
}
```
- 수신 처리(`completeRecv`)는 `tbDeferSend`가 이미 켜져 있으면 보내기를 묶음 끝에 맡긴다. 켠 쪽이 끈다.
- **타이머로 기다리지 않는다.** 한가할 때는 꺼내는 완료가 1–2개라 거의 기다리지 않고, 바쁠수록 묶음이 커져 더 많이 합쳐진다. 모이는 양이 부하에 따라 저절로 조절된다.

보내는 단위 × skip 네 조합을 같은 실행에서 번갈아 돌렸다(방 16, 3회, 값은 워커 2 / 4).

| 조합                 | 전달/s             | `WSASend`당 | 지연 p50           |
| -------------------- | ------------------ | ----------- | ------------------ |
| 수신 단위 · skip     | 285만 / 434만      | 16          | 13.7 / 10.6ms      |
| **묶음 단위 · skip** | **705만 / 1041만** | 152         | **5.8 / 3.2ms**    |
| 수신 단위 · skip 끔  | 565만 / 768만      | 118–126     | 9.7–10 / 7.4–7.5ms |
| 묶음 단위 · skip 끔  | 556만 / 784만      | 117–126     | 9.7–10 / 7.4–7.5ms |

- 수신 단위 · skip의 지연은 같은 날 세 방식만 비교한 측정에서 가져왔다(처리량은 두 측정이 같았다).

- **skip 끔에서는 묶음 단위가 효과가 없다.** 송신 중 표시가 송신 완료 처리까지(4.6–6.4ms) 켜져 있어, 묶음 끝에 `postSend`를 불러도 그냥 돌아가고 결국 완료 처리 때 나간다. 우연한 창이 설계한 창을 덮는다.
- **skip을 켜야 설계한 창(묶음 처리 시간)이 작동한다.** 그 창이 우연한 창(송신 완료 대기 약 5ms)보다 넓으면서 지연은 짧았다.

## 5. 기본값이 채팅에서 기아를 일으켰다

**기본값(수신 단위 + skip)은 채팅에서 처리량이 1/3로 떨어지고 메시지 최대 지연이 1.3초까지 밀렸다. 하트비트를 잘 보내던 클라이언트가 무응답으로 끊긴 것이 단서였다. 기본값을 묶음 단위로 바꿨고, 에코에서는 손해가 없었다.**

**증상**(PC A, 채팅에 무응답 판정을 넣은 뒤): 하트비트를 1초마다 보내는 클라이언트가 "5초 무응답"으로 83건 끊기고, 정상 채팅 클라이언트도 247건 끊겼다. 메시지 최대 지연은 5.96초였다. skip을 끄면 끊김 0, 최대 지연 0.06초, 수신 처리량 3배였다. 무응답 판정이 서버 쪽 기아를 드러낸 것이다.

**재현**(PC B, 같은 조건: 채팅 256세션 + 하트비트만 보내는 64세션, 방 16, 워커 2, 20초, 3회)

| 합치기 범위 · skip             | 수신/s     | `WSASend`당 | 최대 지연       |
| ------------------------------ | ---------- | ----------- | --------------- |
| 수신 단위 · skip (당시 기본값) | 11.7만     | 16          | **0.57–1.29초** |
| **묶음 단위 · skip**           | **38.1만** | 223         | **18–31ms**     |
| 수신 단위 · skip 끔            | 28.6만     | 134         | 21–54ms         |
| 묶음 단위 · skip 끔            | 27.9만     | 134         | 20–24ms         |

- PC B에서는 지연이 5초 기준에 못 미쳐 끊김까지는 가지 않았지만, 방향은 PC A와 같다.
- **원인**: 수신 단위라 받은 패킷마다 `WSASend`를 거의 한 번씩 부른다(4장 표 첫 줄과 같은 상황). 처리량이 떨어진 만큼 큐에 완료가 밀리고 지연이 늘었다.
- skip 즉시 완료를 그 자리에서 이어 처리하는 반복이 워커를 붙잡는 것도 후보였지만, 묶음 단위 · skip의 최대 지연이 18–31ms라 이 조건에서는 드러나지 않았다. 반복 횟수 상한은 넣지 않고 보류했다.

**결정: 기본값을 `mergeSends = 1`(묶음 단위)로 바꿨다.** 에코에서도 확인했다(32B × 16, skip, 3회).

에코: 수신 단위와 묶음 단위 (skip 켬)

| 합치기 범위 | 워커 2  | 워커 4  |
| ----------- | ------- | ------- |
| 수신 단위   | 126만/s | 122만/s |
| 묶음 단위   | 123만/s | 123만/s |

묶음 단위에서 skip 끔과 켬 (워커 2 / 4)

| 항목            | skip 끔         | skip 켬            |
| --------------- | --------------- | ------------------ |
| 채팅 전달/s     | 604만 / 859만   | **791만 / 1163만** |
| 채팅 CPU / 전달 | 0.331 / 0.361µs | 0.255 / 0.295µs    |
| 채팅 지연 p50   | 11.4 / 7.9ms    | 8.3 / 6.0ms        |
| 채팅 지연 p99   | 13.2 / 11.3ms   | 9.9 / 9.2ms        |
| 에코 패킷/s     | 134만 / 131만   | 132만 / 130만      |

- 에코는 두 표 모두 범위가 겹친다(차이 없음). 채팅은 skip 켬이 전달 +31% / +35%다.

- 에코는 한 번에 꺼내는 완료가 1.1–1.4개라 더 합칠 것이 없어 차이가 없다.
- 결론: **묶음 단위 + skip 켬**이 채팅과 에코 모두에서 가장 좋다. 앞 문서 8-3의 "skip은 브로드캐스트에서 손해일 수 있다"는 우려는 수신 단위 때문이었고, 묶음 단위에서는 반대로 skip이 이긴다.

## 6. 남은 문제: 묶음 단위의 넘침

**창을 넓힌 만큼 받는 사람의 송신 링에 더 오래 쌓인다. 방 인원이 고정되지 않는 부하에서 정상 클라이언트가 넘침으로 끊길 수 있어, 컨텐츠 제약(방 인원 상한 등)으로 다룬다.**

- B가 워커 1의 보낼 목록에 올라 있는 동안 다른 워커들은 B에게 넣기만 한다. 워커 1의 묶음이 길어지면 B의 링에 "보낸 사람마다 한 바퀴분"이 아니라 **여러 바퀴분**이 쌓인다. 미루는 구조를 만들 때 "미루는 동안 쌓일 수 있는 최대량"을 다른 스레드가 여러 바퀴 도는 경우까지 넣어 계산해야 했다.
- 방 16 고정 부하(이 문서의 측정)에서는 넘침이 나지 않았다. 방을 계속 옮기는 시험(방 인원이 16명으로 고정되지 않음)에서는 워커 4 · 묶음 단위에서 15초에 23–69건 났고, 옮기지 않으면 0건이었다.
- 서버 쪽 대책 후보(링이 절반을 넘으면 묶음 끝을 기다리지 않고 바로 보내기)도 있지만, 들어오는 양이 빼 가는 속도보다 계속 빠르면 어떤 버퍼 크기로도 막을 수 없다. 그래서 받는 양 자체를 컨텐츠가 제한하는 쪽(방 인원 상한, 보낸 사람 속도 제한)으로 다루기로 했다.
- 서버가 포화된 상태에서 끊김 정책이 정상 클라이언트를 오판하지 않는지는 따로 확인했다 - [섞인 클라이언트 합격 시험](mixed_clients_test_2026_11_03.md)(포화 1.98/2에서 정상·하트비트 클라이언트 끊김 0).

## 7. 한계

- 모든 크기(9.6배, +31% 등)는 이 환경(루프백, 32B 메시지, 방 16 고정, closed-loop 부하)의 숫자다. "WSASend 호출 횟수가 비용을 정하고, 모으는 창은 우연이 아니라 설계로 만들어야 한다"는 방향만 일반화한다.
- 채팅 데모는 워커에서 방 락을 잡고 직접 처리한다. 로직 스레드에서 처리하는 구조는 재지 않았다(그 경우 로직 스레드용 보내기 경계를 따로 설계해야 한다).
- 11-01 측정(2–4장)과 11-03 측정(5장) 사이에 송신 넘침 판정이 바뀌었다("아직 보내지 않은 몫 16KB 초과" → "송신 링 32KB 가득"). 각 장 안의 비교는 같은 판정끼리다.
- 기아의 PC A 숫자와 나머지 PC B 숫자는 섞지 않았다.
