# IOCP 서버 브로드캐스트 송신 경로: 모아 보내기를 넓히고 기본값을 다시 따지다

> 에코에서만 보장하던 모아 보내기를 브로드캐스트(채팅 방)로 넓히자 방 16에서 전달 처리량이 **12.7–12.9배**가 됐다. 보내는 시점을 "워커가 꺼낸 완료 묶음 끝"으로 넓히자 skip을 켠 채로 수신 단위의 **1.33–2.4배**가 되어 skip 끔과 같은 처리량에 도달했고, 송신 완료 대기는 사라졌다. 당시 기본값(수신 단위 + skip)은 채팅에서 전달 처리량이 2.6분의 1이고 최대 지연도 가장 길어, 기본값을 묶음 단위로 바꿨다. 에코에서는 손해가 없었다.

> **수치 기준:** 2026-11-05 PC B `/O2` 재측정 값이다(서버·클라이언트를 그 커밋에서 다시 빌드, 원본과 표는 [결과](../실험폴더/portfolio_o2_2026_11_05/결과.md)). 이전 측정은 서버가 `/Od` 빌드였고, 그 값은 이력으로만 밝혔다.

앞 문서 [IOCP 서버 송신 경로 분석](../networkLibProject/docs/portfolio_send_path_draft_2026_10_26.md)의 후속이다. 앞 문서는 두 가지를 숙제로 남겼다.
- 모아 보내기는 **수신한 세션에게 돌려보내는 응답만** 모았다. 다른 세션으로 가는 송신(브로드캐스트)은 메시지마다 `WSASend`였다(앞 문서 6장 "적용 범위").
- 기본값(GQCSEx + skip)은 **에코로만** 재서 정했다(앞 문서 8-3).

## 핵심 결과

| 질문                     | 결과                                       |
| ------------------------ | ------------------------------------------ |
| 방송은 얼마나 모이나     | `WSASend` 1번에 메시지 **1.06개**          |
| 받는 사람마다 모으면     | 방 16 전달 **12.7배** (30.4만 → 387만/s)   |
| 완료 묶음 끝으로 넓히면  | 수신 단위의 **2.4배**, skip 끔과 같은 수준 |
| 기본값은 채팅에서도 맞나 | 아니었다 - 전달 2.6분의 1, 지연 가장 김    |

- 방송이 메시지마다 `WSASend`였던 것은 skip 켬(기본값)일 때다. skip 끔은 68–139개씩 모였지만 송신 완료 대기라는 우연에 기댄 것이었다(2장).
- 받는 사람마다 모으자 CPU / 전달이 92% 줄고 방 락 보유가 94 → 0.91µs가 됐다(3장).
- 완료 묶음 끝으로 넓히자 여러 보낸 사람의 메시지가 합쳐져 `WSASend` 1번에 59개(워커 2)가 실렸다(4장).
- 기본값(수신 단위 + skip)의 문제는 `/Od` 당시 정상 클라이언트가 무응답 판정에 끊긴 것으로 드러났다. `/O2`에서는 끊기지 않지만 네 조합 중 가장 느리고 최대 지연이 가장 길다. 기본값을 묶음 단위로 바꿨고 에코는 손해가 없었다(5장).

## 1. 측정 환경

- **PC B**(Core i5-8600, 6코어 6스레드), 전원 모드 균형 조정. 서버와 클라이언트가 같은 PC인 루프백이다. 서버·클라이언트 모두 `/O2`다.
- 옛 구조는 그 커밋을 `/O2`로 다시 빌드해 쟀다. 수정 전 `6754260`, 수신 단위 모으기 `649aa97`, 지금 구조 `3fed5a1`이다.
- 비교는 같은 실행 안에서 조건을 번갈아 돌리고, 회차마다 순서를 바꿔 3회 중앙값을 냈다(15초, 기아 시험 20초). 실행 전·중 CPU 상위 프로세스를 기록해, 다른 프로세스가 코어 절반 이상을 쓴 회차는 다시 쟀다.
- **채팅 데모**(`networkLibProject/ChatServer.h`): 방에 입장한 세션이 보낸 메시지를 방 전원(보낸 사람 포함)에게 뿌린다. 방 256개, 세션 256개, 방 크기 1/4/16. 방 크기 1은 에코와 같아 **대조 조건**이다.
- **부하 클라이언트**(LoadClient 채팅 모드): 세션마다 32B 메시지 16개를 묶어 보내고, 자기 메시지 16개가 방송으로 돌아오면 다음 묶음을 보낸다.
- **순서 검사**: 서버가 방 락 안에서 방 순번을 매기고, 같은 락 안에서 방 전원의 송신 링에 넣는다. 클라이언트는 방 순번이 +1씩 오는지 본다. 어긋나면 멈추므로 모든 측정이 순서·누락 검사를 통과한 결과다.
- 지표
  - **전달/s**: 방송 1번 × 방 인원. 서버가 받는 사람 송신 링에 넣은 메시지 수
  - **`WSASend` 1번당 메시지**: 넣은 메시지 수 ÷ 송신 완료 수. 모아 보내기가 되는지 보는 지표
  - **CPU / 전달**: 서버 CPU 시간 ÷ 전달 수
  - 지연: 2–3장은 서버가 보낸 핑의 왕복, 4–5장은 클라이언트가 잰 자기 메시지 왕복이다. **서로 다른 지표라 장을 넘어 비교하지 않는다**

## 2. 기준값: 브로드캐스트는 메시지마다 `WSASend`였다

**skip을 켜면(기본값) 방송은 `WSASend` 1번에 메시지 1.06개였다. skip을 끄면 많이 모였지만, 그것은 송신 완료를 처리하기 전까지 쌓인 우연이었다.**

| 워커 | 방  | skip | 전달/s | `WSASend`당 | CPU / 전달 |
| ---- | --- | ---- | ------ | ----------- | ---------- |
| 2    | 1   | 켬   | 127만  | 16          | 1.19µs     |
| 2    | 1   | 끔   | 127만  | 15.5        | 1.24µs     |
| 2    | 16  | 켬   | 30.4만 | **1.06**    | 6.41µs     |
| 2    | 16  | 끔   | 945만  | 68–139      | 0.21µs     |
| 4    | 16  | 켬   | 45.6만 | **1.06**    | 7.15µs     |
| 4    | 16  | 끔   | 830만  | 32–41       | 0.35µs     |

- 원인은 앞 문서 6장의 적용 범위 그대로다. `OnRecv(A)` 안에서 B에게 보내면 "수신 처리 중인 세션이 아님"으로 판단해 바로 `postSend`를 건다. skip이면 송신이 그 자리에서 끝나 송신 중 표시가 바로 꺼지므로, 다음 메시지도 또 `WSASend`를 건다. 워커 2에서 skip 끔의 약 31분의 1이다.
- skip을 끄면 송신 완료까지 1–3ms가 걸리고(워커 2 3.0ms, 워커 4 1.0ms), 그동안 송신 중 표시가 켜져 있어 다른 구성원의 메시지가 쌓인다. 앞 문서 4장의 "우연한 모아 보내기"가 다른 세션 쪽에서 다시 나타난 것이다.
- 우연이라 불안정하다. 워커 2 skip 끔의 3회 값은 135, 139, 68개였고, 워커 4 skip 끔은 정상 클라이언트가 넘침으로 끊겼다(26, 103, 565건).
- 부작용: skip 켬에서 방 락 보유가 94–124µs였다. 방 락 안에서 구성원 16명에게 `WSASend`를 16번 걸었기 때문이다.
- 방 1(대조)은 둘이 같다. 문제는 브로드캐스트에만 있다.

## 3. 받는 사람마다 모아 보내기

**"수신 처리 중인 세션 하나"만 기억하던 것을 "이번 수신 처리에서 보낼 게 생긴 세션 목록"으로 넓혔다. 방 16 전달이 12.7–12.9배가 됐고, `WSASend`가 방 락 밖으로 나갔다.**

`SendPacket`은 받는 사람이 누구든 링에 넣고 목록에 올리기만 한다. 수신 처리가 끝나면 목록의 세션마다 `WSASend`를 한 번씩 건다. 컨텐츠 코드는 그대로 `SendPacket`만 부른다.

```cpp
static thread_local std::vector<Session*> tSendTargets;	// 보낼 게 생긴 세션 - 각자 I/O 카운트를 하나씩 잡고 있다

void NetworkLib::addSendTarget(Session& session)
{
	if (session.mbSendTarget.exchange(true))
	{
		return;	// 이미 어느 워커의 목록에 있다 - 그 워커가 보낼 때 이번 것도 같이 나간다
	}
	++session.mIoCount;	// 목록에 있는 동안 해제되지 않게
	tSendTargets.push_back(&session);
}

void NetworkLib::flushSends()
{
	for (Session* session : tSendTargets)
	{
		session->mbSendTarget = false;	// 링을 읽기 전에 내린다 - 그 뒤에 넣은 스레드는 자기 목록에 다시 올린다
		postSend(*session);	// 링에 쌓인 전부를 WSASend 1번으로
		decIoCount(*session);
	}
	tSendTargets.clear();
}
```
- 플래그는 **`postSend` 전에** 내린다. 뒤에 내리면, `postSend`가 링을 읽은 뒤 다른 워커가 넣은 메시지가 "이미 목록에 있음"으로 처리되어 아무도 보내지 않게 된다.
- 목록은 워커 시작 때 최대 세션 수만큼 `reserve`한다. 세션은 목록에 최대 한 번이라 재할당이 없다.
- 에코는 목록이 {보낸 사람} 하나라 앞 문서 6장 구조와 같다(특수한 경우).

수정 전·후 빌드를 같은 실행 안에서 번갈아 돌렸다(skip 켬, 3회).

처리량 (수정 전 → 후)

| 워커 | 방  | 전달/s         | 배율       | `WSASend`당 |
| ---- | --- | -------------- | ---------- | ----------- |
| 2    | 16  | 30.4만 → 387만 | **12.7배** | 1.06 → 16.4 |
| 4    | 16  | 45.6만 → 588만 | **12.9배** | 1.06 → 17.0 |
| 2    | 4   | 40.0만 → 302만 | 7.5배      | 1.31 → 16.1 |
| 4    | 4   | 50.8만 → 317만 | 6.2배      | 1.31 → 16.2 |
| 2    | 1   | 127만 → 126만  | 같음       | 16 → 16     |

비용과 지연 (수정 전 → 후)

| 워커 | 방  | CPU / 전달    | 방 락 보유    | 서버 핑 p50  |
| ---- | --- | ------------- | ------------- | ------------ |
| 2    | 16  | 6.41 → 0.52µs | 94 → 0.91µs   | 105 → 10.6ms |
| 4    | 16  | 7.15 → 0.55µs | 124 → 1.25µs  | 72 → 9.3ms   |
| 2    | 4   | 5.08 → 0.59µs | 18.7 → 0.25µs | 20.7 → 4.8ms |

- 방 1(대조)은 그대로다. 이득은 다른 세션으로 가는 송신을 모은 데서 왔다.
- **남은 차이**: 방 16에서 skip 끔이 여전히 2.5배(워커 2, 955만 vs 387만), 1.35배(워커 4, 793만 vs 588만) 빨랐다. 보내는 시점이 "수신 1건 끝"이라 보낸 사람 1명의 묶음(16개)만 합쳐지고, 여러 보낸 사람의 메시지는 합쳐지지 않았기 때문이다.

## 4. 보내는 시점을 완료 묶음 끝으로

**보내는 시점을 "워커가 GQCSEx로 꺼낸 완료(최대 64개)를 다 처리한 뒤"로 넓히자 여러 보낸 사람의 메시지가 받는 사람마다 합쳐졌다. skip을 켠 채로 skip 끔과 같은 처리량이 됐고, 송신 완료 대기는 사라졌다.**

설정 `mergeSends`(송신 합치기 범위)로 고를 수 있게 했다. 0이면 수신 완료 하나마다(3장, 이하 "수신 단위"), 1이면 꺼낸 완료 묶음마다(이하 "묶음 단위") 보낸다.

```cpp
// runWorkerLoopGqcsEx - 완료를 최대 mGqcsBatch개씩 꺼낸다
bOk = GetQueuedCompletionStatusEx(mIOCP, entries.data(), mGqcsBatch, &count, INFINITE, FALSE);
for (ULONG i = 0; i < count; ++i)
{
	handleCompletion(...);	// 수신 완료면 completeRecv → OnRecv → SendPacket(링에 쌓기만)
}
flushSends();	// 이 묶음에서 생긴 송신을 받는 사람마다 한 번에

// completeRecv 끝 - 수신 단위일 때만 여기서 보낸다
if (!mConfig.bMergeSends)
{
	flushSends();
}
```
- `SendPacket`은 워커 스레드에서만 받는다. 다른 스레드에는 모은 것을 보내 줄 `flushSends`가 없어, 링에 넣지 않고 `false`를 돌려준다.
- **타이머로 기다리지 않는다.** 한가할 때는 꺼내는 완료가 1–2개라 거의 기다리지 않고, 바쁠수록 묶음이 커져 더 많이 합쳐진다. 모이는 양이 부하에 따라 저절로 조절된다.

보내는 단위 × skip 네 조합을 같은 실행에서 번갈아 돌렸다(`3fed5a1`, 방 16, 3회, 값은 워커 2 / 4).

| 조합             | 전달/s        | `WSASend`당 | 지연 p50    | 지연 p99    |
| ---------------- | ------------- | ----------- | ----------- | ----------- |
| 수신 단위 · skip | 411만 / 636만 | 16 / 17     | 15.9 / 10.2 | 20.7 / 18.9 |
| 묶음 단위 · skip | 993만 / 846만 | 59 / 29     | 6.5 / 8.2   | 7.6 / 9.6   |
| 수신 단위 · 끔   | 951만 / 826만 | 65 / 30     | 6.3 / 8.3   | 10.5 / 10.4 |
| 묶음 단위 · 끔   | 965만 / 842만 | 65 / 31     | 6.3 / 8.3   | 9.9 / 9.9   |

- 지연 단위는 ms다.
- **skip 켬에서 묶음 단위는 수신 단위의 2.4배 / 1.33배다.** skip 끔에서는 +1.5% / +2%로 효과가 없다. 송신 중 표시가 송신 완료 처리까지(1.7ms / 182µs) 켜져 있어, 묶음 끝에 `postSend`를 불러도 그냥 돌아가고 결국 완료 처리 때 나간다. 우연한 창이 설계한 창을 덮는다.
- **묶음 단위에서 skip 켬과 끔의 처리량은 차이가 없다**(+2.9% / +0.5%, 범위 겹침). skip 켬의 이득은 송신 완료까지 1723 → 7µs(워커 2), CPU / 전달 −2.5% / −3.9%, 지연 p99 9.9 → 7.6ms(워커 2) / 9.9 → 9.6ms(워커 4)다. **`/Od` 때 본 "skip 켬이 +31–35%"는 재현되지 않았다.**
- 방 4는 네 조합이 비슷하고(307만–345만) 방 옮기기 없는 96회 모두 정상 클라이언트 끊김과 넘침이 0이다.

**워커 수를 늘리면 오히려 덜 모인다.** 묶음 단위 · skip, 방 16, 3회.

| 워커 | 전달/s | `WSASend`당 | 꺼낸 완료 | 서버 코어 |
| ---- | ------ | ----------- | --------- | --------- |
| 1    | 709만  | 111         | 64        | 1.03      |
| 2    | 993만  | 59          | 20        | 1.97      |
| 3    | 928만  | 38          | 4.3       | 2.51      |
| 4    | 846만  | 29          | 2.5       | 2.90      |
| 5    | 816만  | 26          | 1.9       | 3.15      |
| 6    | 839만  | 27          | 1.9       | 3.03      |

- 워커가 늘면 완료가 덜 쌓여 한 번에 꺼내는 수가 줄고, 그만큼 덜 합쳐진다는 추정과 방향이 맞다. 원인은 확정하지 못했다. 이 PC에서는 워커 2가 가장 높고, 측정 중 다른 프로세스는 15% 이하였다. PC A에서는 워커 6까지 올랐다(숫자는 섞지 않는다).

## 5. 기본값을 묶음 단위로 바꾼 이유

**수신 단위 + skip은 채팅에서 전달 처리량이 2.6분의 1이고 최대 지연이 가장 길었다. 하트비트를 잘 보내던 클라이언트가 무응답으로 끊긴 것이 단서였다. 기본값을 묶음 단위로 바꿨고, 에코에서는 손해가 없었다.**

**단서**(PC A, 당시 서버 `/Od`, 채팅에 무응답 판정을 넣은 뒤): 하트비트를 1초마다 보내는 클라이언트가 "5초 무응답"으로 83건 끊기고, 정상 채팅 클라이언트도 247건 끊겼다. 메시지 최대 지연은 5.96초였다. skip을 끄면 끊김 0이었다. 무응답 판정이 서버 쪽 처리 지연을 드러낸 것이다.

**`/O2` 재측정**(같은 조건: 채팅 256세션 + 하트비트만 보내는 64세션, 방 16, 워커 2, 20초, 3회)

| 합치기 범위 · skip           | 수신/s | 전달/s | `WSASend`당 | 최대 지연 |
| ---------------------------- | ------ | ------ | ----------- | --------- |
| 수신 단위 · skip (옛 기본값) | 20.0만 | 397만  | 16          | 33–68ms   |
| 묶음 단위 · skip             | 50.8만 | 1013만 | 62          | 14–15ms   |
| 수신 단위 · skip 끔          | 53.6만 | 1020만 | 66–139      | 16ms      |
| 묶음 단위 · skip 끔          | 55.3만 | 1052만 | 139         | 16–51ms   |

- 12회 모두 무응답·넘침·클라이언트 끊김이 0이다. **`/O2`에서 수 초 기아는 재현되지 않았다.** 최대 지연 1.3초(PC B)와 6초(PC A)는 `/Od` 당시 값이다. 수신 단위 · skip이 가장 느리다는 방향은 그대로다.
- 이 조건에서는 묶음 단위 · skip 끔이 skip 켬보다 전달이 3.8% 높고 범위도 겹치지 않는다(1034만–1113만 vs 1006만–1015만). 대신 skip 켬은 최대 지연이 안정적이다(14–15ms vs 16–51ms).
- **원인**: 수신 단위 + skip이라 수신 완료 1건마다 받는 사람 수만큼 `WSASend`를 부른다(4장 표 첫 줄과 같은 상황).

**결정: 기본값을 `mergeSends = 1`(묶음 단위)로 바꿨다.** 에코에서도 확인했다(32B × 16, 3회).

에코: 수신 단위와 묶음 단위 (skip 켬)

| 합치기 범위 | 워커 2  | 워커 4  |
| ----------- | ------- | ------- |
| 수신 단위   | 133만/s | 128만/s |
| 묶음 단위   | 142만/s | 129만/s |

묶음 단위에서 skip 끔과 켬 (워커 2 / 4)

| 항목            | skip 끔         | skip 켬         |
| --------------- | --------------- | --------------- |
| 채팅 전달/s     | 965만 / 842만   | 993만 / 846만   |
| 채팅 CPU / 전달 | 0.201 / 0.358µs | 0.196 / 0.344µs |
| 채팅 지연 p50   | 6.3 / 8.3ms     | 6.5 / 8.2ms     |
| 채팅 지연 p99   | 9.9 / 9.9ms     | **7.6** / 9.6ms |

- 에코는 한 번에 꺼내는 완료가 1–1.6개라 더 합칠 것이 없다. 4KB × 1도 skip과 무관하게 약 6만/s로 같다.
- 결론: **묶음 단위 + skip 켬**을 유지한다. 처리량은 skip 끔과 같고, 송신 완료 대기를 없애며 CPU와 p99가 약간 낮다. skip이 처리량을 올려서가 아니라, **skip 켬에서도 skip 끔만큼 모으면서 완료 대기를 없앨 수 있어서**다.

## 6. 남은 문제: 묶음 단위의 넘침

**창을 넓힌 만큼 받는 사람의 송신 링에 더 오래 쌓인다. 방 인원이 고정되지 않는 부하에서 정상 클라이언트가 넘침으로 끊길 수 있어, 컨텐츠 제약(방 인원 상한 등)으로 다룬다.**

- B가 워커 1의 보낼 목록에 올라 있는 동안 다른 워커들은 B에게 넣기만 한다. 워커 1의 묶음이 길어지면 B의 링에 "보낸 사람마다 한 바퀴분"이 아니라 **여러 바퀴분**이 쌓인다. 미루는 구조를 만들 때 "미루는 동안 쌓일 수 있는 최대량"을 다른 스레드가 여러 바퀴 도는 경우까지 넣어 계산해야 했다.
- 방 16 고정 부하에서는 PC B `/O2` 지금 구조로 워커 1–6 모두 넘침이 없었다. 방을 계속 옮기는 시험(방 인원이 16명으로 고정되지 않음)에서는 워커 4 · 묶음 단위에서 15초에 23–69건 났고, 옮기지 않으면 0건이었다(PC B, 당시 `/Od`, 재측정 안 함).
- 서버 쪽 대책 후보(링이 절반을 넘으면 묶음 끝을 기다리지 않고 바로 보내기)도 있지만, 들어오는 양이 빼 가는 속도보다 계속 빠르면 어떤 버퍼 크기로도 막을 수 없다. 그래서 받는 양 자체를 컨텐츠가 제한하는 쪽(방 인원 상한, 보낸 사람 속도 제한)으로 다루기로 했다.
- 서버가 바쁜 상태에서 끊김 정책이 정상 클라이언트를 오판하지 않는지는 따로 확인했다 - [섞인 클라이언트 합격 시험](mixed_clients_test_2026_11_03.md)(서버 1.86/2에서 정상·하트비트 클라이언트 끊김 0).

## 7. 한계

- 모든 크기(12.7배 등)는 이 환경(루프백, 32B 메시지, 방 크기 고정, closed-loop 부하)의 숫자다. "`WSASend` 호출 횟수가 비용을 정하고, 모으는 창은 우연이 아니라 설계로 만들어야 한다"는 방향만 일반화한다.
- 조건마다 3회 측정이고, 전원 모드를 고정하지 않았다(균형 조정). 다른 프로세스 확인은 실행 전·중 각 1회 표본이다.
- 채팅 데모는 워커에서 방 락을 잡고 직접 처리한다. 로직 스레드에서 처리하는 구조는 재지 않았다(그 경우 로직 스레드용 보내기 경계를 따로 설계해야 한다).
- 옛 구조(2–3장, 넘침 판정 "아직 보내지 않은 몫 16KB 초과")와 지금 구조(4–5장, "송신 링 32KB 가득")는 넘침 판정이 다르다. 각 장 안의 비교는 같은 판정끼리다. 3장 수정 후 빌드도 워커 4 방 16에서 정상 클라이언트 넘침이 1, 0, 1건 있었다.
- 기아의 첫 증상은 PC A 숫자이고 나머지는 PC B 숫자다. 섞어 비교하지 않았다.
