## 1. 무엇을 막나

| 상황                                     | TCP에 맡기면                      | 서버가 볼 것             |
|------------------------------------------|-----------------------------------|--------------------------|
| 클라가 안 읽음 (window 0, 멈춘 앱, 공격) | 끊지 않음                         | 걸린 WSASend가 안 끝남   |
| 회선이 나쁨, 보낼 데이터 있음            | 재전송 한계까지 수십 초           | 걸린 WSASend가 안 끝남   |
| 클라가 사라짐, 보낼 데이터 없음          | keepalive 기본 2시간              | 한동안 아무것도 안 받음  |

- 위 두 줄은 **송신 정체**(정함, 11-02): `mbSendFlag && now - 송신 건 시각 > N초`
- 아래 줄은 **무응답**: `now - 마지막 수신 시각 > N초` - 클라가 한가할 때도 주기적으로 보내야 한다(하트비트)

### 2-1. 누가 언제 검사하나

- **A. 감시 스레드가 1초마다 세션 전부를 돈다 (추천)**
  - 1000세션이면 1초에 비교 2000번 - 수 µs. 핫패스(수신·송신)에는 시각 쓰기 하나만 더해진다
  - 워커와 독립이라 워커가 멈춰도 감시는 돈다(예전 핑 스레드에서 배운 것 - 측정기·감시기는 대상과 독립)
  - 끊을 때는 `tryIncIoCount` → `requestDisconnect` → `decIoCount`. 해제와 `OnRelease`는 지금처럼 워커에서 일어난다
- B. 순회 없는 만료 구조(타이머 휠 등)
  - 수신·송신 때마다 세션을 만료 칸 사이로 옮겨야 한다 - 초당 수십만 번인 핫패스에 락이나 리스트 조작이 붙는다
  - 아끼는 것은 1초에 수 µs인 순회 비용이라 바꾸는 값이 맞지 않는다
- C. 워커가 GQCS 대기 시간 초과 때 검사
  - 워커가 바쁘면 시간 초과가 안 걸려 검사가 밀리고, 워커가 멈추면 감시도 멈춘다

- 11-02 설계 문서 B의 "주기 순회 없음"(하트비트를 순회 없이 하려던 계획)을 A로 바꾸는 결정이다

의견: 감시 스레드 1개가 모든 세션에대해서 순회를 해야하겠구나. 그러면 이 감시 스레드가 네트워크 라이브러리 자체적으로 구현이 되야하는가? 라는 의문이 생기네

답: 두 검사의 성격이 다르다. **송신 정체는 라이브러리, 무응답은 값만 컨텐츠(설정)가 정하는** 쪽을 추천한다.
- 송신 정체(`mbSendFlag`, 송신 건 시각)는 **라이브러리만 볼 수 있는 상태**다. 컨텐츠는 송신 링도 걸린 WSASend도 모른다 → 라이브러리가 검사해야 한다
- 무응답은 "몇 초면 죽은 것으로 보나"가 정책이다. 그래도 검사 자체는 같은 순회에서 비교 한 번이라, 따로 두면 스레드만 늘어난다 → 순회는 라이브러리가 하고, **기준 시간은 설정(0이면 끔)**으로 받는다. "라이브러리는 메커니즘, 정책은 밖에서"를 지키는 방식
- 컨텐츠 고유의 판정(로그인 제한 시간, 잠수 유저 등)은 지금처럼 컨텐츠가 `Disconnect(id)`로 한다. 라이브러리 감시는 **전송 계층의 죽은·막힌 연결**만 맡는다
- 다른 방식과 비교

| 방식                                         | 장점                         | 단점                                              |
|----------------------------------------------|------------------------------|---------------------------------------------------|
| A. 라이브러리가 감시 스레드를 가짐 (추천)    | 컨텐츠가 잊어도 항상 동작    | 라이브러리 스레드가 하나 늘어남                   |
| B. 라이브러리는 `CheckTimeouts()`만, 호출은 밖 | 스레드 정책을 컨텐츠가 정함  | 안 부르면 보호가 없음, 워커와 독립인지 호출에 달림 |

- 선례: 예전 핑 측정도 라이브러리 안의 전용 스레드였다(워커와 독립이어야 워커가 멈춘 시간도 잡힘). 감시도 같은 이유로 워커와 독립이어야 한다

결정: 송신 정체는 A안. 하트비트의 판정은 컨턴체의 영역으로하자.

반영(3판):
- 라이브러리 감시 스레드는 **송신 정체만** 본다(`mbSendFlag && now - 송신 건 시각 > N초`)
- 무응답(하트비트) 판정은 컨텐츠가 한다 → 라이브러리에 수신 시각(`mLastRecvTick`)과 `무응답끊김`·무응답 설정이 **필요 없어진다**
- 이 결정 때문에 2-3의 추천이 바뀐다(하트비트를 컨텐츠가 봐야 하므로 라이브러리가 삼키면 안 된다)

### 2-2. 시각을 어떻게 남기나

- **수신**: 수신 완료마다 `Session::mLastRecvTick`(atomic, `GetTickCount64`)에 쓴다
  - 초 단위 판정이라 ms 정밀도면 충분하고 QPC보다 싸다. 쓰는 쪽은 그 세션의 수신을 처리하는 워커 하나뿐
- **송신**: 지금 있는 `mWsaSendQPC`를 쓴다. 다만 지금은 `mbSendFlag`를 락 안에서 켠 **뒤** 락 밖에서 쓴다
  - 감시가 락 안에서 "플래그 켜짐"을 본 순간 시각은 아직 **이전 송신 것**일 수 있다 → 정상 클라를 오래 걸린 것으로 오판
  - → 시각 쓰기를 플래그와 같은 락 안으로 옮기고, 감시는 `mSendLock`을 잡고 둘을 함께 읽는다(1초에 1000번 - 무시할 만함)

의견: 'GetTickCount64' 대신에 'timeGetTime은' 안되는지?

답: 판정에는 둘 다 충분하다. 차이는 아래와 같고 **`GetTickCount64`를 추천**한다.

| 항목         | `GetTickCount64`          | `timeGetTime`                                        |
|--------------|---------------------------|------------------------------------------------------|
| 크기         | 64비트, 넘어감 없음       | 32비트(DWORD), 49.7일마다 0으로 돌아감               |
| 정밀도       | 10–16ms                   | 기본 수 ms, `timeBeginPeriod(1)`이면 1ms             |
| 비용         | 공유 메모리 읽기 - 매우 쌈 | 비슷하게 쌈                                          |
| 의존         | kernel32                  | winmm.lib 링크 필요                                  |

- 판정 단위가 초라 정밀도 차이는 의미가 없다
- `timeGetTime`을 쓰면 서버가 50일 넘게 돌 때 값이 돌아간다. `(DWORD)(now - last)`처럼 부호 없는 뺄셈이면 안전하지만, 실수하면 끊기 판정이 틀린다 → 64비트로 처음부터 없애는 편이 낫다
- 세션당 4바이트 아끼는 것은 의미가 없다(세션 1000개 = 4KB)

결정: timeGetTime로 사용 수신은 `mLastRecvTick`(atomic) 수신 완료마다 갱신, 송신 시각 쓰기는 `mbSendFlag`와 같은 `mSendLock` 안으로 옮긴다(사용자, 2026-11-03). 시각 함수는 위 답을 보고 확정

반영(3판):
- 시각 함수는 `timeGetTime`(사용자 결정). 경과 시간은 항상 `DWORD` 부호 없는 뺄셈(`now - last`)으로 구해 49.7일 넘어감을 처리한다
- 2-1 결정으로 라이브러리의 수신 시각은 필요 없어졌다 → 수신 시각과 `timeGetTime`은 **컨텐츠의 무응답 판정**(채팅 데모)에서 쓴다
- 송신 정체: 송신 건 시각 쓰기를 `mSendLock` 안으로 옮긴다. 시각 값은 확인 필요 - (a) 지금 있는 `mWsaSendQPC`(QPC)를 그대로 쓴다(필드 추가 없음, 송신 대기 시간 측정과 공유) / (b) `timeGetTime` 값을 따로 둔다(결정과 같은 함수로 통일, 필드 4바이트 추가)
- 결정(4판): **(a) 기존 `mWsaSendQPC`를 그대로 쓴다**(사용자, 2026-11-03)

### 2-3. 하트비트 패킷 형식

- **A. 헤더만(페이로드 길이 0) - 라이브러리가 시각만 갱신하고 `OnRecv`로 넘기지 않는다 (추천)**
  - 헤더에 종류를 넣지 않는다는 원칙을 지키면서 구분된다. 컨텐츠는 하트비트를 몰라도 된다
  - 잃는 것: 컨텐츠가 길이 0 메시지를 쓸 수 없다. 지금 EchoClient 생성기는 길이 0–4096을 만들므로 1–4096으로 바꿔야 한다(채팅은 이미 길이 0을 잘못된 패킷으로 끊는다)
- B. 라이브러리는 무엇을 받든 시각만 갱신하고, 하트비트 형식은 컨텐츠가 정한다(예: 채팅 `Ping` 종류)
  - 컨텐츠마다 만들어야 하고, 하트비트가 `OnRecv`까지 올라간다
- 공통: 서버는 하트비트에 답하지 않는다(서버는 측정·반사를 하지 않는다 - 11-01 결정). 서버가 죽은 것은 클라가 따로 판단한다

의견: 페이로드가 0이라는것은 인코딩되지도, 시퀀스 넘버도 들어가지않은 상태의 패킷인데. 상대가 connect을 한뒤 페이로드 길이 0짜리만을 넘기면 계속해서 서버의 자원을 묶을것같은데 어떨까?

답: 맞다. 다만 이건 **하트비트 형식의 문제가 아니라, 무응답 판정이 막는 범위의 문제**다.
- 무응답 판정이 막는 것은 **죽은 연결**(클라가 사라짐)이다. "살아 있지만 쓸모없는 연결"은 막지 못한다. 하트비트에 페이로드나 순번을 넣어도 같다 - 공격자는 그 형식대로 보내면 된다
- 살아 있는 연결이 자원을 묶는 것은 따로 막아야 한다

| 막는 방법                                    | 누가        | 막는 것                                              |
|----------------------------------------------|-------------|------------------------------------------------------|
| 로그인 제한 시간(접속 후 N초 안에 인증)      | 컨텐츠      | 인증 안 한 연결이 하트비트만으로 버티기              |
| 인증 후 잠수 제한(의미 있는 요청 없이 N분)   | 컨텐츠      | 인증한 유저의 자리 차지                              |
| 최대 세션 수(`maxSession`, 이미 있음)        | 라이브러리  | 전체 자원 상한                                       |
| IP당 연결 수 제한                            | 라이브러리 또는 앞단 | 한 곳에서 연결을 많이 여는 것               |
| 하트비트 빈도 제한(초당 N개 넘으면 끊기)     | 라이브러리  | 길이 0 패킷을 쏟아 CPU를 쓰게 하는 것                |

- 인코딩·순번: 암호화(세션별 키, AES-GCM 예정)를 넣으면 **페이로드가 0이어도 인증 태그가 붙는다**(GCM은 빈 평문에도 태그를 만든다). 그때는 하트비트도 키 없이는 위조할 수 없다. 지금 형식을 길이 0으로 정해도 암호화 때 막히지 않는다
- 그래서 추천은 그대로 A(길이 0, 라이브러리가 삼킴)이고, 위 표 중 **로그인 제한 시간은 채팅 데모 때 컨텐츠에, 하트비트 빈도 제한은 이번에 라이브러리에** 넣는 것을 제안한다(빈도 제한은 수신 처리에서 카운터 하나)
- 정정: 위 암호화 문단은 부정확했다. GCM이면 빈 평문에도 태그(16B)가 붙어 **회선 위 길이는 0이 아니다**. 그때는 "복호화한 페이로드가 0바이트"로 구분해야 한다

반영(3판) - 2-1 결정으로 추천을 **B(컨텐츠가 정함)**로 바꾼다
- 무응답 판정을 컨텐츠가 하므로, 컨텐츠가 하트비트를 **봐야** 한다. A처럼 라이브러리가 삼키면 컨텐츠는 하트비트가 왔는지 모른다
- B면 하트비트는 그냥 컨텐츠 메시지 하나다(예: 채팅 `Heartbeat` 종류 - 페이로드 첫 바이트). 라이브러리는 아무것도 안 바꾼다: 길이 0 특수 처리, EchoClient 생성기 수정(0–4096 → 1–4096) 모두 필요 없다
- 컨텐츠는 `OnRecv`마다(하트비트든 다른 메시지든) 세션의 마지막 수신 시각을 `timeGetTime`으로 적고, 자기 타이머로 30초 넘은 세션을 `Disconnect(id)`한다
- 자원을 묶는 클라(위 표)도 컨텐츠 몫이 된다: 로그인 제한 시간, 하트비트 빈도 제한 모두 컨텐츠가 메시지 종류를 보고 정한다

결정: **B - 하트비트 형식과 판정은 컨텐츠가 정한다**(사용자, 2026-11-03). 라이브러리는 길이 0 특수 처리를 하지 않는다

### 2-4. N 값과 설정

- **송신 정체 10초, 무응답 30초(클라 하트비트 10초 간격이면 3간격 동안 아무것도 안 온 것), `server.cfg` 키 + 0이면 끔 (추천)**
  - 시험 때는 짧게(예: 3초) 바꿔 15초 시험 안에서 확인한다 - 그래서 상수보다 설정이 낫다
  - setter는 다른 설정처럼 `Start` 전에만(`Assert(!mbRunning)`)
- 송신 정체 10초면 "초당 약 3KB(링 32KB ÷ 10초)도 못 받아 가는 클라"를 끊는 셈이다
- 끊으면 통계 `송신정체끊김`, `무응답끊김`을 따로 센다(지금 `넘침끊김`과 구분)

의견: 클라 하트비트를 놓칠수가 있나? tcp로 하는거아니야?

답: 맞다. TCP라 **잃어버리지는 않는다.** "3번 놓친 것"은 틀린 표현이라 본문을 "3간격 동안 아무것도 안 온 것"으로 고쳤다. 놓치는 게 아니라 **늦게 오는** 경우가 있어서 간격보다 넉넉히 잡는다.
- 나쁜 회선: 세그먼트를 잃으면 TCP가 다시 보내는데, 재전송 대기가 0.2초 → 0.4초 → 0.8초…로 늘어 몇 초 늦을 수 있다
- 클라가 멈춤: 앱이 잠깐 멈추거나(로딩, 모바일 백그라운드) 하트비트 앞에 큰 데이터가 쌓여 있으면 그만큼 늦게 나간다
- 서버가 바쁨: 수신 완료가 IOCP 큐에서 기다리면 시각 갱신도 늦어진다
- 정말 계속 못 가면 TCP가 재전송을 포기하고 연결을 끊는데(Windows 기본 약 20초 이상), 그때는 수신 실패로 원래 경로에서 끊긴다
- 그래서 무응답 30초는 "하트비트 10초 간격 + 늦게 와도 오판하지 않을 여유"이고, 송신 정체 10초는 하트비트와 무관하다(서버가 보낸 것을 클라가 안 받아 가는 경우)

결정: 송신 정체 10초, 무응답 30초, `server.cfg` 키(0이면 끔), `Start` 전에만 설정(사용자, 2026-11-03)

반영(3판): 2-1 결정으로 라이브러리 설정은 **송신 정체 10초만**(`server.cfg`, 0이면 끔). 무응답 30초는 컨텐츠(채팅 데모) 설정으로 옮긴다

## 3. 시험

- 받지 않는 클라 → `송신정체끊김` 또는 `넘침끊김`(서버가 많이 보내면 링 32KB가 먼저 찬다)
  - 송신 정체만 따로 보려면 링이 차기 전에 막혀야 한다: 4장 5번의 시험 클라(작은 수신 버퍼, 링보다 적게 보냄) + 기준 3초로 15초 시험 안에서 확인
- 정상 에코·채팅 클라 → `송신정체끊김` 0 (기준 3초로 줄여도 0이어야 오판이 없다는 근거)
- 무응답(아무것도 보내지 않는 클라)은 컨텐츠 몫이라 채팅 데모 때 시험한다

- 5번 주의: 서버 `WSASend`는 커널 송신 버퍼로 복사되면 끝나고, 클라 커널 수신 버퍼도 수십 KB 이상이다. 받지 않는 클라가 조금 보내면 에코가 두 커널 버퍼에 다 들어가 **정체가 안 생기고**, 많이 보내면 링 32KB가 차서 **넘침이 먼저** 난다. 보내는 양만으로 그 사이를 맞추기는 불안정하다
  - → 시험 클라는 `SO_RCVBUF`를 작게(예: 1KB) 잡고 받지 않으며, 보내는 양은 링보다 작게(예: `bytesPerConn` 16KB). 그러면 클라 수신 창이 금방 0이 되고, 서버 커널 송신 버퍼가 찬 뒤 WSASend가 대기로 남아 정체만 생긴다. 서버 송신 버퍼 크기 때문에 안 되면 `sendBufZero` 시험 옵션으로 서버 쪽도 줄인다(구현 때 확인)

- 감시 스레드는 송신을 걸거나 완료를 처리하지 않는다 - 끊기 요청만 하고, 해제와 `OnRelease`는 지금처럼 워커에서 일어난다
- `Stop` 순서: 감시 스레드를 먼저 멈춘다(세션을 다 끊는 중에 감시가 같은 세션을 잡지 않게)

- 시험은 `sendBufZero`로 커널 송신 버퍼를 없애 결정적으로 재현했다

### 5-1. 기본 송신 버퍼에서 제로 윈도 클라를 끊는가 (2026-11-03, PC A, 판정 기준 3초)

받지 않는 클라(`recv`를 부르지 않음, 수신 버퍼 1KB → 수신 창 0)가 보낸 양 = 서버가 돌려줘야 할 양만 바꿨다. 서버는 기본 송신 버퍼, 정상 EchoClient와 동시에 실행.

| 쌓이는 양          | 넘침끊김   | 송신정체끊김 | 무엇이 끊었나                                           |
|--------------------|------------|--------------|---------------------------------------------------------|
| 16KB, 64KB         | 0          | 0            | 끊지 않음 - 서버 커널 송신 버퍼에 다 들어감             |

- 모든 경우 정상 클라 끊김 0, 정상 종료
- **이 PC의 서버 커널 송신 버퍼는 약 64KB**로 보인다(64KB까지 흡수, 72KB부터 대기). 송신 정체가 맡는 구간은 약 64–96KB, 그 위는 넘침
- 결론: 제로 윈도 클라는 쌓이는 양이 커널 버퍼(~64KB)를 넘으면 **송신 정체 또는 넘침으로 반드시 끊긴다**. 그 아래에서는 끊지 않는다 - 커널 버퍼 64KB는 OS가 소켓마다 상한을 두는 몫이고, 서버가 그 클라에게 더 보낼 일이 생기면(채팅 방송 등) 곧 위 구간으로 올라간다. 보낼 것도 받을 것도 없이 붙잡고만 있는 클라는 무응답(컨텐츠) 판정의 몫
