## 1. 무엇을 막나

| 상황                                     | TCP에 맡기면                      | 서버가 볼 것             |
|------------------------------------------|-----------------------------------|--------------------------|
| 클라가 안 읽음 (window 0, 멈춘 앱, 공격) | 끊지 않음                         | 걸린 WSASend가 안 끝남   |
| 회선이 나쁨, 보낼 데이터 있음            | 재전송 한계까지 수십 초           | 걸린 WSASend가 안 끝남   |
| 클라가 사라짐, 보낼 데이터 없음          | keepalive 기본 2시간              | 한동안 아무것도 안 받음  |

- 위 두 줄은 **송신 정체**(정함, 11-02): `mbSendFlag && now - 송신 건 시각 > N초`
- 아래 줄은 **무응답**: `now - 마지막 수신 시각 > N초` - 클라가 한가할 때도 주기적으로 보내야 한다(하트비트)

### 2-1. 누가 언제 검사하나

- **A. 감시 스레드가 1초마다 세션 전부를 돈다 (추천)**
  - 1000세션이면 1초에 비교 2000번 - 수 µs. 핫패스(수신·송신)에는 시각 쓰기 하나만 더해진다
  - 워커와 독립이라 워커가 멈춰도 감시는 돈다(예전 핑 스레드에서 배운 것 - 측정기·감시기는 대상과 독립)
  - 끊을 때는 `tryIncIoCount` → `requestDisconnect` → `decIoCount`. 해제와 `OnRelease`는 지금처럼 워커에서 일어난다
- B. 순회 없는 만료 구조(타이머 휠 등)
  - 수신·송신 때마다 세션을 만료 칸 사이로 옮겨야 한다 - 초당 수십만 번인 핫패스에 락이나 리스트 조작이 붙는다
  - 아끼는 것은 1초에 수 µs인 순회 비용이라 바꾸는 값이 맞지 않는다
- C. 워커가 GQCS 대기 시간 초과 때 검사
  - 워커가 바쁘면 시간 초과가 안 걸려 검사가 밀리고, 워커가 멈추면 감시도 멈춘다

- 11-02 설계 문서 B의 "주기 순회 없음"(하트비트를 순회 없이 하려던 계획)을 A로 바꾸는 결정이다

### 2-2. 시각을 어떻게 남기나

- **수신**: 수신 완료마다 `Session::mLastRecvTick`(atomic, `GetTickCount64`)에 쓴다
  - 초 단위 판정이라 ms 정밀도면 충분하고 QPC보다 싸다. 쓰는 쪽은 그 세션의 수신을 처리하는 워커 하나뿐
- **송신**: 지금 있는 `mWsaSendQPC`를 쓴다. 다만 지금은 `mbSendFlag`를 락 안에서 켠 **뒤** 락 밖에서 쓴다
  - 감시가 락 안에서 "플래그 켜짐"을 본 순간 시각은 아직 **이전 송신 것**일 수 있다 → 정상 클라를 오래 걸린 것으로 오판
  - → 시각 쓰기를 플래그와 같은 락 안으로 옮기고, 감시는 `mSendLock`을 잡고 둘을 함께 읽는다(1초에 1000번 - 무시할 만함)

### 2-3. 하트비트 패킷 형식

- **A. 헤더만(페이로드 길이 0) - 라이브러리가 시각만 갱신하고 `OnRecv`로 넘기지 않는다 (추천)**
  - 헤더에 종류를 넣지 않는다는 원칙을 지키면서 구분된다. 컨텐츠는 하트비트를 몰라도 된다
  - 잃는 것: 컨텐츠가 길이 0 메시지를 쓸 수 없다. 지금 EchoClient 생성기는 길이 0–4096을 만들므로 1–4096으로 바꿔야 한다(채팅은 이미 길이 0을 잘못된 패킷으로 끊는다)
- B. 라이브러리는 무엇을 받든 시각만 갱신하고, 하트비트 형식은 컨텐츠가 정한다(예: 채팅 `Ping` 종류)
  - 컨텐츠마다 만들어야 하고, 하트비트가 `OnRecv`까지 올라간다
- 공통: 서버는 하트비트에 답하지 않는다(서버는 측정·반사를 하지 않는다 - 11-01 결정). 서버가 죽은 것은 클라가 따로 판단한다
