# 에러와 해결 방법 기록

세션을 시작할 때 CLAUDE.md가 이 파일을 함께 불러온다. 같은 에러를 다시 겪지 않도록, 새 에러를 해결하면 아래 형식으로 추가한다.

형식: **증상**(실제 메시지) → **원인** → **해결** → **재발 방지**

---

## 1. 환경·도구 (2026-10-24 ~ 10-25)

### 1-1. `git commit -m`에 큰따옴표가 있으면 커밋 실패
- **증상**: `error: pathspec '완료 출력 ...' did not match any file(s) known to git`
- **원인**: PowerShell 5.1이 네이티브 명령에 인자를 넘길 때, 문자열 안의 `"`에서 인자를 잘못 나눈다.
- **해결**: 커밋 메시지를 파일로 쓰고 `git commit -F 파일`로 커밋.
- **재발 방지**: 커밋 메시지는 항상 파일로 넘긴다. 파일은 BOM 없는 UTF-8(`New-Object Text.UTF8Encoding($false)`)로 쓴다. BOM이 있으면 메시지 첫 글자 앞에 섞인다.

### 1-2. PowerShell 스크립트(.ps1) 실행 시 파싱 오류
- **증상**: `Missing ')' in function parameter list.` - 한글 주석 부분이 `?대뜑 湲곗?`처럼 깨져 보임
- **원인**: PowerShell 5.1은 BOM 없는 파일을 ANSI(CP949)로 읽는다. UTF-8 한글이 깨지면서 문법이 무너진다.
- **해결**: `.ps1`을 BOM 있는 UTF-8로 다시 저장.
- **재발 방지**: `.ps1`을 새로 만들면 BOM을 붙인다. Write 도구로 만든 새 파일은 BOM이 없으므로 저장 후 변환한다.

### 1-3. 새 C++ 헤더에서 엉뚱한 컴파일 오류
- **증상**: `warning C4819: 현재 코드 페이지(949)에서 표시할 수 없는 문자가...`, `error C2447: '{': 함수 헤더가 없습니다`, `C2065: 'PacketHeader': 선언되지 않은 식별자` (새로 만든 `PacketHeader.h`)
- **원인**: BOM 없는 UTF-8 파일을 MSVC가 CP949로 읽어 한글 주석이 다음 줄 코드를 삼켰다.
- **해결**: 헤더를 BOM 있는 UTF-8로 저장.
- **재발 방지**: C++ 소스·헤더, `.vcxproj`/`.filters`는 BOM 있는 UTF-8. 기존 파일은 이미 BOM이 있고, 수정할 때 인코딩을 유지한다.

### 1-4. cfg 파일을 못 읽음
- **증상**: `설정 파일 오류 err=5 key=癤?/`
- **원인**: `ParserLib`가 BOM을 키의 일부로 읽는다. PowerShell 5.1의 `Set-Content -Encoding UTF8`은 BOM을 붙인다.
- **해결**: `[IO.File]::WriteAllText(경로, 내용, (New-Object Text.UTF8Encoding($false)))`로 BOM 없이 저장.
- **재발 방지**: **cfg만 BOM 없음**(소스·스크립트와 반대). 측정 스크립트가 `server.cfg`를 바꿀 때도 BOM 없이 쓰고 원본 바이트로 복원한다.

### 1-5. Git Bash에 `jq`, `python`, `node`가 없음
- **증상**: `jq: command not found`, `node: command not found`
- **해결**: JSON 확인은 PowerShell `ConvertFrom-Json`.

### 1-6. 빌드 끝에 `'pwsh.exe'은(는) 내부 또는 외부 명령...이 아닙니다`
- **원인**: 프로젝트의 빌드 후 이벤트가 PowerShell 7을 찾는다.
- **해결**: 결과물(exe)은 정상 생성된다. 무시해도 된다.

### 1-7. `Start-Process -PassThru`로 띄운 프로세스의 종료 코드가 빈 값
- **해결**: 종료 확인은 출력 로그(`[main] 종료 완료`)로 한다.

### 1-8. 백그라운드로 띄운 서버를 정상 종료할 방법이 없음
- **증상**: 서버가 콘솔 키(`Q`) 입력으로만 끝나서, 자동 테스트에서 `stop()` 경로를 실행할 수 없었다.
- **해결**: 서버 종료를 Ctrl+C(`SetConsoleCtrlHandler`)로 바꾸고, `tools/send_ctrlc.ps1`이 대상 프로세스 콘솔에 붙어(`AttachConsole`) Ctrl+C를 보낸다(`GenerateConsoleCtrlEvent`).
- **참고**: EchoClient·LoadClient는 여전히 `Q` 키라 테스트에서는 강제 종료한다. 그래서 클라가 종료 시 찍는 요약(탐침 RTT 전체)은 테스트 로그에 남지 않는다.

### 1-9. 세션 임시 폴더에 둔 테스트 스크립트가 사라짐
- **원인**: scratchpad 폴더는 세션 전용이다.
- **해결**: 재사용할 스크립트는 저장소 `tools/`에 둔다(`echo_test.ps1`, `send_ctrlc.ps1`, `load_sweep.ps1`).

### 1-10. 전원 모드 확인 명령이 안 됨
- **증상**: `powercfg /getoverlayscheme` → `매개 변수가 잘못되었습니다.`
- **원인**: 이 Windows 버전(25H2)에서 지원하지 않는다. 설정 명령(`/overlaysetactive`)은 동작한다.
- **해결**: 현재 모드는 레지스트리 `HKLM\SYSTEM\CurrentControlSet\Control\Power\User\PowerSchemes`의 `ActiveOverlayAcPowerScheme`로 읽는다. 최고 성능 `ded574b5-45a0-4f42-8737-46345c09c238`, 균형 조정 `00000000-0000-0000-0000-000000000000`.
- **재발 방지**: 측정 전후로 레지스트리 값을 확인하고, 끝나면 균형 조정으로 되돌린다(`finally`에서).

### 1-11. 성능 카운터를 영어 경로로 못 읽음
- **원인**: 한국어 Windows는 성능 카운터 이름이 현지화돼 `\Processor Information(...)` 경로가 맞지 않는다.
- **해결**: 이름이 현지화되지 않는 WMI 클래스 `Win32_PerfFormattedData_Counters_ProcessorInformation`을 쓴다. 실효 클럭 = `ProcessorFrequency × PercentProcessorPerformance / 100`.

### 1-12. 결과표에서 열 일부가 안 보임
- **원인**: `Format-Table`은 속성이 10개를 넘으면 일부 열을 숨긴다.
- **해결**: `Format-Table -Property * -AutoSize | Out-String -Width 400`.

### 1-13. 테스트 로그(server.txt)를 읽으면 한글이 깨짐
- **증상**: `Get-Content ... -Encoding UTF8`로 `echo_test.ps1`의 `server.txt`를 읽으면 `[stat] ����=253`처럼 깨짐
- **원인**: 서버 콘솔 출력을 파일로 리다이렉트하면 콘솔 코드 페이지(CP949)로 저장된다. 소스(UTF-8 BOM)와 인코딩이 다르다.
- **해결**: `Get-Content 파일 -Encoding Default`로 읽는다.
- **재발 방지**: 테스트 로그는 CP949, 소스·스크립트는 UTF-8 BOM, cfg는 BOM 없는 UTF-8 - 읽는 파일 종류마다 인코딩을 맞춘다.

### 1-14. cfg를 스크립트로 만들었더니 키 이름이 바뀜
- **증상**: 채팅 클라가 에코 모드로 돌아 서버가 모든 패킷을 잘못된 채팅 패킷으로 끊음(`잘못된패킷` 7만, `입장=0`). 만든 cfg에 `roomSize = 16;` 대신 `16Size = 16;`
- **원인**: 자리표시자 `ROOM`을 `-replace 'ROOM', '16'`으로 바꿨는데, PowerShell `-replace`는 **대소문자를 구분하지 않아** `roomSize`의 `room`까지 바뀌었다. 파서는 모르는 키를 무시하고 roomSize는 기본값 0(에코)이 됐다.
- **해결**: 대소문자를 구분하는 `-creplace`로 다시 만듦.
- **재발 방지**: 스크립트에서 문자열을 바꿀 때는 `-creplace`를 쓰고, 자리표시자는 다른 단어와 겹치지 않는 형태(`@@ROOM@@` 등)로 한다. 클라가 시작할 때 찍는 설정값(`[main] roomSize = ...`)으로 cfg가 의도대로 읽혔는지 먼저 확인한다.

### 1-15. 백그라운드 측정이 중간에 끊기고 cfg가 측정용 값으로 남음
- **증상**: `load_sweep.ps1`을 백그라운드로 돌리다 3회차 도중 exit code 4로 종료. 이후 `server.cfg`에 `chatRoomCnt = 256`, `client.cfg`에 `roomSize = 4`가 남아 있었다
- **원인**: 세션이 끝나면서 백그라운드 작업이 함께 종료돼 스크립트의 `finally`(cfg 원복)가 돌지 못했다.
- **해결**: `git diff`로 측정용 값만 바뀐 것을 확인하고 `git checkout --`으로 되돌린 뒤 다시 측정.
- **재발 방지**: 긴 측정 뒤에는 결과보다 먼저 `git status`로 cfg가 원래대로인지 본다. 측정 중에는 세션을 유지한다.

### 1-16. 서버 통계 스레드가 수 초씩 멈춰 회차 값이 0 또는 부풀려짐
- **증상**: 채팅 방 16 측정 36회 중 4회에서 서버 `[stat]` 줄이 3–13개뿐(정상 약 20개). 한 회차는 첫 줄 `전달/s=4974501`(클라가 받은 48만의 약 10배) 뒤로 통계가 끊겨 정상 구간이 비고 0으로 집계됐다. 같은 실행들에서 클라 `connectFail` 256–512(서버가 늦게 받기 시작)
- **원인(추정, 미확인)**: 방 16 부하에서 통계 스레드가 CPU를 못 받아 수 초씩 늦게 돌았다. 1초 구간 길이를 카운터를 읽기 전에 재므로, 그 뒤에 늦어지면 여러 초 분량이 1초로 나뉘어 부풀려진다.
- **해결(이번 결과)**: 영향받은 회차는 클라 수신량과 교차 확인했다 - 0이 된 1회는 3회 중 최솟값이라 중앙값에 영향 없고, 나머지 3회는 서버 값이 클라 값과 맞았다.
- **추가 관찰 (2026-11-01)**: 부하가 작은 에코 테스트(10초)에서도 서버 통계 5줄(정상 약 15줄), EchoClient 출력 1줄 반으로 **서버와 클라의 1초 출력이 같은 시간대에 함께 멈췄다**. 클라는 죽지 않았고(마지막 쓰기 시각 = 스크립트가 강제 종료한 시각, 에러 출력 없음), 정상 클라 끊김 0·세션 0·정상 종료. 같은 조건을 다시 돌리면 통계 22줄로 정상 → 서버 통계 스레드만의 문제가 아니라 **PC 전체가 수 초 멈춘 것**으로 보인다(원인 미확인)
- **재발 방지**: 범위(최소–최대)에 0이나 몇 배 차이가 보이면 그 회차 로그의 통계 줄 수부터 본다. 근본 수정 후보: 구간 길이를 카운터를 읽는 순간 기준으로 재기, 통계 스레드 우선순위 올리기(미적용).

### 1-17. 측정 도중 서버를 못 띄워 load_sweep이 1회차에서 멈춤
- **증상**: `Start-Process : This command cannot be run due to the error: Access is denied.` - 2×2 측정(24조건 × 3회)이 1회차 19번째 실행에서 끝나고, 그때까지의 1회차 결과만으로 요약표가 나옴(exit code 0이라 알아채기 어려움). 실패한 실행 폴더의 `server.txt`는 0바이트
- **원인(추정)**: 직전 실행의 서버가 13:15:11에 종료를 마친 같은 초에 다음 서버를 띄웠다. 이전 프로세스가 완전히 사라지기 전에 같은 exe를 다시 실행해 거부된 것으로 보인다. 앞서 몇 번 본 "시작 직후 connectFail 256–512"도 같은 원인일 수 있다
- **해결**: `load_sweep.ps1`이 실행마다 이전 서버 프로세스가 사라질 때까지 기다리고(`Wait-NoServer`, 최대 15초), 실패하면 3초 뒤 한 번 더 시도, 그래도 안 되면 그 실행만 건너뛰고 경고를 남긴다
- **재발 방지**: 측정 결과를 볼 때 요약표의 범위가 한 값(`a~a`)이면 회차 수부터 확인한다. 출력에서 `[경고]`를 찾는다

### 1-18. 대소문자만 바꾸는 이름 변경이 파일에 저장되지 않음
- **증상**: 스크립트로 `header.len` → `header.Len`처럼 바꿨는데 "변경" 출력도 없고 파일도 그대로였다 (2026-11-02, 코딩 규칙 적용 중 클라 참조 수정)
- **원인**: 바뀌었는지 `if ($new -ne $old)`로 확인했는데, PowerShell의 `-ne`/`-eq`는 **대소문자를 구분하지 않는다**. 대소문자만 다른 두 문자열을 같다고 보고 저장을 건너뛰었다
- **해결**: 대소문자를 구분하는 `-cne`로 비교해 다시 저장
- **재발 방지**: 문자열을 비교할 때는 `-ceq`/`-cne`, 바꿀 때는 `-creplace`(1-14와 같은 함정). 이름 변경 뒤에는 옛 이름을 `Select-String -CaseSensitive`로 다시 찾아 0건인지 확인한다

### 1-19. 훅 스크립트가 한글 경로를 못 읽고 조용히 통과함
- **증상**: 코딩 규칙 훅(`tools/check_cpp_style.ps1`)에 위반 파일 경로를 JSON으로 넘겼는데 출력 없이 exit 0 (2026-11-02, 경로에 사용자 폴더 `정민혁`이 들어간 시험 파일)
- **원인**: PowerShell 5.1은 stdin을 콘솔 코드 페이지(CP949)로 읽는다. Claude Code는 훅 입력 JSON을 UTF-8로 보내므로 한글 경로가 깨져 `Test-Path`가 거짓 → 검사할 파일이 없다고 보고 통과했다. 출력(stderr)도 같은 이유로 UTF-8로 맞춰야 Claude가 한글 메시지를 읽는다
- **해결**: 스크립트 맨 앞에서 `[Console]::InputEncoding`과 `[Console]::OutputEncoding`을 BOM 없는 UTF-8로 설정
- **재발 방지**: Claude Code와 주고받는 PowerShell 스크립트(훅 등)는 입출력 인코딩을 UTF-8로 먼저 맞춘다. 훅을 시험할 때는 입력 JSON을 `ConvertTo-Json`으로 파일에 만들어 넘긴다 - bash `echo "..."`는 `\\`를 `\` 하나로 바꿔 JSON이 깨진다

## 2. 코드 버그 (실행·테스트에서 발견)

### 2-1. 서버 핑을 넣은 뒤 정상 연결이 끊김
- **증상**: EchoClient `unexpectedClose=2`, 서버 `넘침끊김=2`
- **원인**: EchoClient는 "돌아오지 않은 에코 바이트"를 서버 송신 링 크기(16384B) 이하로 유지해 왔는데, 서버 핑(15B)도 같은 링 자리를 차지해 링이 꽉 찬 순간 에코가 들어가지 못했다.
- **해결**: 클라 한도를 링 크기 - 1KB(15360B)로 낮추고, 서버는 링이 가득 차면 **핑만 버리고 연결은 유지**(`건너뜀` 통계). `Data`만 넘칠 때 끊는다.
- **재발 방지**: 라이브러리 제어 패킷을 새로 넣을 때 송신 링 자리 계산에 포함한다. 측정 때문에 정상 연결이 끊기면 안 된다.

### 2-2. 큐 한도를 줄였더니 에코가 멈춤
- **증상**: `maxInflight=1024`에서 `EchoKB/s=0`, `4096`에서 처리량 1/4로 감소와 퐁 표본 급감
- **원인**: 한도가 최대 패킷(4099B)보다 작으면 큰 패킷을 중간까지만 보내고 멈추는데, 서버는 미완성 패킷을 에코하지 않아 한도가 영원히 안 빈다(교착). 퐁도 패킷 경계에서만 나가서 같이 막혔다.
- **해결**: `maxInflight`가 `MAX_PACKET_SIZE`보다 작으면 `init`에서 거부.

### 2-3. 지연 히스토그램의 백분위수가 틀릴 수 있음
- **증상**: 코드 검토 중 발견 - 0µs 칸이 답일 때 값이 다음 칸으로 덮어써진다.
- **원인**: "아직 못 찾음"을 값 0으로 표시했다.
- **해결**: `found50` 같은 별도 플래그로 판정.

### 2-4. 패킷 단위 수신 전에는 클라 송신 중 퐁을 끼우면 스트림이 깨질 위험
- **원인**: EchoClient는 서버 재조립을 시험하려고 데이터를 패킷 중간에서도 잘라 보낸다. 그 사이에 퐁을 끼우면 서버가 받는 스트림이 깨진다.
- **해결**: 퐁(제어 패킷)은 대기열에 두고 데이터 스트림이 **패킷 경계**에 올 때만 보낸다(`mCtrlQueue`).

### 2-5. 묶음을 키우자 LoadClient 연결이 넘침으로 끊김 (GQCSEx 64의 EchoClient 넘침도 같은 원인)
- **증상**: `msgSize × overSend` = 12KB(한도 15,360B 이내)인데 서버 `넘침끊김` 455건(4KB×3), 2.9만 건(32B×384)
- **원인**: 클라는 에코를 다 받으면 바로 다음 묶음을 보내지만, 서버는 **송신 완료를 처리해야** 송신 링에서 그 데이터를 뺀다(송신 완료까지 2~4ms). 그래서 송신 링에 "송신 완료 대기 중인 이전 묶음 + 다음 묶음"이 같이 있을 수 있다. 데이터가 상대에게 도착한 것과 링에서 빠진 것은 다른 시점이다.
- **해결**: LoadClient 묶음 한도를 `(16384 - 1024) / 2` = 7,680B로 낮춤(`MAX_BATCH_BYTES`). 크기 비교는 4KB 묶음으로.
- **재발 방지**: 클라가 "응답을 받았으니 서버 버퍼가 비었다"고 가정하지 않는다. 송신 완료가 늦게 처리되는 GQCSEx 큰 배치에서 같은 넘침이 나는 것도 이 때문이다.

### 2-6. (미해결) 정상 EchoClient가 가끔 넘침으로 끊김
- **증상**: 기본 설정(GQCS, 워커 2) 15초 에코 테스트 6~7회 중 1~2회 정상 클라 `unexpectedClose=1`, 서버 `넘침끊김` +1 (2026-10-26)
- **원인**: 2-5와 같다. EchoClient는 "돌아오지 않은 에코 바이트 ≤ 15,360B"로 서버 송신 링(16KB)을 지키려 하지만, 송신 링은 **송신 완료 통지를 처리해야** 비워진다. 완료가 IOCP 큐에서 ~2ms 기다리는 동안 이미 클라에 도착한 데이터가 링을 차지해, 클라 기준으로는 한도 안인데 링이 넘친다.
- **원인 확인 (2026-10-29, i5-8600 PC)**: 넘침 순간 송신 링을 "이미 WSASend에 넘긴 바이트(가)"와 "아직 안 넘긴 바이트(나)"로 나눠 찍는 진단 출력으로 확인.
  - 정상 EchoClient 넘침: `링사용=14517 (가)=14517 (나)=0 송신경과=8476us` → 링 전체가 이미 클라에 도착한 데이터. 완료 통지가 처리되지 않아 자리가 안 빈 것
  - 대조(받지 않는 클라): (나)가 1.2만~1.5만B, WSASend 경과 77~166ms → 진짜 느린 클라는 (나)가 쌓인다
  - 판별 근거: 정상 클라는 에코 안 온 바이트 ≤ 15,360B를 지키고, (나)는 클라에 도착하지 않은 바이트이므로 정상 클라라면 (나) ≤ 15,360B. 넘침 기준을 (나)로 바꾸면 정상 클라는 끊기지 않고 느린 클라는 그대로 잡힌다
- **재현 조건**: 버그 빈도는 송신 완료 지연에 비례한다. 이 PC는 기본 설정(워커 2)에서 송신 완료까지 17us라 정상 에코 21회 중 1회뿐(에코 + LoadClient도 3회 중 0회). **워커 1 + EchoClient + LoadClient**(송신 완료까지 10~11ms)에서 처음 3회 중 1회 재현했으나, 수정 전 빌드를 번갈아 더 돌리니 16회 중 1회로 드물었다 → 이 PC에서는 반복 횟수로 수정 효과를 보일 수 없다. 지연만으로는 부족하고 "큰 송신이 완료를 기다리는 사이 클라가 다음 데이터를 보내는" 타이밍이 맞아야 하는 것으로 보인다
- **측정 해석 실수**: 수정 전 3회 중 1회만 보고 "수정 후 9회 중 0회"를 효과의 근거로 삼았다. 수정 전 빈도가 1/16이면 18회 연속 0이 나올 확률은 약 30%. 재발 방지: 수정 전후 비교 전에 같은 조건에서 수정 전 빈도부터 충분히 확인한다. 드문 버그는 조건을 주입해 재현한다 - `server.cfg` `testSendCompleteDelayMs`(송신 완료 처리 전 Sleep)로 수정 전 15초마다 244~386회 끊김, 수정 후 0회를 결정적으로 확인(2026-10-29)
- **본질**: 서버의 넘침 정책이 "느린 클라"와 "서버의 완료 처리 지연"을 구분하지 못한다. 서버가 바쁠수록 정상 클라를 끊는다.
- **해결 방향**: 클라 한도를 줄이는 임시 조치는 하지 않기로 함(사용자 결정). 1단계: 넘침 기준을 (나)로 변경 + 송신 링 2배 + 명시적 송신 묶기. 2단계: 버퍼 조각 송신 큐는 직렬화 버퍼와 함께(CLAUDE.md 다음 할 일 0번).
- **재발 방지**: 버퍼 한도 정책을 만들 때 "그 버퍼가 비워지는 시점"이 상대가 관찰하는 시점과 같은지 확인한다.
- **이후 (2026-11-02)**: 판정을 "송신 링이 가득 차면 끊기"로 되돌렸다(사용자 결정, 링 32KB). 완료 대기 몫을 다시 세지만 링이 EchoClient 한도(15,360B)의 2배보다 커서 정상 에코 클라는 구조로 안 끊긴다 - 지연 주입 9회 모두 0. 링을 줄이거나 클라 한도를 늘릴 때는 이 관계(클라 한도 × 2 ≤ 링)를 지킬 것

### 2-7. (관찰, 원인 미확인) 브로드캐스트에서 정상 LoadClient가 넘침으로 끊김
- **증상**: 수정 전·후 비교 측정 72회 중 1회(수정 전 빌드, skip 끔, 방 16, 워커 4, 1회차) 서버 `넘침끊김=4`, 클라 `unexpectedClose=4`. 같은 실행에서 시작 직후 `connectFail=512`와 통계 스레드 멈춤(1-16, 통계 7줄)도 함께 있었다 (2026-11-01)
- **추정 원인**: 방송에서는 받는 사람 B의 "아직 안 넘긴 바이트"에 방 전원의 메시지가 쌓인다. B의 클라가 아무리 잘 받아도 다른 보낸 사람들의 속도는 B가 정하지 못하므로, 2-6과 같은 방식(클라 한도로 서버 링을 지키기)이 통하지 않는다. skip 끔이면 B의 송신이 완료를 기다리는 수 ms 동안 링에만 쌓여 한도(16KB)에 닿을 수 있다 - LoadClient 제약 `roomSize × overSend × msgSize ≤ 15360`은 보낸 사람마다 묶음 1개라는 가정인데, 자기 묶음이 돌아온 보낸 사람은 B의 송신이 끝나기 전에 다음 묶음을 보낼 수 있다
- **현재**: 1회뿐이고 서버가 멈췄던 실행이라 재현 조건을 모른다. 수정 후 빌드는 36회 중 0회
- **추가 발생 (2026-11-01, 수정 후 빌드)**: 멈춘 2×2 측정에서 수신 단위 · skip 끔 · 방 4 · 워커 4 1회 7건. 다시 돈 2×2(72회)에서 **워커 4 · 방 16에서만** - 묶음 단위 · skip 끔 3회 중 1회 206건(측정 중반부터 끊기고 재접속 클라가 또 끊김), 묶음 단위 · skip 3회 중 2회 각 1건. 모두 서버 처리량이 가장 높은 조건(전달 780만–1040만/s)
  - 처음 추정(클라가 늦게 읽어 WSASend가 대기로 넘어감)은 **로그로 기각**: 넘침이 난 초에도 `송신즉시=100.0%`, `송신반환 대기=0.00`(워커가 건 WSASend 중 대기 0) - 커널 송신 버퍼는 여유가 있었다. 끊긴 이유는 **우리 송신 링의 "안 넘긴 몫"이 16KB를 넘은 것**, 즉 서버가 그 받는 사람에게 한동안 WSASend를 부르지 않은 것
  - 원인 1 (묶음 단위 · skip 끔, 206건): 송신 중 표시가 송신 완료 처리까지 켜져 있다 - 넘침 시작 순간 송신 완료까지가 4.2–4.7ms → 6.2–7.2ms로 늘었다. 그동안 다른 보낸 사람의 다음 묶음들이 쌓임 = 2-6과 같은 구조(서버의 완료 처리 지연을 클라 탓으로 셈)
  - 원인 2 (묶음 단위 · skip, 2건) - **모아 보내기 일반화 설계의 허점**: B가 워커1의 보낼 목록에 있는 동안(`mFlushQueued = true`) 다른 워커는 B에게 넣기만 한다. 워커1의 묶음(최대 64완료)이 길어지는 사이 다른 워커들이 여러 바퀴 돌면 B에게 **여러 바퀴 분량**이 쌓인다. "보낸 사람마다 한 바퀴분(방 16 최대 약 8KB)"이라는 가정이 틀렸다
  - 고칠 후보: **조기 보내기**(넣은 뒤 안 넘긴 몫이 한도의 절반을 넘으면 묶음 끝을 기다리지 않고 그 자리에서 postSend - 원인 2 해결, 평소 모으기는 유지), 한도 키우기(여유만 늘림), 시간 기준 판정(원인 1까지 - 송신 큐 2단계와 함께)
  - **재발 방지**: 미루는 구조를 만들 때 "미루는 동안 쌓일 수 있는 최대량"을 다른 스레드가 여러 바퀴 도는 경우까지 넣어 계산한다
- **재발 방지(할 일)**: 방송 트래픽의 넘침 기준을 다시 설계할 때(송신 큐 2단계) 받는 쪽 한도를 "보낸 사람 수 × 묶음"이 아니라 시간 기준(가장 오래된 미전송 데이터의 나이) 등으로 볼지 검토

## 4. 측정 해석 실수 (숫자는 맞았지만 잘못 읽을 뻔한 것)

### 4-1. 처음 잰 처리량이 서버가 아니라 측정 클라의 한계였다
- **증상**: 에코 160MB/s에서 정체, 워커를 늘려도 그대로
- **원인**: EchoClient가 4스레드에 3.95코어로 포화(바이트 단위 생성·검증 비용)
- **해결**: 클라 CPU를 "사용 코어 / 스레드 수"로 출력하고, 처리량 전용 LoadClient를 따로 만들었다.
- **재발 방지**: 처리량 숫자를 볼 때 **서버와 클라 CPU를 항상 같이** 본다. 클라가 먼저 포화면 그 숫자는 쓰지 않는다.

### 4-2. 같은 조건이 회차마다 30% 넘게 달랐다
- **원인**: 노트북 전원 모드와 하이브리드 CPU의 스레드 배치·클럭 변화
- **해결**: 전원 연결 + 최고 성능 모드 + 조건마다 3회, 회차마다 실행 순서 돌리기 + 중앙값 → 편차 ±1~9%

### 4-3. 표의 클라 CPU 4.34가 "4개 중 4.34"로 읽힘
- **원인**: 클라 2개 조건은 두 프로세스의 합(워커 8개 중)인데 분모를 안 적었다.
- **해결**: CPU는 항상 "사용 코어 / 스레드 수"로 표기. `load_sweep.ps1`은 스레드 수를 클라 출력에서 읽는다.

### 4-4. 서버 CPU %가 작아 보여 판단이 어려움
- **원인**: `CpuSampler`는 PC 전체(14스레드) 대비 %라 1코어 = 7.1%
- **해결**: 서버 출력을 `cpu코어=사용코어/워커수 (커널 %)`로 바꿨다.

### 4-5. 크기가 다른 조건이 한 줄로 합쳐져 처리량 범위가 62만~546만으로 나옴
- **증상**: `32x16` 줄의 패킷/s 범위가 627,425~5,465,658, `32x128`(GQCS·GQCSEx) 줄이 표에서 사라짐
- **원인**: `load_sweep.ps1`이 조건을 `MsgSize`로만 묶어 같은 32B인 `32x16`과 `32x128`이 한 그룹이 됐다.
- **해결**: 그룹 키에 `OverSend` 추가, CSV에서 다시 집계.
- **재발 방지**: 범위(최소~최대)가 몇 배씩 벌어지면 측정 편차보다 **집계 키**를 먼저 의심한다. 조건 문자열의 모든 축을 그룹 키에 넣는다.

### 4-6. 프로파일러를 켠 채 GQCS와 GQCSEx를 비교함
- **증상**: GQCSEx 이득이 프로파일러를 켰을 때와 껐을 때 다르게 나옴
- **원인**: 프로파일 기록 비용이 호출 횟수에 비례한다. GQCS는 완료마다 `GQCS` 태그를 기록하고 GQCSEx는 64개에 1번이라, 기록 비용이 GQCS 쪽에만 더 붙는 **혼입 변수**였다.
- **해결**: `Profile::SetEnabled`(`server.cfg` `profile`)로 처리량 비교는 끄고 재고, 프로파일은 비용 분해에만 쓴다.
- **재발 방지**: 측정 도구의 비용이 비교 대상마다 다르게 붙는지 먼저 따진다. 처리량 숫자와 프로파일 숫자를 같은 실행에서 얻지 않는다.

### 4-7. 송신 완료까지 2~4ms를 "ACK 대기"로 해석함
- **원인**: 송신 버퍼 0 실험에서만 본 숫자로 판단했다. 기본 설정(즉시 성공 100%)에서도 2.5~4.2ms였다.
- **해결**: IOCP 큐에서 완료 통지가 기다린 시간으로 정정. skipOnSuccess(큐를 거치지 않음)에서 41µs로 떨어져 확인됨.
- **재발 방지**: 해석 전에 대조 조건(기본 설정)에서도 같은 숫자가 나오는지 본다.
